## Major

### M1. 讨论 embed 读、写中继在烧掉 jti 之前不核对组织

审查基线：

- `packages/core-backend/src/routes/plm-embed-discussion.ts:138-160`
- `packages/core-backend/src/routes/plm-embed-discussion-read.ts:123-145`

两条中继只比较 `claims.tenant_id` 和数据源实际服务的租户，然后就 `consumeEmbedJti`，再把调用方的 embed token 交给已配置的源。同一租户的另一个组织，以及根本没有 `org_id` 的 token，都会通过。BOM context（`plm-embed.ts:107-110`）和 visual HTTP 中继已经按“组织必须相等，任一侧缺失都拒绝，并且发生在 jti 和 provider 之前”收过口。讨论交换不使用集成账号去读被服务组织的 BOM，所以它不是那条用源凭据跨组织读 BOM 的洞。它仍是同一类中继准入：失败方向是开放，并且会消耗一次性 jti。定为 Major，不定为 Blocker。

修复后：写中继 `plm-embed-discussion.ts:147-150`，读中继 `plm-embed-discussion-read.ts:131-134`。缺组织或组织不一致返回 `403 EMBED_ORG_MISMATCH`，不消费 jti，不调用交换。提交 `12f16f1990d0b76e1231c4bf71a3ffacf555e05d`。

### M2. 审批卡包关闭后，持有人不能销毁已保存的授权

审查基线：

- 路由对所有方法先调用 `requirePlmApprovalCard()`，失败即 `404 PLM_CARD_DISABLED`：`packages/core-backend/src/routes/plm-approval-bindings.ts:14-21`
- `unbind` 走 `bound()`，而 `bound()` 无条件调用 `requirePlmApprovalCard()`：`PlmPersonalApprovalBindingService.ts:128` 与 `:246-248`

`PLM_APPROVAL_CARD_ENABLED` 不是精确 `'true'` 时，`DELETE` 到不了清授权的 `UPDATE`。加密 grant、未完成任务和已发出的卡片会留在库里；包重新打开后，旧授权会恢复成可用。设计说明把解绑定义成销毁 grant、撤回任务和卡片，并且不签发决定（同一文档第 72 行）。BOM 个人写回的解绑已经不看开关（`PlmPersonalBomWriteBindingService.ts:493-497`）。审批卡这条没有对齐。

修复后：只有非 `DELETE` 才要求开关（`plm-approval-bindings.ts:37-49`）。`unbind`（`PlmPersonalApprovalBindingService.ts:246-270`）在持有人事务里 `SELECT ... FOR UPDATE`，清空 `encrypted_grant`，把任务标成不活跃，把已发送卡片标成 `revoked`。不调用 provider，不写审批决定。列表、绑定、同步、对账仍然关闭。提交 `7294145a9c3628b96d163b61a1d44cfa334c3ae0`。

### m2. 共享账号的 `approveApproval` / `rejectApproval` 仍会 POST

审查基线 `PLMAdapter.ts:3592-3632`。非 mock、`apiMode === 'yuantus'` 时，这两个方法用适配器自己的 `select`（集成凭据）POST 到 ECO approve/reject。生产决策门已经在更外层拒绝：桥 `ApprovalBridgeService.ts:1282-1288` 在本地决策写入之前抛 `409 PLM_PERSONAL_BINDING_REQUIRED`；federation `federation.ts:2030-2087` 直接返回同一个 409，不调用适配器。当前没有生产调用点。方法本身仍是一条共享账号写路径，mock 模式还会返回伪造的已批准结果。

修复后 `PLMAdapter.ts:3594-3599`：两种模式都返回 `PLM_PERSONAL_BINDING_REQUIRED`，不发请求。提交 `f166663edf4dc8f947b4c49ea3110c4b06b50347`。

### m3. PLM 镜像的 `canDecideCurrentNode` 仍为 true

审查基线 `approval-seat-authorization.ts:234`。`decisionDoorIsSeatGated` 对 `plm:` 前缀返回 false，于是 `resolveCanDecideCurrentNode` 对 pending 的 PLM 镜像返回 true。桥已经拒绝这类决定，待办和详情却把“可以决定”交给客户端。

修复后同一函数在座位门之前返回 false（`approval-seat-authorization.ts:235-237`）。没有 published definition 的旧平台单，以及售后单，仍然返回 true，因为那些门还接受决定。副作用被限制在共享谓词上：旧的 `POST /:id/approve` 查询要求 `source_system = 'platform'`（`approvals.ts` 里该 `SELECT`），普通 PLM 行到不了这里；若有一行 `plm:` 前缀却被标成 platform，现在会 `403`，不再在本地结案。注释已改到和这个谓词一致，提交 `55156511e3422a5472f47e14ddbf3e8d89e21461`。行为提交是 `f166663edf4dc8f947b4c49ea3110c4b06b50347`。

### m4. 个人 BOM 写回开关关闭时仍先插入尝试审计

审查基线 `plm-workbench.ts:1168-1195`（ECO 意图在 `:1310` 一带同样先插入再派发）。开关关闭时，请求在通过身份解析之后仍写入 `operation_audit_logs`（`status_code` 0），然后派发才以 404 失败。关包应当没有审计行，也没有派发。开关打开时“先提交尝试审计、审计失败则 503 且不派发”保持不变。结果审计失败不改变源系统已经成功的响应，这一层没有改。

修复后 `refusePersonalBomWriteWhenDisabled`（`plm-workbench.ts:957-966`）在行写回（`:1182`）和 ECO 意图（`:1324`）上，位于身份解析之后、`insertPlmWritebackAudit` 之前。开关不是精确 `'true'` 时返回 `404 PLM_BOM_WRITE_DISABLED`。身份不合法仍是 403，缺幂等键仍是 400。提交 `f28e2bc6046b24f7ba0f76f93de5c582b6f5160a`。

### m5. BOM 评审 realdb 的后台 worker 可能打到非回环 webhook

`plm-bom-review-service.ts:1263` 的完成投递使用全局 `fetch`，目标来自 `multitable_webhooks.url`。专用完成用例使用回环地址，并先停用其它 webhook。两个不筛选 webhook 的 worker（realdb 文件里 `two real background workers` 与相邻的 SLA 用例）没有先停用非回环行。当前夹具的 owner 没有 `multitable:send_webhook`，`prepareCompletion` 会取消而不是 `fetch`。一旦夹具或库里留下发送权限和非回环 URL，worker 会真的 POST，双 worker 用例还会因为抛错把 `failures` 计成非 0。

修复只在测试里：`plm-bom-review-realdb.test.ts:157-168` 在未设置 `W20_PROVIDER_DIR` 时拒绝非回环 `fetch`；`:100-116` 的 `parkRemoteWebhooks` 在这两个 worker 之前停用非回环行，并在 `finally` 里按原 `active` 恢复。`W20_PROVIDER_DIR` 是显式的真实 provider 排练，守卫故意跳过。提交 `12c440848300083e35e09cb3532593c37e3cab22`。该文件没有在本环境执行，见测试一节。

## 核对过、没有改

- 没有第三套审批引擎。平台 N-of-M 仍是 `ApprovalProductService` 对 `approval_records.actor_id` 的 `COUNT(DISTINCT actor_id)`（约 `ApprovalProductService.ts:13236-13265`）。PLM 决定不进入这套计数。个人卡把命令交给圆图，回执模式要求 `actor_auth_user_id`、`seat_status`、`stage_complete`（`plm-personal-approval-wire.ts:76-91`）。阶段是否完成由圆图回执表达，MetaSheet 不替 PLM 计法定人数。
- 个人审批 grant 是 `yua_`，个人 BOM 写回 grant 是 `yuw_`，用途字段分开（`plm-personal-approval-wire.ts:96`，`plm-personal-bom-write-wire.ts:69`）。
- 写回的对象权限在授权之前：`getOwnedDataSource` 先于 `isFeatureAvailable`（`plm-workbench.ts:1113-1151`）。未授权是 403 `not-entitled`，不跳过所有权。
- 共享账号的 BOM 行更新和 ECO 意图方法已经返回 `PLM_BOM_WRITE_UNCREDENTIALED_REFUSED`（`PLMAdapter.ts:2779`、`:2790`）。
- BOM 评审状态机仍是库约束：待评审、评审中、有问题、已完成，以及已完成再打开。`disable` 把绑定停在终态，完成投递要求 `status === 'active'`（`plm-bom-review-service.ts:1117`）。协作快照是评审状态，不是 PLM 提交结果。
- 开关打开时，尝试审计先于派发；尝试审计失败是 503 且不派发。结果审计失败只记日志。意图表里的 outcome 更新和这次 HTTP 审计不是同一层：outcome 写在派发事务里，写失败会回滚本地意图并在同一幂等键上再次调用源系统。这是既有的 unknown / 可恢复边界，这次没有把它改成“先对外提交再补本地状态”。

## 延后

- `ENABLE_PLM` 仍走 `parseBooleanEnv`，未设置时在平台模式下默认开启（`product-mode.ts:3-24`）。协作包开关（评审、审批卡、个人 BOM 写回、visual embed）已经是精确 `'true'`。把产品模式改成精确字面量会改变所有未设置该变量的部署，超出这个可选包。残留风险：`yes` / `on` / `1` 仍能打开产品面。
- 不在 `verifyEmbedToken` 里全局强制 `tenant_id` 和 `org_id`。源凭据读路径和讨论中继已经在消费 jti 之前失败关闭。全局校验会拒绝不是 embed 业务令牌的现有夹具，这次没有扩大这个验证器。
- 只关闭 `PLM_BOM_REVIEW_ENABLED` 时，讨论中继是否仍随 `ENABLE_PLM` 挂载，是产品面取舍。现有包开关本身没有因此被绕开。
- `completionWebhooks` 通过 `completionAccess`（`plm-bom-review-service.ts:1279-1322`）更新配置，不看绑定是否 `active`。投递仍要求 active。关闭期间可以改规则，不会因此发出。收紧写入需要单独的产品决定，这次不改。
- 生产完成 webhook 没有主机白名单（`plm-bom-review-service.ts:1263`）。客户配置的 URL 是合法目的地，加白名单会在没有产品决定时打断现有接收方。测试侧已经拒绝非回环，生产行为未改。
- 平台 N-of-M 把 `system:auto-approval` 算进 distinct `actor_id`。那是平台引擎的计数，不是 PLM 法定人数。这次不改平台计数。
- 历史本地 `approval_records` 仍可能出现在 PLM 历史读模型里。新的决定路径已经拒绝共享账号写入。清理历史行不是这次的权限修复。
- 个人写回意图上的 `binding_id` 没有外键。缺外键不改变这次的锁顺序和拒绝语义。
