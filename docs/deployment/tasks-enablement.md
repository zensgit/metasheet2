# 任务功能开通指引（on-prem 管理员）

适用对象：负责 on-prem 部署的管理员。
目标：让普通员工能打开「任务」，能创建任务，也能被派发任务。

任务功能默认关闭。要开通，需要按顺序做四件事。
前三步是一次性的。第四步对每个要使用任务的人都要做。

前提：要使用任务的员工，账号必须已启用，并且是当前组织的成员（用户详情里「所属组织」包含当前组织）。不满足时，派发会提示这个人不是当前组织的有效成员，见文末常见问题。

| 步骤 | 做什么 | 谁来做 |
| --- | --- | --- |
| 1 | 打开后端开关并重启 | 部署管理员（服务器上操作） |
| 2 | 建一个带两个任务权限的角色 | 平台管理员 |
| 3 | 把角色分配给员工 | 平台管理员 |
| 4 | 为每位员工开通「任务」使用 | 平台管理员 |

平台管理员始终可以使用任务，不需要做步骤 2 到 4。
下面所有「管理员」操作，都要用平台管理员账号登录。

## 步骤 1：打开后端开关并重启

在界面上没有这个开关。它是后端的环境变量。

顺序很重要：先把部署或升级包的步骤全部做完，再把这个开关作为单独的一步写进 `app.env`，然后重启后端。
以后每次升级也一样：升级完成后，确认这一行还在、写法不变，再重启。

1. 打开部署目录下的 `docker/app.env`。
2. 加入一行，写法必须完全一致：

   ```env
   TASKS_ENABLED=true
   ```

   - 只认小写 `true`。写成 `TRUE`、`1`、`true ` 或 ` true` 都不会生效。
   - 同一个键只写一次。文件里已经有这一行时，原地修改，不要在末尾再加一行：不同的启动方式对重复的行取值不同。
3. 重启后端，让新值生效。

用 PM2 的部署（默认）：先把 `app.env` 读进当前终端，再带 `--update-env` 重启。
只改文件、直接 `pm2 restart`，新值不会生效。

```bash
cd /opt/metasheet
set -a; source docker/app.env; set +a
pm2 restart metasheet-backend --update-env
pm2 save
```

用 systemd 的部署：`systemctl restart metasheet-backend.service`。
直接用代码仓库里的 Docker Compose 文件部署的环境（on-prem 包里没有 Compose 文件）：重建后端容器，例如 `docker compose -f docker-compose.app.yml up -d backend`。
Windows 无 Docker 部署：按该部署文档里的重启方式操作，同样要带 `--update-env`。
如果你的服务名或目录不同，以你实际的部署为准。

开通后，已登录的员工刷新页面或重新登录，顶部才会出现「任务」入口。

API 校验（自动化用）：用任意已登录账号请求当前用户接口。
返回里 `data.features.tasks` 为 `true`，表示后端开关已生效；为 `false` 表示开关没有生效。

```bash
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/api/auth/me"
```

也可以请求任务接口：返回 200 表示开关已生效；返回 404 表示开关没有生效。
（这个接口还要求账号本身能使用任务，所以请用平台管理员账号，或已做完步骤 2 到 4 的员工账号。）

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/tasks/context"
```

## 步骤 2：创建「任务成员」角色

角色需要包含两个任务权限：

| 权限码 | 界面里显示的名称 | 作用 |
| --- | --- | --- |
| `tasks:read` | 任务读取 | 看到「任务」入口，查看任务 |
| `tasks:write` | 任务写入 | 创建、修改任务，派发任务 |

不要勾选「任务管理」（`tasks:admin`）。目前没有任务功能用到它，普通员工不需要。

在产品里操作（以界面为准，待验收时核对）：

1. 进入「角色管理」页面（地址 `/admin/roles`）。
2. 点「新建角色」。
3. 「角色 ID」填 `tasks_member`。「角色名称」填 `任务成员`。
4. 在「权限映射」里勾选「任务读取」和「任务写入」。
5. 点「创建角色」。

API（自动化用）：

```bash
curl -s -X POST "$BASE/api/roles" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"id":"tasks_member","name":"任务成员","permissions":["tasks:read","tasks:write"]}'
```

## 步骤 3：把角色分配给员工

在产品里操作（以界面为准，待验收时核对）：

1. 进入「用户管理」页面（地址 `/admin/users`）。
2. 在用户列表里点中这位员工，打开详情。
3. 找到「角色操作」，在下拉框里选「任务成员 (tasks_member)」。
4. 点「分配角色」。

API（自动化用）：

```bash
curl -s -X POST "$BASE/api/admin/users/$USER_ID/roles/assign" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"roleId":"tasks_member"}'
```

## 步骤 4：为员工开通「任务」使用

只分配角色还不够。每位员工还要单独开通「任务」使用。
必须先做完步骤 3，员工详情里才会出现「tasks」这一项。

在产品里操作（以界面为准，待验收时核对）：

1. 仍在「用户管理」页面，打开这位员工的详情。
2. 找到「插件使用」区域，找到名为 `tasks` 的一项。
3. 点「开通插件使用」。
4. 确认这一项显示「已分配角色」「插件使用已开通」「当前实际可用」。

人多时可以批量：在用户列表里勾选多位员工，在「批量操作」里选命名空间 `tasks`，点「批量开通插件使用」。

API（自动化用）。请求体只有一个布尔字段 `enabled`：

```bash
curl -s -X PATCH "$BASE/api/admin/users/$USER_ID/namespaces/tasks/admission" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"enabled":true}'
```

批量版本：

```bash
curl -s -X POST "$BASE/api/admin/users/namespaces/tasks/admission/bulk" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"userIds":["<id1>","<id2>"],"enabled":true}'
```

核对结果：回到这位员工的详情，「插件使用」区域里 `tasks` 一项显示「当前实际可用」，就表示这个人已经可以用任务。

## 完成后怎么验收

1. 让一位普通员工刷新页面或重新登录。顶部应出现「任务」入口（以界面为准，待验收时核对）。
2. 这位员工能打开任务页，能创建任务。
3. 在记录里给另一位已开通的员工派发任务，不再提示「有负责人还不能使用任务功能」；在任务页或任务详情里把他加为负责人，不再提示「对方还不能使用任务功能」（以界面为准，待验收时核对）。

## 常见问题

**派发时提示「有负责人还不能使用任务功能」，或在任务页、任务详情里加负责人时提示「对方还不能使用任务功能」，怎么办？**
说明被派发的这个人，步骤 2 到 4 没有做完整。
请检查两件事：他是否已被分配「任务成员」角色（步骤 3）；他的「tasks」是否已开通（步骤 4）。
如果提示的是「任务功能未开启」，说明步骤 1 没有生效。
做完后，重新派发即可。

**提示「有负责人不是当前组织的有效成员」或「该用户不在当前组织或已停用」，怎么办？**
说明这个人的账号没有启用，或者不是当前组织的成员。这一项在检查任务使用之前判断，和步骤 1 到 4 无关。
请在「用户管理」里打开这位员工的详情，先确认账号已启用（如果开启了目录待激活功能，还要求账号已完成激活），再看「所属组织」（以界面为准，待验收时核对）：
- 没有归属任何组织：详情里有「加入默认组织」。它只会加入默认组织，所以只在当前组织就是默认组织时有用。加入组织可能带来考勤名册等影响，请先看界面上的说明。
- 属于别的组织：这个页面上不能改，请通过目录管理把他加入当前组织。

**员工看不到顶部的「任务」入口。**
先确认步骤 1 的接口校验返回 200。
再确认这位员工的「tasks」显示「当前实际可用」。
然后让他刷新页面或重新登录。

**新建用户时已经在用户表单里选了「任务成员」角色，为什么还是提示不能使用任务？**
在用户表单里选角色，不会同时开通「任务」使用。请对这位用户再做一次步骤 4。
另外，不要在用户表单里把两个任务权限作为「直接权限」勾给用户；请通过步骤 2 的角色授予。

**某位员工的「任务成员」角色被移除过，后来又重新分配了，为什么还是不能用？**
移除角色时，这位员工的「任务」使用会被关闭；重新分配角色不会自动重新开通。
请对这位员工再做一次步骤 4。

**管理员需要做步骤 2 到 4 吗？**
不需要。平台管理员始终可以使用任务。

**某个员工以后不再使用任务。**
在「插件使用」里点「关闭插件使用」即可。对应的 API 是把 `enabled` 设为 `false`。
