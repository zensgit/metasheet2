# 任务功能开通指引（on-prem 管理员）

适用对象：负责 on-prem 部署的管理员。
目标：让普通员工能打开「任务」，能创建任务，也能被派发任务。

任务功能默认关闭。要开通，需要按顺序做四件事。
步骤 1 和 2 是一次性的。步骤 3 和 4 对每个要使用任务的人都要做。

前提：要使用任务的员工，账号必须已启用，并且是当前组织的成员（用户详情里「所属组织」包含当前组织）。不满足时，派发会提示这个人不是当前组织的有效成员，见文末常见问题。

| 步骤 | 做什么 | 谁来做 |
| --- | --- | --- |
| 1 | 打开后端开关并重启 | 部署管理员（服务器上操作） |
| 2 | 建一个带两个任务权限的角色 | 平台管理员 |
| 3 | 把角色分配给员工 | 平台管理员 |
| 4 | 为每位员工开通「任务」使用 | 平台管理员 |

平台管理员始终可以使用任务，不需要做步骤 2 到 4；但他的账号同样要是当前组织的成员，否则不能创建任务。

本指引只开通任务本身。任务提醒、每日汇总和钉钉工作通知另有开关（`TASKS_SCHEDULER_ENABLED` 等），默认关闭，怎么打开不在本指引范围内；打开后谁会收到通知，见下文「任务通知」。
下面所有「管理员」操作，都要用平台管理员账号登录。

## API 命令里用到的变量

文中的 API 命令（自动化用）都用下面几个变量。先在终端里设好：

```bash
BASE=http://127.0.0.1                 # 访问地址，末尾不要带 /api
ADMIN_TOKEN='<平台管理员账号的令牌>'
TOKEN='<任意已登录账号的令牌>'
USER_ID='<要操作的员工的用户 ID>'
```

- 安装文档里的 `API_BASE` 写的是 `http://127.0.0.1/api`，以 `/api` 结尾。这里的 `BASE` 要去掉末尾的 `/api`，否则地址会变成 `/api/api/...`：登录那一步会返回 401（提示缺少令牌），带令牌的请求会返回 404。
- 如果你不是在服务器本机上操作，把 `127.0.0.1` 换成你实际的访问地址。
- 令牌用登录接口取得，返回里 `data.token` 的值就是令牌：

```bash
curl -s -X POST "$BASE/api/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"email":"<登录邮箱>","password":"<密码>"}'
```

## 步骤 1：打开后端开关并重启

在界面上没有这个开关。它是后端的环境变量。

顺序很重要：先把部署或升级包的步骤全部做完，再把这个开关作为单独的一步写进 `app.env`，然后重启后端。
以后每次升级也一样：升级完成后，确认这一行还在、写法不变，再重启。

1. 打开部署目录下的 `docker/app.env`。
2. 加入一行，写法必须完全一致：

   ```env
   TASKS_ENABLED=true
   ```

   - 只认小写 `true`。写成 `TRUE` 或 `1` 都不会生效。
   - 等号两边不要加空格。
   - 同一个键只写一次。文件里已经有这一行时，原地修改，不要在末尾再加一行：不同的启动方式对重复的行取值不同。
3. 重启后端，让新值生效。

用 PM2 的部署（默认）：先把 `app.env` 读进当前终端，再带 `--update-env` 重启。
只改文件、直接 `pm2 restart`，新值不会生效。

```bash
cd /opt/metasheet
set -a; source docker/app.env; set +a
pm2 restart metasheet-backend --update-env
pm2 save
```

用 systemd 的部署：`systemctl restart metasheet-backend.service`。
直接用代码仓库里的 Docker Compose 文件部署的环境（on-prem 包里没有 Compose 文件）：重建后端容器，例如 `docker compose -f docker-compose.app.yml up -d backend`。
Windows 无 Docker 部署（适用于在 Windows 上不用 Docker 安装的 on-prem 包，两条包线都带同一个启动脚本）（待在 Windows 主机上核对）：在部署目录下打开 PowerShell，运行 on-prem 包里自带的启动脚本。它会先读入 `app.env`，再带 `--update-env` 重启后端，最后执行 `pm2 save`。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\ops\attendance-onprem-start-pm2.ps1
```

- 在 PowerShell 里直接运行 `pm2 restart metasheet-backend --update-env`，不会读入 `app.env`，新值不会生效。
- 这个脚本先找部署目录下的 `app.env`，找不到才用 `docker\app.env`。如果两个文件都有，脚本只读部署目录下的那个，请在两个文件里都加上这一行。
- PM2 里已有的进程定义和当前部署目录对不上时，脚本会删掉它，按 `ecosystem.config.cjs` 重新创建。
- 如果这台机器的后端是由计划任务启动的（pm2-runtime），先在这台主机上确认这个脚本适用再运行：在 PM2 后台进程已经退出时运行 pm2 命令，可能另起一个只属于当前会话的 PM2 后台进程。

如果你的服务名或目录不同，以你实际的部署为准。

开通后，已登录的员工刷新页面或重新登录，顶部才会出现「任务」入口。

API 校验（自动化用）：用任意已登录账号请求当前用户接口。判断开关是否生效，以这个接口为准。
返回里 `data.features.tasks` 为 `true`，表示后端开关已生效；为 `false` 表示开关没有生效。
这一项只说明开关，不说明某个人能不能使用任务。每个人能不能用，看步骤 4 的核对结果。

```bash
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/api/auth/me"
```

还可以请求任务接口，确认某个账号能使用任务：
- 返回 200：开关已生效，这个账号能打开任务。能不能创建任务、能不能被派发，以步骤 4 的「核对结果」为准。
- 返回 403：开关已生效，但这个账号还不能打开任务。请检查步骤 2 到 4。如果这个账号还在用临时密码，改密码之前也会返回 403。
- 返回 404：不能只凭这一项判断开关没有生效。后端版本不支持任务、请求地址写错、代理没有转发这个地址，也会返回 404。请以当前用户接口里的 `data.features.tasks` 为准。

（平台管理员账号始终能使用任务；员工账号要做完步骤 2 到 4 才会返回 200。）

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $TOKEN" \
  "$BASE/api/tasks/context"
```

## 步骤 2：创建「任务成员」角色

角色需要包含两个任务权限：

| 权限码 | 界面里显示的名称 | 作用 |
| --- | --- | --- |
| `tasks:read` | 任务读取 | 看到「任务」入口，查看任务 |
| `tasks:write` | 任务写入 | 创建、修改任务，派发任务 |

不要勾选「任务管理」（`tasks:admin`）。目前没有任务功能用到它，普通员工不需要。

在产品里操作（以界面为准，待验收时核对）：

1. 进入「角色管理」页面（地址 `/admin/roles`）。
2. 点「新建角色」。
3. 「角色 ID」填 `tasks_member`。「角色名称」填 `任务成员`。
4. 在「权限映射」里勾选「任务读取」和「任务写入」。
5. 点「创建角色」。

API（自动化用）：

```bash
curl -s -X POST "$BASE/api/roles" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"id":"tasks_member","name":"任务成员","permissions":["tasks:read","tasks:write"]}'
```

## 步骤 3：把角色分配给员工

在产品里操作（以界面为准，待验收时核对）：

1. 进入「用户管理」页面（地址 `/admin/users`）。
2. 在用户列表里点中这位员工，打开详情。
3. 找到「角色操作」，在下拉框里选「任务成员 (tasks_member)」。
4. 点「分配角色」。

注意：不要用用户列表「批量操作」里的「修改角色」→「应用角色」来做这一步（确认框写的是「确认把所选用户的角色改为 …？」）。
它不是给员工加一个角色，而是把所选员工原有的角色全部换成这一个：其他角色会被移除，和被移除角色相关的插件使用（例如考勤）也会被关闭；所选员工里如果有平台管理员，也会失去管理员身份。
用「导出以便修改」「导入更新」改角色，效果也一样。

API（自动化用）：

```bash
curl -s -X POST "$BASE/api/admin/users/$USER_ID/roles/assign" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"roleId":"tasks_member"}'
```

人多时，用这个接口逐个分配。它只增加角色，不动员工已有的其他角色：

```bash
for USER_ID in <id1> <id2> <id3>; do
  curl -s -X POST "$BASE/api/admin/users/$USER_ID/roles/assign" \
    -H "Authorization: Bearer $ADMIN_TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"roleId":"tasks_member"}'
  echo
done
```

## 步骤 4：为员工开通「任务」使用

只分配角色还不够。每位员工还要单独开通「任务」使用。
必须先做完步骤 3，员工详情里才会出现「tasks」这一项。

在产品里操作（以界面为准，待验收时核对）：

1. 仍在「用户管理」页面，打开这位员工的详情。
2. 找到「插件使用」区域，找到名为 `tasks` 的一项。
3. 点「开通插件使用」。
4. 确认这一项显示「已分配角色」「插件使用已开通」「当前实际可用」。

人多时可以批量：在用户列表里勾选多位员工，在「批量操作」里选命名空间 `tasks`，点「批量开通插件使用」。

API（自动化用）。请求体只有一个布尔字段 `enabled`：

```bash
curl -s -X PATCH "$BASE/api/admin/users/$USER_ID/namespaces/tasks/admission" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"enabled":true}'
```

批量版本：

```bash
curl -s -X POST "$BASE/api/admin/users/namespaces/tasks/admission/bulk" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"userIds":["<id1>","<id2>"],"enabled":true}'
```

核对结果：先刷新浏览器页面（开通后，详情里的「权限」区域不会自动更新），再打开这位员工的详情，确认两项：
- 「插件使用」区域里 `tasks` 一项显示「当前实际可用」；
- 「权限」区域里同时列出 `tasks:read` 和 `tasks:write`。

两项都满足，这个人才能使用任务，也能被派发任务。
只看到「当前实际可用」还不够。
如果「权限」里缺其中一个，进入「角色管理」，在「角色目录」里点「任务成员」，在「权限映射」里确认「任务读取」和「任务写入」都已勾选，点「保存角色」。然后再刷新页面，打开这位员工的详情核对。

## 完成后怎么验收

1. 让一位普通员工刷新页面或重新登录。顶部应出现「任务」入口（以界面为准，待验收时核对）。
2. 这位员工能打开任务页，能创建任务。
3. 在记录里用「派发任务」给另一位已开通的员工派发任务，不再提示「有负责人还不能使用任务功能」；在任务详情里用「添加负责人」把他加为负责人，不再提示「对方还不能使用任务功能」（以界面为准，待验收时核对）。任务列表页上新建任务时不能指定负责人，所以不在那里验收这一项。
4. 被派发任务的那位员工打开顶部的「待办中心」，能在「任务」分组下看到分配给他、还没完成的任务（以界面为准，待验收时核对）。待办中心只要求能使用任务；没有审批权限的员工也能打开它，只看到任务。

## 任务通知

任务通知（钉钉工作通知）默认关闭。下面三个开关要同时设为 `true`（写法要求和步骤 1 一样），当前组织还要已接入钉钉，才会发送通知。任何一个没打开，都不发送任何任务通知，包括到期提醒和每日汇总。

```env
TASKS_SCHEDULER_ENABLED=true
TASKS_NOTIFICATION_DELIVERY_WORKER_ENABLED=true
TASKS_NOTIFICATION_DINGTALK_WORK_NOTIFICATION_ENABLED=true
```

打开后，谁会收到哪种通知：
- 从记录派发任务：发给每一位负责人，不发给派发人自己。关注人和清单成员收不到这一条。
- 在任务详情里添加负责人：只发给被添加的这一位，不发给其他负责人。
- 任务被完成、重新打开、删除或有新评论：发给任务的创建人、负责人、关注人和任务所在清单的成员，不发给做这个操作的人自己。

发送前还会再检查一次，不满足就不发：
- 收件人仍是当前组织的有效成员，并且仍能查看这项任务；
- 前两种（派发、添加负责人）还要求收件人在发送时仍是这项任务的负责人；
- 上面这几种通知生成后 24 小时内还没发出的，不再发送。

查看最近 24 小时的发送情况（只读查询）：

```sql
SELECT status, last_error, count(*) AS n
  FROM task_notification_deliveries
 WHERE created_at > now() - interval '24 hours'
 GROUP BY status, last_error
 ORDER BY status, last_error;
```

`status` 为 `sent` 表示已发出，`skipped` 表示没有发（例如没通过上面的检查），`failed` 表示发送失败且不会再发。

## 升级与回退（带「从记录派发任务」来源关联的版本）

这个版本新增一条迁移 `zzzz20261104150000_create_task_source_links`，在库里新建表 `task_source_links`，记下每项从记录派发的任务来自哪条记录，以及防止重复派发的记录。

### 升级

1. 网页和后端用同一个安装包一起升级时，没有先后。
2. 网页和后端分开部署时，先升级后端（迁移步骤保持开启），再升级网页。反过来的话，在两者版本不一致的这段时间里，从记录派发的任务不会记下来源记录，以后也补不上；派发后重试还可能多建一项任务。
3. 新版本的后端必须在已经跑过这条迁移的库上启动。升级到新版本时不要关闭迁移步骤；迁移步骤失败时，不要直接重启后端。否则任务详情、从记录派发任务、记录上的任务列表都会报错。

### 回退

1. 只回退程序，不回退迁移。用上一个安装包重新部署，并关闭迁移步骤：Windows 升级脚本加 `-RunMigrations 0`，Linux 升级脚本设 `RUN_MIGRATIONS=0`。表 `task_source_links` 和它的迁移记录都留在库里；旧版本不读这张表，可以直接在升级过的库上运行。
   - 不关闭迁移步骤时，旧安装包的迁移步骤会失败，提示 `corrupted migrations: previously executed migration … is missing`。这是旧安装包不认识新版本加的迁移，不是库坏了；关闭迁移步骤后重新部署即可（升级脚本随后怎么处理，以脚本的输出为准）。
2. 网页和后端分开部署时，先回退网页，再回退后端（和升级的顺序相反）。用同一个安装包一起回退时，没有先后。
3. 不要在共享的库上（测试环境、演示环境、正式环境）执行这条迁移的回退（`--rollback`）。表里有数据时，这条迁移的回退会拒绝执行，提示 `TASK_SOURCE_LINKS_DOWN_BLOCKED`，库里什么都不改。不要为了让回退通过而手工清空这张表：清掉的是所有从记录派发的任务的来源和防重复记录，不能恢复。
4. 只有一次性的测试库可以回退这条迁移，并且要在新安装包上执行（旧安装包没有这条迁移，做不了）。执行前：
   - 先确认它是最后执行的一条迁移。下面查询的结果必须是 `zzzz20261104150000_create_task_source_links`；不是的话不要用 `--rollback`，它回退的是最后执行的那一条，不一定是这一条。

     ```sql
     SELECT name FROM kysely_migration ORDER BY timestamp DESC, name DESC LIMIT 1;
     ```

   - 表里有数据时，先手工清空这张表，再执行回退。
   - 不要只手工删表而留着迁移记录：新版本会认为迁移已经做过，表却不在，任务详情会报错。表和迁移记录要么一起删，要么都留着。
5. 回退后再升级回新版本：这条迁移不会重跑，表和数据原样可用。回退前派发的任务，在旧版本上看不到来源，升级回来后重新显示。回退期间在旧版本上派发的任务，来源写在任务描述里，升级后不会出现在记录的任务列表里。
6. 通知（只在打开过「任务通知」的三个开关时相关）：新版本生成、回退时还没发出的「派发任务」和「添加负责人」通知——
   - 回退期间通知开关开着：旧版本会把它们标为发送失败（`failed`，原因 `payload_invalid`），不会补发，之后再升级也不会补发。
   - 回退期间通知开关关着：它们留着待发；升级回新版本后，生成不到 24 小时的会发出，超过 24 小时的不再发送。

   统计被旧版本标为失败的这类通知（只读查询）。这些是被旧版本结束的通知，不是数据损坏：

   ```sql
   SELECT count(*) AS n
     FROM task_notification_deliveries
    WHERE status = 'failed'
      AND last_error = 'payload_invalid'
      AND source_type = 'task_event'
      AND payload->>'event' IN ('created', 'assignee_added');
   ```

## 常见问题

**派发时提示「有负责人还不能使用任务功能」，或在任务详情里加负责人时提示「对方还不能使用任务功能」，怎么办？**
说明至少有一位负责人还不能使用任务：对他来说，步骤 2 到 4 没有做完整。
派发时的提示不会说是哪一位。派发给多人时，请逐个检查这些负责人，或者减少负责人、分批派发，找出是哪一位。在任务详情里加负责人时，提示说的就是正在添加的这一位。
对每位要检查的人，看三件事：
- 是否已被分配「任务成员」角色（步骤 3）；
- 「tasks」是否已开通（步骤 4）；
- 刷新页面后打开他的详情，「权限」里是否同时列出 `tasks:read` 和 `tasks:write`。缺其中一个时，按步骤 4「核对结果」里的说法修改「任务成员」角色。
如果提示的是「任务功能未开启」，说明步骤 1 没有生效。
做完后，重新派发即可。

**提示「有负责人不是当前组织的有效成员」或「该用户不在当前组织或已停用」，怎么办？**
说明这个人的账号没有启用，或者不是当前组织的成员。这一项在检查任务使用之前判断，和步骤 1 到 4 无关。
请在「用户管理」里打开这位员工的详情，先确认账号已启用（如果开启了目录待激活功能，还要求账号已完成激活），再看「所属组织」（以界面为准，待验收时核对）：
- 没有归属任何组织：详情里有「加入默认组织」。它只会加入默认组织，所以只在当前组织就是默认组织时有用。加入组织可能带来考勤名册等影响，请先看界面上的说明。
- 属于别的组织：这个页面上不能改，请通过目录管理把他加入当前组织。

账号被移入回收站，也会得到这个提示。移入回收站的账号不会出现在「成员」列表里。
在「成员」里找不到这个人时，先核对填写的用户 ID；再看同一页的「回收站」：
- 在「回收站」里找到了：如果是误删，可以点「恢复」。恢复后账号回到移入前的启用状态，原有角色和「tasks」开通都还在，再重新派发即可。已离职或有意删除的人，请改派给别人，不要为了派发去恢复。
- 两处都没有：说明用户 ID 写错了，或者账号已被清除。已清除的账号不能恢复，只能新建账号，再重新加入组织并做步骤 3、4。

**员工看不到顶部的「任务」入口。**
先确认步骤 1 的当前用户接口返回里 `data.features.tasks` 为 `true`。
再确认这位员工的「tasks」显示「当前实际可用」，并且刷新页面后打开他的详情，「权限」里同时列出 `tasks:read` 和 `tasks:write`。
然后让他刷新页面或重新登录。

**刚给员工开通完，他的「任务」入口过了一会儿才出现。**
后端有多个进程时（默认的 on-prem 部署只有一个），开通后最长约一分钟内，当前用户接口 `/api/auth/me` 返回的权限可能还是旧的，所以页面上的「任务」入口会晚一点出现；「用户管理」详情里的「权限」也可能晚一点更新。
任务接口本身是立即生效的。等一分钟左右再刷新页面即可。

**新建用户时已经在用户表单里选了「任务成员」角色，为什么还是提示不能使用任务？**
在用户表单里选角色，不会同时开通「任务」使用。请对这位用户再做一次步骤 4。
另外，请不要直接给用户单独授予这两个任务权限；请通过步骤 2 的角色授予。

**某位员工的「任务成员」角色被移除过，后来又重新分配了，为什么还是不能用？**
移除角色时，这位员工的「任务」使用会被关闭；重新分配角色不会自动重新开通。
请对这位员工再做一次步骤 4。

**管理员需要做步骤 2 到 4 吗？**
不需要。平台管理员始终可以使用任务，只要他的账号是当前组织的成员。

**某个员工以后不再使用任务。**
在「插件使用」里点「关闭插件使用」即可。对应的 API 是把 `enabled` 设为 `false`。
