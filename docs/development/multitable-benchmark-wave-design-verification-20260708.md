**类型**：验证记录（非设计锁）。本文记录一次无人值守开发波次中已发生的事实与已验证的结论，不主张任何未经 ratify 的设计。

---

## 1. 范围

owner 设定的总目标：以多维表对标线的**余下开发**为总目标池，规划、排序、可并行地推进，并在完成后给出设计与验证 MD。本波在无人值守下完成一次完整的「审计 → 排序 → 起草 → 实现 → 对抗门禁 → 落地 / 开 PR」循环，本文即该波的验证记录。

本文只覆盖设计与实现类交付物。任何触及权限 / 中央授权语义的事项按项目红线由 owner 独占处置，通过独立渠道跟踪，不在本文展开——这既是纪律，也因本仓公开。

## 2. 目标池的形状（本波最重要的结论）

10 个能力面并行审计真实代码，得 **120 个缺口**。分档：`需要新设计 72 · 待批阻塞 14 · 待 owner 输入 11 · 可自动 14 · 权限锁定 9`。严格去重后：**36 个缺口里只有约 1 个是真正「现在就能自动做」的实现**（≈3%）。

**36 个缺口塌缩成约 7 个簇，卡在约 6 个 owner 决定：**

| 簇 | 内容 | 卡点 |
|---|---|---|
| A 视图渲染集 | 非网格视图物化 · 客户端分组 · 分组无限滚动 · 画廊分组 | 一个数据模型决定 |
| B 排序基座 | 手动行序 · 看板列内序 · 仪表盘拖拽布局 | 一个 fractional-index 决定 |
| C 公式求值器 | formula→formula · 数组 / 对象操作数 · 关系式组合 · 缺失函数 | 一个 RFC 重开决定 |
| D AI 阶梯 | 若干待批锁 + 点亮 | 批复 + 环境值 |
| E 权限 / 出口边界 | （owner 独占） | 红线；且是 F 簇的 GA 闸 |
| F 协同 GA 基建 | 广播 / 适配器 / 失效传播 | 价值全押在 E |
| G 字段元数据 | 选项稳定 ID（keystone）→ 类型转换 · 调色板 | 一个决定 |

**结构性事实：owner 是双重瓶颈** —— 既是 ratify-in（设计锁批复），也是 merge-out（行为 / 运行时 PR 只能由 owner 合并）。因此无人值守跑动的产出上限**不是功能落地数，而是「待批 PR 的深度」**。这决定了本波策略：**起草道封顶 2 项**（第 3 项之后为负吞吐——它加深瓶颈而非缓解），余力投向**能自证的实现切片**与**对抗性验证**。

⚠️ **完整性声明（此池是下限，非全集）**：协同面审计输出在第 5 个缺口处截断，另有一个能力面审计未完整返回。不得把「120」当作穷尽计数。

## 4. 方法学产出：三次「前提被证伪」

本波交给每个子代理的前提都要求**先证伪再动手**。三次全部命中，这是本波价值密度所在。

### 4.1 一个自称守卫的 fixture ——以及一个比 mutation 更强的检测法

公式目录切片最初附带的「对齐守卫」把引擎函数名**手抄**进测试，再断言 `目录 ⊆ 手抄表`。对抗门禁两路证明它是死的：

- **结构性证明**（无需运行）：该测试与引擎之间**没有 import 边**。因此引擎的任何改动都**永远不可能**让它变红。
- **A/B mutation**：删掉引擎里的某个函数注册 → 该守卫**绿**；对照探针守卫 → 红。

> **可复用判据：若一个测试与它声称守护的对象之间没有活引用（import 边或运行时读取），它就是 fixture 而非守卫。读 import 列表即可判定，不必运行。**

作者给出的「不可能实现真守卫」的理由（跨包 import 会在导入期拉起数据库连接池）经实证为**属实但无害**——构造连接池对象并不打开套接字，且仓内已有多个后端测试直接 import 该引擎。**「模块 X 不可 import」通常只是「按我最先尝试的方向不可 import」**：守卫本该长在**后端侧**（可直接 import 引擎、文件读取前端目录）。

修复本身携带同类风险：新守卫用文件读取 + 正则抓取名字，若路径断裂或格式变动，**正则匹配 0 个名字 → 差集为空 → 静默转绿**。因此新守卫**必须断言自己的抓取产物合理**（非空、数量下界、已知锚点名存在），并以「弄坏抓取」的 mutation 证明它变红而非变绿。本波五道 mutation（M-A..M-E）全部证红。

### 4.2 「五个非网格视图都静默截断」——两头都说错了

- **画廊视图是假阳性**：它的截断**有披露、可导航**（翻页器），且不计算任何跨行值。从缺陷集剔除。
- **「静默」被收紧成「比静默更糟」**：工具栏与视图链**平级**，对每种视图都渲染全表行数。于是同屏出现两个互相反驳的数字，而没有任何控件能调和它们。
- **「五个视图行为一致」为假**，且它们的修法**互不相容**（各自需要不同的数据形状）。此叉口被明确命名并交给各自闸门后的切片，而非糊成一个「通用分页」。
- **严重性升级**：其中一个视图会把**已经载入内存的行永不渲染**，并把由分页制造出来的孤儿计数当作事实展示；另两个视图的**坐标系本身是截断的函数**（坐标轴外延是「页」的属性而非「数据」的属性）。这类「从被截断的集合算出错误的外延 / 聚合」远重于「少渲染几行」。

### 4.3 「服务端分组小计是错的」——值是对的，骨架是错的

服务端**早已**按过滤全集发出真实的每组计数，客户端两处 wire type **都已声明该字段**，然后把它丢弃。审计声称小计**值**有误——不成立：值由服务端按过滤全集算出并正确解析。坏掉的是分组**骨架**（存在性 / 计数 / 顺序 / 边界）。锁里明文禁止声称前者。

并且「直接读那个字段」也不成立：该分组树只是页脚聚合配置的**副产品**（未配置聚合时提前返回），且相关端点在大数据量上**硬失败**。更深的张力在于：该路径**故意**先全载再在内存中过滤，因为部分条件没有 SQL 形式——所以「真计数 + 无 N+1 + 分组感知游标」**不可能**统一成单条 SQL。锁选择照搬仓内既有的分叉先例，并要求游标**显式降级**。

## 5. 一次设计向平台约束的让步

#3931 记录了一条继承而来的设计不变量（其 INV-3）：某个分页元数据的语义先于其展示环节被确定，因此其披露切片被约束为**渲染布尔「我是否被截断」+ 一个动作，而非精确的「N / M」**，并以仓库级 grep 断言强制，且明文禁止任何切片「顺路把它改掉」（那属于中央权限领域，需 owner 单独处置）。

这是一次**设计承认约束、而非绕过约束**的实例：某个直觉上更好的产品行为在当前平台模型下不可安全实现，于是设计让步并把约束固化为不变量，交由 owner 处置根因。
