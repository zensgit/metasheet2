# Multitable AI-shortcut prompt-config history rendering — S2 DESIGN LOCK (PROPOSED)

- **Status**: PROPOSED — awaiting owner ratification. Docs-only PR; no runtime code ships here.
- **Slice**: S2 of the AI-fields governance arc (S1 provenance/grouping foundation [merged] → 🔒 S1b true history-batch rollback → **S2 prompt-as-audited-config UI (this lock)** → S3 staleness lineage → S4 cost visibility → S5 cleaning-oriented kinds).
- **What S2 is NOT**: S2 adds no recording, no new storage, no new route, and no revert/restore behavior. The backend already appends every `aiShortcut` config change to `meta_config_revisions` (`config-revision-recorder.ts`) inside the same transaction as the field mutation — that plumbing is untouched. S2 is a **read-side rendering slice only**: make the ALREADY-RECORDED diff legible where it is ALREADY displayed, in the ALREADY-EXISTING config-history modal. See §4 for the full list of things this lock deliberately does not touch.
- **Change surface when implemented** (single runtime PR after ratification): `apps/web/src/multitable/components/MetaConfigHistoryModal.vue` only (a new render branch for `field` + `property` rows whose diff contains an `aiShortcut` key), plus its render-test spec `apps/web/tests/multitable-config-history-modal.spec.ts`. **No backend changes, no new tables, no migrations, no new env flags, no restore-surface change, no new redaction module.**

## §1 Problem (verified at line level)

1. **The recording side already works.** `recordConfigRevision` / `fieldUpdateDiff` (`config-revision-recorder.ts:89-146`) treat a field's `property` key as ONE atomic value in `FIELD_CONFIG_KEYS = ['name', 'type', 'property', 'order']` (`config-revision-recorder.ts:61`). A field-property PATCH that only touches `property.aiShortcut` (kind/sourceFieldIds/params) produces an `update` diff with `changedKeys = ['property']` and `before.property` / `after.property` holding the **entire property object** (whatever else lives alongside `aiShortcut`), not a sub-diff scoped to the `aiShortcut` key itself. This is correct and sufficient for storage (D2: diff-first, changed-keys-only) — the gap is entirely on render.
2. **The render side already exists, but degrades exactly where prompt config lives.** `MetaConfigHistoryModal.vue` (verified: wired into `MultitableWorkbench.vue:536-548` via `configHistory`/`configHistoryLabelOf`/`configRestorePreview`/`configRestoreExecute`, a DIFFERENT component from `HistoryCenterModal.vue` which is RECORD history — S1's `ai-shortcut` source label lives in `HistoryCenterModal.vue:133`, a separate concern; confirmed these are two distinct Vue files with two distinct backend read routes, `/config-history` (T9-R3, `univer-meta.ts:8013`) vs the record-history route S1 touched) already renders EVERY entity type generically via `summarizeConfigValue` (`MetaConfigHistoryModal.vue:134-150`): objects become `k: v` pairs one level deep, primitive arrays join with `; `, and **anything nested two levels deep falls back to `JSON.stringify`**.
   - For an `aiShortcut` property diff, `display(rev.after?.property)` calls `summarizeConfigValue(propertyObj, 0)` → at depth 1 the `aiShortcut` object's own entries (`kind`, `sourceFieldIds`, `params`) get formatted → but `params` (the object holding `targetLang`/`instruction`/`options`) is reached at depth 2, which hits the `depth >= 2` branch and is dumped as a **raw JSON blob**, e.g. `params: {"instruction":"Flag anything mentioning a competitor by name","targetLang":"French"}`.
   - This is legible-ish for `kind`/`sourceFieldIds` but NOT for `params` — the single most human-relevant part of a prompt-config change (the actual instruction text an editor wrote) renders as an unformatted JSON fragment rather than a labeled, readable field. It also mixes ANY other `property` sub-key that happened to change in the same PATCH into the same blob (not scoped to `aiShortcut` at all).
   - Confirmed via `apps/web/tests/multitable-config-history-modal.spec.ts`: no existing test exercises a `property`/`aiShortcut` diff — the render gap is untested as well as unaddressed.
3. **Redaction has never been considered for this surface.** `summarizeConfigValue`'s own comment (`MetaConfigHistoryModal.vue:130-133`) asserts "these are CONFIG values (never record data), so no value-masking is needed" — true for structural config (kind enums, field-id arrays, view filters) but not examined against a FREE-TEXT field (`params.instruction`, up to 500 chars, `ai-shortcut-config.ts:43`) that a human author can type anything into, including an accidentally pasted secret. §3 makes this call explicitly instead of leaving the blanket comment to stand unexamined.

## §2 LOCK-A — what gets rendered

- **A1**: `MetaConfigHistoryModal.vue` gains a render branch scoped EXACTLY to: `rev.entityType === 'field'`, `rev.action === 'update'` (or `'create'`/`'delete'` — a create/delete also carries the whole `property` object in `after`/`before` respectively), `rev.changedKeys.includes('property')` (update) or `action !== 'update'` (create/delete), AND the relevant side's `property` object has an `aiShortcut` key present (in `before` for delete, `after` for create, either/both for update). Everything else keeps rendering through the EXISTING generic `summarizeConfigValue` path — **no other `changedKeys` entry, no other entity type, is touched.**
- **A2**: within that branch, the `aiShortcut` sub-object renders as three labeled lines, not one blob:
  - `kind`: the enum value as-is (`summarize` / `classify` / `extract` / `translate`) — already a short human word, no further formatting needed.
  - `sourceFieldIds`: each id resolved to its field name via the SAME `recordLabelOf` callback the modal already receives as a prop (`configHistoryLabelOf` in the workbench, `MetaConfigHistoryModal.vue:109`) — falls back to the raw id string if the field was since deleted or renamed-away-from-cache, mirroring `configHistoryLabelOf`'s own existing `?? entityId` fallback (`MultitableWorkbench.vue:907`). No new resolution mechanism.
  - `params`: rendered key-by-key (`options` joined `; `, `targetLang` as-is, `instruction` as-is) instead of falling through to `JSON.stringify` — each value passed through the redaction call in §3 first.
  - For `update`, each of the three lines above is shown before→after (only for keys that actually changed — comparing `before.aiShortcut` vs `after.aiShortcut` client-side per sub-key is display-only and does not change what was stored); for `create`/`delete`, only the single relevant side is shown (no arrow).
- **A3**: if a `property` diff has NO `aiShortcut` key on either side (an ordinary property tweak — e.g. a select field's option list), rendering is BYTE-IDENTICAL to today's `summarizeConfigValue` path. This lock changes rendering for aiShortcut-bearing diffs only.
- **A4**: this is a pure additional render branch in an existing component — no new modal, no new route, no new prop. `MetaConfigHistoryModal.vue`'s existing props (`items`, `recordLabelOf`, `isZh`, `previewRevert`, `executeRevert`) are unchanged; the new branch is computed from `rev` alone (already in scope inside the `v-for`).

## §3 LOCK-B — redaction posture (explicit call)

**The call: `params.instruction` and `params.options` entries pass through the SAME redaction discipline this codebase already applies to automation log strings, reusing the EXISTING frontend redactor — not a new module.**

- **B1 (what exists)**: `apps/web/src/multitable/utils/automation-log-redact.ts` exports `redactString(value: unknown): string`, a dependency-free, DOM-safe regex redactor (Bearer tokens, JWTs, `sk-`-prefixed keys, DingTalk secrets, `KEY=value`-shaped env assignments, signed-URL query params, DB connection strings). It exists specifically so secret-shaped substrings never reach rendered DOM, and is already bundled in the browser build for the automation-log surface.
- **B2 (why prompt config is NOT the same trust tier as view/permission config, despite the existing blanket comment)**: `kind` and `sourceFieldIds` are STRUCTURAL — drawn from a closed enum and from the sheet's own field-id set (`ai-shortcut-config.ts:18,64`), authored through a picker UI, never free text. `params.instruction` is the ONE genuinely free-text value in this entire feature (up to 500 chars, `AI_SHORTCUT_MAX_INSTRUCTION_LENGTH`) — a human can type anything, including "use this API key for context: sk-...". That is qualitatively different from the config values `summarizeConfigValue`'s comment was written against (view filters, permission grants, field type enums), which cannot contain accidentally-pasted secrets because their shapes are closed. The blanket "config values never need masking" comment is right for those shapes and wrong for this one — S2 narrows it rather than overturning it wholesale.
- **B3 (why NOT "safe to show verbatim to an actor who already has permission")**: permission-to-view is not the deciding factor here — the risk isn't the viewer seeing THIS field's own config (they already can, and already could, by opening the field's edit panel directly, which is unredacted today and stays that way — this lock does not touch the live field-edit UI, only the HISTORY render). The risk is a secret pasted into an instruction by author A becoming DISCOVERABLE by anyone who can view field config history — a broader, more persistent audience than "whoever is editing the field right now" (history persists indefinitely; edit-panel exposure is transient and requires already knowing to look). Applying the existing redactor here is cheap defense-in-depth consistent with how this codebase already treats every other free-text surface that reaches a rendered log — it costs nothing for the overwhelmingly common case (an ordinary instruction like "flag anything mentioning a competitor by name" passes through `redactString` completely unchanged, since it matches none of the redactor's patterns).
- **B4 (scope discipline — what this does NOT do)**: this lock does **not** extend `redactString`'s pattern set, does **not** add a new redaction module, and does **not** touch `packages/core-backend/src/multitable/automation-log-redact.ts` (the backend twin) or the `/config-history` READ route — redaction happens client-side, display-only, on the `params.instruction`/`params.options` strings at render time, exactly where `automation-log-redact.ts` already runs for step output/error text. The stored `meta_config_revisions` row is untouched (unredacted at rest, as it is today for every other config value) — this is a render-time mask, not a persistence-time one, matching how `redactString` is used for automation logs today (redaction happens at record time there because that's a durable audit log across many viewers with varying trust; here it happens at render time because the value itself is already stored plainly and this is a display concern, not a new persistence decision).

## §4 Where this surfaces — and explicit non-goals

- **Surfaces in**: the EXISTING `MetaConfigHistoryModal.vue`, opened via the EXISTING "⚙ Config history" button (`MultitableWorkbench.vue:66`) already wired to `field` entity-type filtering. No new modal, no new button, no new navigation path. This follows the established pattern from §4's own verified fact: `view` and `sheet_config` config diffs already render through the same generic `summarizeConfigValue` path in the same modal with no entity-type-specific modal of their own (confirmed: `MetaConfigHistoryModal.vue` has exactly one rendering path per row, keyed only by `action`/`changedKeys`, not by a per-entity-type sub-component) — S2 adds one more entity-shape-aware branch to that same single path, it does not invent a new UI surface.
- **NON-GOAL 1 — no restore/revert of a prompt config in this slice.** This is not merely a scoping choice — it is ALREADY the system's own current behavior, verified: `classifyRevert` (`config-restore.ts:32-38`) gates any field `update` whose `changed_keys` aren't a subset of `SAFE_FIELD_KEYS`; `property` is not safe, so a `property`-only diff (which is exactly what an aiShortcut-only config change produces) is classified `gated` UNCONDITIONALLY. Even with `MULTITABLE_ENABLE_FIELD_RETYPE_REVERT=true`, `isSupportedFieldRetypeRevert` (`config-restore.ts:94-101`) requires `changed_keys.includes('type')` — "v1: type-changing reverts only (property-only deferred)" per its own comment — so a pure `aiShortcut` config change can NEVER reach the confirmable "safe" revert path today, flag on or off. S2 does not change any of this; it renders the diff more legibly, it does not make it revertible. (Distinct from S1b, which is about reverting RECORD-value batches, not config.)
- **NON-GOAL 2 — no new redaction module.** Per §3-B4: reuse `apps/web/src/multitable/utils/automation-log-redact.ts` as-is; do not fork, extend, or generalize it as part of this slice.
- **NON-GOAL 3 — no backend change.** The `/config-history` read route, its per-entity-type permission gate, and `meta_config_revisions`'s stored (unredacted) contents are all unchanged. S2 is FE-only.
- **NON-GOAL 4 — no change to non-aiShortcut config rendering.** Per A3, every other `changedKeys` value (`name`, `type`, `order`, non-aiShortcut `property` shapes, and every `view`/`permission`/`sheet_config` row) renders byte-identically to today.

## §5 Golden matrix (render-only; no runtime write behavior — extends `multitable-config-history-modal.spec.ts`)

| # | Scenario | Locked outcome |
| --- | --- | --- |
| G1 | field `create` with `property.aiShortcut` present in `after` | `kind`/`sourceFieldIds` (resolved to field names)/`params` render as separate labeled lines; no raw JSON blob for `params` |
| G2 | field `update` changing only `params.instruction` | before→after instruction text shown per-line; `kind`/`sourceFieldIds` unchanged, not repeated as a diff line (or shown identically before=after, per implementation choice — either is acceptable, but the raw-JSON fallback must not appear) |
| G3 | `params.instruction` containing a secret-shaped substring (e.g. an `sk-`-prefixed token or a `Bearer …` string) | the rendered DOM shows the REDACTED form (`redactString`'s output), never the raw secret substring |
| G4 | field `update` changing an ordinary, non-aiShortcut `property` sub-value (e.g. a select field's option list, no `aiShortcut` key on either side) | renders IDENTICALLY to pre-S2 behavior via the existing generic `summarizeConfigValue` path (regression guard — proves A3) |
| G5 | `sourceFieldIds` referencing a field id no longer resolvable (deleted/renamed out of the label cache) | falls back to the raw id string, same fallback behavior as `configHistoryLabelOf`'s existing `?? entityId` (regression guard — no new resolution mechanism, reuses the existing prop) |
| G6 | a field `update` revision whose `changedKeys = ['property']` (a pure aiShortcut change) | the revert button MAY render exactly as today — `canRevert` is deliberately presentation-only (`previewRevert && rev.action === 'update'`, `MetaConfigHistoryModal.vue:158`; its own comment: "the gate stays server-side; this only shows the server's preview") and S2 does NOT change it. The golden locks the CLICK path: opening revert-preview on a pure-aiShortcut property revision surfaces the server's GATED `classifyRevert` outcome fail-closed (no confirmable preview, no execute affordance, no restore-surface change) — confirms NON-GOAL 1 at the layer where the gate actually lives. Hiding the button pre-classify would be a separate FE-gating slice, explicitly OUT of this render-only lock |
| G7 | field `update` with BOTH an aiShortcut-bearing `property` change AND a `name` change in the same `changedKeys` | `property` renders via the new aiShortcut branch; `name` still renders via the existing generic before→after line — the two coexist without either branch swallowing the other's key |

## §6 Rollout

No new env flag. This is a pure FE render change behind the same permission gate the `/config-history` route already enforces (`canManageFields` for `entity_type = 'field'` rows) — nothing in this slice widens who can see a field's config history, it only changes how the already-visible payload is displayed. Implementation lands as one FE-only PR (component + spec) after ratification.
