# Strict login grant scope — local implementation contract

2026-11-18. This is the formal local contract for the strict login grant scope, receipt, grant rows, evidence detach, and exact-grant session revocation. It incorporates the closed design review, the correction closure, the formal administrator-proof contract, and the accepted container adapter. It permits the bounded local files named below. It does not enable production, mount a route, flip a flag, admit real customer data, or declare the bundle delivered.

`delivered`, `b2Complete`, `productionAvailable`, `containerAdapterProved`, `credentialChainEnabled`, `firstPopulationAdmitted`, `universalAbaClosed`, and `loginPropagationDecided` stay false. Codec `productionAvailable`, the six assurance gates, `DINGTALK_AUTH_REQUIRE_GRANT`, `DINGTALK_AUTH_AUTO_LINK_EMAIL`, `DINGTALK_AUTH_AUTO_PROVISION`, `DINGTALK_CONTAINER_LOGIN_ENABLED`, `DIRECTORY_DEPROVISION_ENABLED`, `DIRECTORY_DEPROVISION_CONNECTION_SCOPE_ENABLED`, and `DIRECTORY_DEPROVISION_REVOKE_CREDENTIALS_ENABLED` stay unset or not the exact literal `true`. Do not add `EXTERNAL_IDENTITY_LOGIN_ENABLED`. The global flag manifest records `EXTERNAL_LOGIN_STRICT_SESSION_MAX_AGE_SECONDS` and `DIRECTORY_DEPROVISION_REVOKE_CREDENTIALS_ENABLED` for operator inventory. The session lifetime has no default value and broad credential revocation defaults off.

## Ordinary session fence

Main's external issuer, not this store, acquires the user `SHARE`, then the exact resolved integration `SHARE`, re-reads installed scope on that same client, calls `createUserSession` on that same `PoolClient`, commits, and only then mints the token. A password-origin call does not become DingTalk because the user has a strict grant. A request body or header connection is a selector, not origin proof. A scope probe before transport, or an object-existence check alone, is not this fence. The strict branch never calls `createUserSession`. Lane A does not fall back to it.

`lockAuthoritativeDirectoryBindingAccount` already holds the directory account and the integration `FOR UPDATE`. Lane B keeps that order. A later `FOR SHARE` on the same client is compatible with the held `UPDATE`. Do not insert a weaker lock ahead of that `UPDATE`, and do not take a second directory or root discovery after session locks.

## Schema

One migration, `zzzz20261118120000_strict_login_grant_scope`, sorts after actor inputs `zzzz20261118090000` and proof sets `zzzz20261118100000`. `up` creates empty objects only: no backfill, no scope seed, no `VALIDATE`, no `CONCURRENTLY`. Indexes are only on the new empty grant table. `user_sessions` gains nullable `external_auth_context jsonb` and two `NOT VALID` checks. Old rows are not validated.

`directory_connection_login_scope` is insert-only. `connection_id` is the primary key and a `directory_integrations` foreign key `ON DELETE RESTRICT`. `command_id` is unique. The insert trigger sets `transitioned_at` to `clock_timestamp()`. Update, delete, and truncate raise `55000`. Grant creation does not write this row. There is no second global marker.

`admin_login_grant_command_receipts` is insert-only. `command_key` is the 64-hex primary key. `purpose` is `admin_login_grant_enable`. `outcome` is `enabled`. `proof_id` is unique and references `security_action_challenges` `ON DELETE RESTRICT`. `command_id` is stored and is not unique. `target_count` is at least 1 with no upper bound. `canonical_intent`, `intent_digest`, and `result` are stored. There is no `authority_witness` column and no 100-target or 256KiB check. Update, delete, and truncate raise `55000`.

`user_external_identity_login_grants` stores one historical row per target. Uniqueness is `(command_key, target_ordinal)` and `(command_key, local_user_id)`. `command_id` is copied and is not unique. `evidence_id` references evidence `ON DELETE RESTRICT`. `identity_id` is historical text with no user foreign key. `live_identity_id` is nullable and references `user_external_identities` `ON DELETE RESTRICT` while live. `local_user_id` has no user foreign key. `connection_id` references `directory_integrations` `ON DELETE RESTRICT`. `binding_revision` is `bigint` and `binding_revision_text` must equal `binding_revision::text`. `application_revision` and `access_generation_text` stay canonical decimal text with no upper bound and no cast of application text to `bigint`. `assurance` is `self_authenticated`. `grant_method` is `admin_explicit`. A partial unique index on `(live_identity_id, connection_id) WHERE revoked_at IS NULL` is the live slot. A disabled unrevoked row still occupies it.

The only grant updates are a disable that leaves `revoked_at` null, and one terminal transition from `revoked_at IS NULL` whether or not the row was already disabled. Terminal revoke sets `enabled` false, `revocation_generation` to exactly the old value plus one, `live_identity_id` null, and `revoked_at` to `clock_timestamp()`, with a closed reason and actor. Disable history is kept. A revoked row rejects every later update and delete. `local_user_id` is in the same NULL-safe immutable comparison, so a disable or terminal revoke cannot change the original user. The check does not infer `revoked_at IS NULL` from disable history. Closed reasons are `deprovision`, `admin_unbind`, `admin_disable`, `recycle_purge`, `privilege_elevation`, and `binding_replaced`. There is no `self_unbind`. `deprovision` requires `revoked_event_id` or `revoked_run_id`. Those foreign keys are `ON DELETE RESTRICT`. Reauthorization is a new id. This command inserts enabled rows only. The disabled-unrevoked state stays legal so a later accepted disable cannot block identity delete.

The grant insert trigger copies `subject_key`, `app_scope`, `material_fingerprint`, and `capability_revision_seen` from the evidence row already named by the consumed snapshot. That read does not take `FOR SHARE` or `FOR UPDATE`. It refuses a mismatch of witness, identity, binding, application revision, organization, or connection. The store does not call `resolveAdminGrantTargetSet` and does not run a second discovery read after session locks.

Deferred constraint triggers on receipt insert, grant insert, and `security_action_challenges` after `status` becomes `consumed` for `admin_login_grant_enable` call `strict_login_grant_assert_bundle`. At commit the function sees final rows. A consumed new-purpose proof must have exactly one matching receipt whose `consumed_action_ref` is `agc:` plus the command key, whose canonical intent and count match the seal, and whose grant set matches the proof children and the receipt `result` in ordinal, user, identity, binding, evidence, witness, access generation, privilege witness, application revision, and connection. Missing, extra, or mismatched rows, or a native consume with no receipt, fail the commit. The check does not require grants to stay enabled, a non-null live foreign key, unrevoked evidence, or current target state. Failed challenge parents and unrelated old purposes do not acquire the rule. This migration does not rewrite the proof migration. The seal row is declared `record`, not `admin_grant_proof_seals%ROWTYPE`. `up` can finish before the proof tables exist. The bundle `SELECT` fails closed when those tables are absent. There is no `check_function_bodies` bypass, and the proof tables stay off the prerequisite list. Each stored `granted_by` must equal the receipt actor.

`user_sessions.external_auth_context` is metadata only. It is non-null exactly when `id LIKE 'xs.%'`. When non-null it is a v1 object with exactly these keys: `v` number 1, `provider` text `dingtalk`, `connectionId`, `identityId`, `grantId`, `evidenceId`, `orgId`, `subjectAppScope`, `subjectKey`, `bindingRevision`, `applicationRevision`, `accessGeneration`, `capRev`, `assurance` text `self_authenticated`, `policyRevision` number, `scopeAsserted` boolean false. `BEFORE UPDATE OF external_auth_context` rejects every update of that column, including setting null and including setting the same value. This migration does not insert sessions and does not guard `TRUNCATE` on `user_sessions`. SQL scope and context predicates do not call `chr(0)`. The JavaScript parser still rejects NUL.

`down` proves one open caller transaction with two equal `pg_current_xact_id()` values and `transaction_isolation` exactly `read committed` before it changes timeouts or locks. Autocommit raises `STRICT_LOGIN_GRANT_DOWN_REQUIRES_TRANSACTION`. Any other isolation raises `STRICT_LOGIN_GRANT_DOWN_REQUIRES_READ_COMMITTED`. `lock_timeout` is 5 seconds and `statement_timeout` is 5 minutes. `ACCESS EXCLUSIVE` order is `directory_integrations`, `user_external_identities`, `user_external_identity_evidence`, `user_external_identity_login_grants`, `admin_login_grant_command_receipts`, `user_sessions`, `directory_connection_login_scope`. Evidence is before grants. `security_action_challenges` is locked only to drop this migration's trigger. Any scope row, grant row, receipt row, or non-null context raises `STRICT_LOGIN_GRANT_DOWN_BLOCKED` before drop. Drop only this migration's objects. Do not lock `users`. Restore timeouts only for those three refusal codes, not for `55P03` or `40P01`. Any SQL error rolls the caller transaction back. T4 down runs before a later proof down because the receipt foreign key points at the challenge parent.

## Installation witness

A failed catalog or `kysely_migration` read refuses. No process cache is kept. No migration row and no `pg_class` row under the three owned table names means never-installed. An unlogged table, a partitioned table, or a view of one of those names is not never-installed. Installed still requires the ordinary permanent tables (`relkind` `r`, `relpersistence` `p`) plus the context column, the two checks, the triggers, the functions, and the live-slot index. Any other named relation is partial: the witness refuses, and `down` raises `STRICT_LOGIN_GRANT_DOWN_BLOCKED` instead of treating it as absent. A connection with no scope row then stays on the legacy path behind the caller's share or the already held integration update, and a re-read. A ledger row with any required object missing, or strict objects without the ledger row, raises `STRICT_LOGIN_GRANT_INSTALLATION_REFUSED`. Table existence does not set `productionAvailable`.

Legacy DingTalk sign-in and administrator unlink can therefore return HTTP 503 while all connections are still unscoped. The installation check uses three database round trips for schema selection, the migration ledger and the combined catalog query. Issuing a session rechecks scope in its own transaction. During rollout, the rates of `grant_state_unavailable` on login and HTTP 503 on unlink distinguish this dependency from a user lacking a grant. Inspect the migration ledger and object catalog together when those rates rise.

`readConnectionLoginScope` returns immediately, with no lock, when the installation is never-installed. When it is installed, the function takes the integration `FOR SHARE` and then reads the scope row. Call it only at a legal point. Under the directory bind, that point is after the existing `FOR UPDATE`.

`insertConnectionLoginScope` takes the integration `FOR UPDATE`, re-reads absence, inserts one row, and holds that lock through the caller commit. It does not flip an environment flag.

## Lock composition

Callers hold integration at the rank they already have. They hold identity rows before evidence. `detachEvidenceForIdentities` locks unrevoked evidence `FOR UPDATE` in id order and applies the installed evidence terminal transition. It runs when no scope row and no grant exist. An already terminal evidence row is not updated again. `revokeForScope` and `revokeForIdentity` then lock unrevoked grant rows `FOR UPDATE` in id order and apply the terminal transition. They do not lock integration, users, evidence, watermarks, or sessions. If the grant id set changes while those locks are taken, the function throws and the caller rolls back rather than locking a new id out of order.

Exact-grant session revocation does not accept `lockedUserIds` or any other array as proof that locks are held. `collectStrictGrantSessionUsers` is a plain read of `xs.%` sessions whose stored `grantId` is one of the exact grant ids. `prelockUserSessionWatermarks` is the call that locks. Its `userIds` argument is the set to lock now. For each id, in code-unit order, it inserts the non-revoking `1970-01-01` UTC baseline `ON CONFLICT DO NOTHING` and then locks that watermark row `FOR UPDATE`. It does not advance `revoked_after` and it does not lock sessions. A missing watermark row is absence, not a held tuple. The caller is expected to already hold the user row when this runs. This function does not take a new user or directory lock.

`revokeSessionsForExactGrants` derives its own user set, locks those watermark rows, advances them with unqualified `GREATEST(revoked_after, clock_timestamp())` and the fixed reason `strict_grant_revoked`, and only then locks `user_sessions` by id and sets `revoked_at`. It does not read `DIRECTORY_DEPROVISION_REVOKE_CREDENTIALS_ENABLED`, does not call `revokeUserSessions`, and does not bump `access_generation`. If the user set grows in a way that would lock a new watermark out of order, or a session appears for a user whose watermark is not already locked, it throws before taking that lock. The caller rolls back.

Lane B collects credential-leg users with its own reads, unions them with `collectStrictGrantSessionUsers`, and calls `prelockUserSessionWatermarks` once on that union before any session lock. B's watermark value updates for the credential legs live in `strict-credential-chain.ts` and run on rows this prelock already holds, still before session locks. B then calls `revokeSessionsForExactGrants`. After that returns, B does not lock a watermark row it does not already hold. Re-locking a row this transaction already holds is compatible. A new watermark lock after session locks is not.

There is no second lower-rank directory or root discovery after session work.

## Grant bundle

The admin command imports the only grant writer, `insertConsumedGrantBundle`, from `strict-login-grant-bundle.ts`. Ordinary login and directory readers import the separate `strict-login-grant-store.ts` module. The bundle module statically imports `createAdminGrantProofService` from `admin-grant-proof.ts` and calls `assertConsumedOnTx` and the receiving comparison before the receipt insert and again immediately before each grant insert. `grantedBy` must equal the context user and the intent actor before the receipt insert. The service is created with the caller-supplied `publicOrigin`. It does not catch load failures, `ADMIN_GRANT_SESSION_ASSERTION_UNRELEASED`, `ADMIN_GRANT_ACTOR_INPUTS_UNRELEASED`, or `ADMIN_GRANT_CONSUME_BRAND`. Those errors propagate and no receipt or grant is written. The live `consumeOnTx` stores a consumed brand on the returned object. `assertConsumedOnTx` requires that brand, the same transaction object, the same normalized intent, and the session assertion. `issue` still throws `ADMIN_GRANT_ATTEMPT_VARIANT_UNRELEASED` and is not this writer. `ADMIN_GRANT_ACTOR_INPUTS_UNRELEASED` remains a contract code and is not thrown by the current consume or assert bodies.

Stable grant ids are `slg.` plus the SHA-256 of `metasheet:strict-login-grant-id:v1|` and `JSON.stringify([commandKey, ordinal, userId])`. Ordinals are the 1-based code-unit order of intent `userId`. The command key is `adminGrantCommandKey` from `admin-grant-proof-storage.ts`: SHA-256 of `metasheet:admin-login-grant-command:v1|` and `JSON.stringify(['admin_login_grant_enable', actorId, orgId, commandId])`. Ids are computed before the receipt insert and stored in `result.grants`. The receipt is inserted before the grants. A `23505` on `user_external_identity_login_grants_live_slot_uq` is `STRICT_LOGIN_GRANT_GRANT_OCCUPIED`. The store does not revoke the occupant and does not read a receipt after the statement error. Other `23505` conflicts keep the constraint name for a later new-transaction reconciliation by the command. The aborted transaction is not reused.

The command module is specified here and is not part of the early schema publish. It uses a static import of `assertAuthenticatedSessionContext`, which `security-action-proof.ts` exports as the alias of `assertSessionContext`, and a type-only import of `StrictLoginGrantCaller`. It does not property-lookup that name, does not dynamic-import it, and does not catch a load failure into a finished path. The live proof module also static-imports that alias. `requireSession` calls it directly. `ADMIN_GRANT_SESSION_ASSERTION_UNRELEASED` remains a contract code and the current `requireSession` does not throw it.

The command's authorized read runs first, before `prepareConsume` and before target discovery. It binds the same actor and organization, derives the command key, and does not consult proof secrets, current targets, evidence freshness, old-proof credential match, grant enabled-state, or target roles. The actor-only root revalidates the actor plan, runs the current account gate on the locked actor, locks the actor's positive organization membership, then current watermark, session, and `lockBinding`, then the read-only browser assertion. `browser.session` must be the same object as the context before that discovery. `assertCurrent` takes no row locks. A new actor session id is allowed. The old proof session id, issued-at, and browser are not compared. The old proof does not need to be unexpired. There is no target receiving call and no receipt return before those current checks. The receipt compare then uses stored purpose, actor, organization, command id, and the exact canonical intent, not the digest alone. The same key with a different intent is a conflict. Absence is an authorized miss. The read may see retained grant identity inside the receipt. It does not join current targets as a success condition.

On a miss, that actor-only root closes before fresh preparation. `prepareConsume` runs inside the one reconciliation try. The fresh root uses the exact `prepared.privilegePlan` object from that call. It does not call `discoverPrivilegeRolePlan` again. `consumeOnTx` owns the one consume-phase receiving read and returns the genuine snapshot. The command does not call the receiving reader and does not call it again after session or proof locks. Fresh order is consume, receipt, all grants, the required caller-transaction values-free audit, then commit. The audit insert uses the same transaction and fixed action, outcome, target count, and command key. Failure aborts. A pool audit repository is not a substitute. The command does not activate a user, restore membership, advance `access_generation`, supersede deprovision, or insert a session.

A same-command race, a stale `prepareConsume`, a consume-stale error, or a named unique conflict may reconcile once by reading the committed receipt in a new transaction. That read uses the same context, browser, and normalized intent captured for the operation. It does not call `prepareConsume`, `consumeOnTx`, mutations, bcrypt, or a provider exchange again. Unknown commit stays uncertain when that read cannot establish the receipt. `STRICT_LOGIN_GRANT_GRANT_OCCUPIED` is rethrown.

## Preserved behavior

Evidence-only identities detach before identity delete even when no scope row and no grant exist. Strict-only deprovision is work even when legacy `grant_changed` is absent and `effects.length` is 0. It does not take a new `access_generation` bump. DR-11(a′) stays in Lane B's credential primitive: sessions are grant, user, strict and left, or depart-all; tokens are user, left and grant or strict, or depart-all; left is clear or no remaining method. The exact credential flag gates those broad legs. Exact-grant session revocation still runs for grants this call revoked. `noRemainingLoginMethod` counts a usable local password or a grant whose current pins, account, and membership would pass. Cards do not count. A read error aborts. Invite acceptance is independent of a strict grant. Three hundred seconds of evidence freshness is admission-only for new grant issue and consume. Continuing login, verify, and refresh use unrevoked current pins plus the ordinary account and membership, not `fresh_until`.

`SECURITY_ACTION_POLICY_REVISION` remains the constant in `external-login-assurance.ts`. A lower stored `policyRevision` refuses on continue. A higher value does not. `capRev` is retained and not compared. `scopeAsserted` stays false.
