## 1. 用户已确定的方向与本稿建议

用户已确定：功能默认关闭；关闭时使用系统默认考勤时区；启用后采用管理员配置的员工／考勤组时区；已批准且处于有效期内的出差使用目的地时区。先审阅，批准后开发。

本稿建议：开关归组织管理员所有，员工不能自行开启、覆盖考勤时区，也不根据设备时区、GPS 或 IP 自动切换。“系统默认时区”指所属组织的默认考勤规则时区，不是操作系统时区、数据库会话时区或员工个人界面时区。每个组织必须能在设置页明确看到该默认值。

启用时建议采用唯一优先级：有效批准出差 → 管理员配置的员工专属时区 → 当前有效的计算考勤组时区 → 系统默认考勤时区。员工专属配置可以为空，表示继承；考勤组配置为空也表示继承。已配置但非法、读取失败或有多份冲突配置，不得伪装成“未配置”后回退。

基础规则及两项首版限制已获用户批准开发；旧收尾结果和本次开发授权仍不构成合并、部署或启用授权。

## 3. 明确的产品行为

| 状态 | 采用的时区 | 例子 |
| --- | --- | --- |
| 关闭，员工在东京，设备为东京时区 | 系统默认 | 系统为 Asia/Singapore，则按新加坡时间与日期归属 |
| 关闭，已批准新加坡出差 | 系统默认 | 出差审批仍存在，但目的地不覆盖默认时区 |
| 开启，员工配置 Asia/Tokyo | 员工配置 | 东京当地 09:00，即 UTC 00:00 |
| 开启，无员工配置，考勤组配置 Asia/Singapore | 考勤组配置 | 按新加坡本地工作日及班次时间计算 |
| 开启，东京员工已批准且生效的新加坡出差 | Asia/Singapore | 东京 10:00 的同一瞬间为新加坡 09:00；不会凭设备时间变成东京打卡 |
| 出差尚未最终批准、尚未开始、已结束、已撤销／失效 | 员工 → 组 → 系统默认 | 结束后恢复当前基础配置，不恢复可能已过期的旧配置 |
| 开启，无员工及组配置 | 系统默认 | 合法继承，不阻止普通员工打卡 |

开启多时区不会自动把班次 09:00 改成另一个墙上时刻：原定 09:00–18:00 按有效目的地时区解释。出差另有工作安排时，应另行通过既有排班流程调整。出差不自动免打卡、不自动生成已打卡事件，不自动发放加班、假期余额或报销权益。

普通在线打卡始终由服务器生成 UTC 瞬间。多时区改变的是该瞬间的显示、工作日与班次窗口解释，不改变世界上实际发生的时刻。日历“今天”是该有效时区的自然日；跨夜班的归属工作日由现有工作日解析器决定，两者可能不同。

## 4. 出差审批与时区生效

首版支持一张出差单、一个目的地时区、一段连续有效区间。目的地城市可显示，但决定计算的是经过校验的 IANA 时区。多城市行程、地理定位、外部差旅系统同步留作后续独立需求。

出差单输入员工、目的地时区、起止时间和必要审批信息。起止时间必须显示所采用的时区和 UTC 偏移，转换并保存为 UTC 瞬间；生效区间使用 startAt ≤ instant < endAt。首版采用整班边界生效，不允许在一个已经开始的班次中途更换时区。审批预检应拒绝切穿已发布班次／已存在未闭合记录的区间；界面提示选择下一完整班次开始。不能用一个只有日期的范围暗示精确的抵达时刻。

最终批准才在同一事务发布出差时区安排。提交、草稿、审批中、拒绝不会生效。撤销通过已有批准后的取消流程治理：批准取消后终止未来有效安排，保留原审批及使用过的快照。修改已批准的目的地或范围需新一轮审批，不能原地覆盖历史。

同一组织同一员工的已生效出差安排不得时间重叠，使用数据库排他约束／锁防止并发批准。批准时校验组织、员工有效成员身份、详情和审批实例的绑定。读侧遇到两条冲突安排必须明确拒绝，不能按创建时间挑一条。

开关、默认时区、员工／组配置的变更只影响生效后的新班次和新记录。已开始的班次和下班打卡沿用原记录冻结的上下文；精确重试沿用原操作回执。不能因出差开始、结束或开关变化，让同一班的下班落到另一个工作日。

首版保留现有按员工／工作日聚合的记录模型，不悄悄扩展成多条同日记录。跨时区往返若在同一归属工作日产生第二份不同的时区／班次上下文，预检或新开班写入返回明确 409，要求管理员调整完整班次安排；不能合并两份不同上下文来计算。跨日期变更线、同日多时区重复开班因此不是首版无条件支持的场景。这一限制需要审阅接受，否则须单独批准更大的记录模型改造。

## 5. 最小数据设计

以下为拟议结构，字段和路由在批准后的实现 PR 中最终核对，不代表现有数据库已经有这些字段。

1. 组织策略：一份 org_id 唯一的多时区开关、版本和变更审计；enabled 为严格布尔值，缺省 false。默认时区复用所属组织默认考勤规则，不再复制一份可以漂移的默认值。不存在策略行等于关闭；数据库读取失败不等于不存在。
2. 员工配置：组织内管理员维护的 IANA 时区覆盖，带生效区间、版本及审计。空配置表示继承。时区配置不取 users 的界面显示偏好。若核对后有合适的既有组织内有效期配置则复用，否则新增最小配置表。
3. 考勤组：复用 attendance_groups.timezone 和有效计算组归属。组变更不能使历史记录重算；启用预检检查计算组归属的完整性。排班组与展示组不代替计算考勤组。
4. 出差详情：新增 business_trip 请求类型和类型化详情表，绑定同组织审批请求／员工，保存目的地时区、UTC 起止瞬间及最终批准后的有效状态／版本。按已有专用请求类型模式提交，不开放任意 metadata 伪造批准安排。
5. 时间上下文快照：复用事件及记录现有 timezone、work_date 和 UTC 时间字段；按需要增加受版本约束的来源快照，包含模式、策略版本、员工／组配置版本、出差引用和冻结窗口。只增加实际重试、重算和解释所必需的字段，不另造通用规则平台。

所有新表和引用必须包含 org_id 约束，并验证引用对象来自同一组织。新迁移放在 packages/core-backend/src/db/migrations；不写 legacy SQL 流。迁移不回填或删除旧考勤数据。旧记录没有新策略快照时按旧存储字段显示，标为旧规则记录；不能猜测当年的出差。

用户此前说旧数据可以不要，不作为本轮自动删库或删表授权。开发验证使用独立合成数据库；如确需清空特定环境，另报清单和影响再批准。

## 6. 服务端、API 与界面

提取独立 attendance-timezone-policy 模块，输出有效 IANA 时区、来源、版本、有效边界和必要的冻结信息。index.cjs 只做路由接线。纯选择逻辑与组织内数据库读取分开；事务内读取及冻结作为写入权威。

统一流程：服务器 UTC 瞬间 → 组织策略 → 有效基础配置／批准出差 → 有效时区 → 该时区自然日 → 已发布班次候选及跨夜归属 → 原有规范冻结／事件写入。

不能只覆盖最终返回的 timezone 字段：候选窗口构造、轮班日期索引、休息段、工作日／节假日判断、晚到早退、每日聚合都必须使用同一上下文。批量预取路径和普通读取路径也必须相同。已闭合记录读取／导出使用存储快照；禁止按当前设置解释过去的记录。加班、补卡及更正使用其目标班次的冻结上下文；历史导入保留现有受治理的源时区协议，不被当前出差自动重解释。

API 建议：

- 复用 GET /api/attendance/rules/me，增加 attendanceTimeContext：resolvedForInstant、effectiveTimezone、timezoneSource、mode、policyVersion、下一生效边界。此上下文针对服务器当前瞬间；原 asOf／resolvedForDate 仍代表所查询的排班日期。二者不能混为一谈。日历多日预览返回逐日有效上下文，而不是假设整个月同一个时区。
- 前端时钟在校准成功后消费 attendanceTimeContext 的有效时区；日期与日历仍校验服务器瞬间／排班日期一致性，跨出差边界刷新，不增加无限纠正请求循环。沿用 #6321 的失效、恢复和禁止设备时钟回退规则。
- 普通 POST /api/attendance/punch 仍不接受客户端 occurredAt。省略 timezone 时服务端决定；提供合法但与权威上下文不一致的 timezone 时返回 409 上下文已变化，客户端刷新。非法值返回 422；不能由客户端选择目的地或伪造出差身份。
- 拟增加组织时区设置、员工覆盖和专用出差提交／批准取消契约；路由前缀及权限沿用现有 attendance 管理／请求约定。审批权限与配置权限分别验证；本人读取只返回自己的生效信息。所有跨组织伪造拒绝 403/404。
- 配置修改使用版本并发检查；旧版本提交返回 409。写入事务重新验证组织成员及有效策略，遵守已有锁顺序、操作回执和冻结约束，不另造幂等协议。

管理员设置页显示“多时区考勤”（默认关闭）和系统默认时区；启用前提供受影响人数／冲突数预览。员工页显示“当前考勤时区：新加坡；来源：已批准出差；有效到……”。关闭时显示“系统默认时区”。设备／个人界面时区只可辅助对照，不能替换考勤时间。导出保留 UTC 瞬间、归属工作日、IANA 时区和来源，跨时区记录不能显示一个无时区的混合时间列。

## 7. 边界与故障处理

| 情况 | 拟定处理 |
| --- | --- |
| 系统默认时区未配置或非法 | 管理员设置／启用预检明确提示；拒绝受影响计算，不静默变 UTC |
| 配置或批准安排读取失败 | 503，不降级到设备或另一时区；零新增事件／记录 |
| 浏览器时区、设备时钟改变 | 不影响服务端归属；前端失去校准时显示不可用，不伪造精确时间 |
| 返回前策略版本变化 | 以写入事务权威读取及冻结结果为准；响应解释实际采用的版本 |
| 同一操作重试跨午夜或跨出差结束 | 回放原回执，不重复写入、不改归属；输入冲突依原规则拒绝 |
| 一次开班后时区改变 | 原班下班使用已冻结上下文，新完整班次才用新配置 |
| 两份有效配置／出差冲突 | 409，零写入；提交／批准侧并发约束同样覆盖 |
| 夏令时跳过的本地时刻 | 不能构造合法瞬间时 422，要求调整；不自动推后一小时 |
| 夏令时重复的本地时刻 | 出差输入需显示并确认具体偏移；排班歧义未被现有显式窗口合法消解时拒绝发布／开班，不能静默选一次 |
| 跨夜班与夏令时 | 分别验证真实 UTC 时长和既有休息／计薪分钟口径，不以墙上钟表差值代替实际时长 |
| 关闭／回滚功能 | 不重写历史；关闭影响新班，已开始班继续冻结语义。紧急退旧程序先停止写入并检查新类型／快照兼容，不声称一键无损回滚 |

## 8. 分阶段开发计划

每个阶段以一个可审阅 PR 为单位；实现和审阅分开。阶段 PR 不代表可单独部署的完整产品。整个功能始终默认关闭，直到全链路验收通过且用户另行批准启用。

| 阶段 | 交付 | 完成门槛 | 粗估工作日 |
| --- | --- | --- | --- |
| D0：批准后冻结合同 | 核对最新 main、受影响调用清单、确定路由／锁顺序／记录碰撞限制，完成设计锁批准记录 | 用户批准本稿；无重复实现；不存在悬而未决的 P0 语义 | 0.5–1 |
| D1：组织策略和配置 | 最小 Kysely 迁移、组织策略与员工配置、计算组继承、纯解析器、配置 API | 关闭／开启优先级、组织隔离、非法值、缺行与 DB 故障、并发版本、迁移 apply/replay/rollback 测试通过 | 2–3 |
| D2：运行时统一 | 打卡、已发布窗口、跨夜／轮班日期、事务冻结、规则读取、日历预取及历史读取区分 | 默认关闭语义正确；重试不漂移；现有守卫 mutation 红→恢复绿；业务计算与 UI 上下文一致 | 2–4 |
| D3：出差审批 | 专用出差请求及详情、最终批准事务、重叠防护、取消／结束恢复、边界预检 | 待审不生效、批准一次生效、重试不重复、同日冲突与中途切换明确拒绝、取消不改历史 | 2–3 |
| D4：界面与完整验收 | 管理员开关与预览、员工时区来源、出差申请／审批、日历／导出、设计和验证 MD | 浏览器证据、下面所有适用门槛通过、新 head CI；独立终审 | 2–3 |

总计约 9–14 个有效工作日，包含并行审阅；不是无人值守连续运行承诺。D0 如发现冻结／每日记录模型必须扩大，先报告范围和估时，不偷偷加建多日多时区模型。

开发模型建议沿用此前授权的分工：Sol6.1/high 负责主要实现及真实测试；Astra/high 负责时间归属、审批一致性和独立审阅，发现难以反驳的并发／冻结问题时再升 max；Luna/medium 负责证据索引和文档一致性。Kimi K3 与 Grok4.7 分别做有边界的第二意见，记录实际 CLI 模型和支持的 effort，不假定 CLI 一定支持 high/max。最终结论由主代理核对代码与原始测试证据，不靠模型投票。
