# 多维表公式能力（C 簇）— 现状对账与「RFC 重开」决策简报

**类型**：决策简报 / 能力现状分析（docs-only，零 runtime，可自验）。非设计锁——不主张任何新设计，只对账**已存在的能力**、映射目标池 C 簇缺口到**已有的 RFC 决定**，并给 owner 一个可拍板的框架。所有事实按 `origin/main` @ `140cd6e49` 逐条核实。

**为什么现在给这份**：C 簇（公式求值器）是目标池的重大缺口，其唯一决策阻塞点是 `formula-parser-and-derived-ref-graph-rfc-b1c1-20260526.md` 的「重开」判断。本简报把该判断拆到可执行粒度——**并发现其中一大块无需重开 RFC 即可自主推进**。

---

## §1 公式能力现状（逐条核实，非泛述）

- **求值引擎**：`packages/core-backend/src/formula/engine.ts`，字符串替换 + `calculate()` 模型。**已注册 78 个函数**（源码 `functions.set('…')` 计数）——RFC 起草时（2026-05-26）为 46 个，经 1a/1b 批次 + 目录对齐 #3934 增长约 70%。
- **派生输入**：formula 字段**可**引用 lookup / rollup 字段（单跳派生输入；token picker 只过滤 `type === 'formula'`）。
- **formula→formula = 今天被挡**：A2-defense（`univer-meta.ts:~1827` 注释「The product does NOT support a formula field referencing another formula field」）在**创作期硬挡**——前端 `formulaSourceFields` 排除 `type === 'formula'`，表达式校验把手打的 formula 引用标错并禁存，raw-API 路径也补挡。根因：`recalculateRecord` **无记录内拓扑序**，formula→formula 链会对陈旧中间值静默求值。（注：权限层 `univer-meta.ts:~3124` 仍**防御性**遍历 formula→formula 边以处理遗留/安全，这不是能力支持。）
- **依赖持久化**：formula 有持久依赖(RFC §C1 所述 `formula_dependencies` 语义)；lookup/rollup **无**持久依赖图（保存时即时扫 + 单层重算）。统一图 `derived_field_references`（RFC 的 C1）**未建**。

---

## §2 RFC 已拍板的两条决定（本简报不推翻，只映射）

`formula-parser-and-derived-ref-graph-rfc-b1c1-20260526.md`（已拍板 2026-05-27）：

| # | 决定 | 翻盘条件（RFC 原文） |
|---|---|---|
| **B1** | 做 A2b 加固宏展开；**B1b（ANTLR AST 重求值）推迟** | ① 产品要把公式能力**做大**（新增大量函数/类型/**跨记录语义**），重写求值反比扩 `calculate()` 划算；② 决定砍掉「多维表 formula 复用网格 A1 引擎」的耦合本身 |
| **C1** | **暂不建**统一派生依赖图（C1 只是手段，单跳够用） | 出现具体的**多跳派生**需求（formula→formula / 传递 rollup） |

RFC 的核心论证（仍成立）：**B1b 与 `calculate()` 紧耦合，要么对 AST 重实现全部函数语义、要么换外部函数集 → parity 风险高、无即时产品收益**。故「扩 `calculate()`」是耐久路径，「重写 B1b」只在加**跨记录语义**时才划算。

---

## §3 C 簇缺口分解为三条路（关键产出）

把「公式求值器」缺口按**它撞哪条 RFC 翻盘条件**分成三段，成熟度与所需决定天差地别：

| 路 | 内容 | 撞哪条翻盘条件 | 可否自主推进 |
|---|---|---|---|
| **路 1 — 更多标量函数** | 补齐引擎可注册但目录未暴露 / 尚未实现的**单值函数**（文本/日期/数学/逻辑族） | **无**——沿既有 `calculate()` + 目录（#3934 模式）扩，不触 B1b/C1 | **✅ 可自主**（每批开 PR，门禁验签名/i18n/漂移守卫） |
| **路 2 — formula→formula 多跳** | 让 formula 引用另一 formula（传递派生） | **C1 翻盘条件**（具体多跳需求）+ 需 C1→C2a（递归 CTE 传递闭包 + 拓扑级联重算）→C3（环检测） | ❌ 需 owner 重开 RFC + 后续 runtime 弧 |
| **路 3 — AST 重求值 / 跨记录语义** | 数组/对象操作数深化、跨记录聚合语义、以 AST 取代字符串替换 | **B1 翻盘条件 ①**（公式能力做大 + 跨记录语义） | ❌ 需 owner 重开 B1b（parity 风险高） |

**这是本简报最有价值的发现**：目标「对标并超越」确实触发 B1 翻盘条件①的字面（「把公式能力做大」），但 RFC 自身论证**扩 `calculate()` 比 B1b 划算，除非加跨记录语义**。因此——

> **路 1（更多函数）是 C 簇里一大块可**在不重开 RFC 的前提下**自主推进的子路**，沿 #3934 已证的目录+守卫模式（引擎注册 → 目录暴露 → backend 漂移守卫 → i18n）。owner **无需**为路 1 做任何决定。

---

## §4 给 owner 的决策框架（三个独立拍板，非一揽子）

1. **路 1（更多函数）—— 无需 owner 决定，可授权我在子代理恢复后按批推进**（每批：引擎实现或已注册 + 目录 + 漂移守卫 + i18n，开 PR 待审）。若 owner 只想动一处，这条**零决策成本**。
2. **路 2（formula→formula 多跳）—— 需 owner 拍「是否重开 C1」**。判据 = 是否有具体的多跳派生场景（RFC 原文翻盘条件）。若重开，按 C1→C2a→C3 推进（各独立 gate）。
3. **路 3（AST / 跨记录）—— 需 owner 拍「是否重开 B1b」**。RFC 已警告 parity 风险高、无即时收益；建议**仅当**路 1/路 2 不足以达成对标目标时才启动。

**顺序建议**：先走路 1（自主、零决策、即时可见的函数覆盖增益）→ 观察对标缺口是否仍显著 → 再由 owner 决定路 2/路 3 是否值得其重开成本。这避免为「大部分只是缺函数」的缺口过早支付 B1b/C1 的重写代价。

---

## §5 本简报不主张什么

- 不主张推翻 RFC 的 B1/C1 拍板——只把 C 簇缺口映射到其既有翻盘条件。
- 不主张路 1 的具体函数清单（那是各实现批 PR 的内容 + 门禁验证；#3934 是第一批）。
- 不主张 formula→formula「应该」支持——只陈述它今天被 A2-defense 挡、启用它 = C1 的范围。
- 不碰权限/中央授权（K3）；§1 对 A2-defense 与权限 taint-check 的区分仅为陈述现状。
- 未命名任何外部产品——C 簇「缺口」按「尚未具备的能力」表述，非对标某产品。
