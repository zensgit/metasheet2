## FU-1 — dynamic link-field target resolution for `resultWriteback`

### (a) The exact open decision

T3-5 v1 ratified **literal-triple-only** addressing (`targetBaseId` + `targetSheetId` + `targetRecordId`,
second-batch ballot Q2). The open decision: **may the target *record* of a cross-base approval-outcome
backwrite ever be resolved dynamically from a link field on the trigger record — and if so, under which
mandatory guard rails — or does literal-triple-only remain the sole addressing mode?**

### (b) Risk class: cross-base-writeback (compounded by untrusted-data-as-address)

Dynamic resolution makes **record DATA choose the write address**. Anyone who can influence the trigger
record's link cell (own edit, shared record, imported row, automation) steers where the approval outcome
lands — the exact laundered-input threat locked in
`multitable-ai-output-untrusted-write-source-designlock-20260705.md` §1, applied to *addresses* instead of
values. Without a pinned domain, a link cell repointed at an arbitrary record turns a ratified, narrow
writeback into a data-driven arbitrary-record write in another base.

### (c) PROPOSED default (fail-closed / default-off)

**Do not build now.** Literal-triple-only remains the sole addressing mode until a named integration
presents a concrete need (same trigger discipline as A3 destination authorization: capability waits for a
named consumer). **If and when the owner ratifies a build**, the following guard rails are locked as
non-negotiable preconditions of that slice:

1. **Only the record id may be dynamic.** `targetBaseId` and `targetSheetId` stay literal config — the
   write *domain* is pinned by the rule author; the link field selects a row inside it, never a base/sheet.
2. **Domain check on the resolved record (fail-closed, reject-never-coerce).** The resolved record must
   live in the declared target sheet/base; any mismatch → skip, nothing written (membrane §2-B).
3. **Resolution is fail-closed.** Empty link, multi-value link, dangling reference, or a link field not of
   single-link type → observable `backwriteSkipped`, source untouched, no partial write.
4. **Same membrane, no parallel weaker path** (membrane §2-A/§2-C and §3 cross-base row): the SAME executor
   gate family as v1 (`evaluateCrossBaseWriteGate`), trigger-actor authority re-checked against the
   *resolved* record, per-record eligibility + lock checks, no-oracle uniform skip
   (masked ≡ missing ≡ not-writable), same-base resolution rejected (v1 hardening preserved), and the
   singleton per-target-base quota unchanged.
5. **Default-off at save level:** the dynamic-addressing config key is rejected at rule save until the
   enablement precondition (f) is met — merged ≠ enabled ≠ safe-to-enable.

**Argument:** the ask (write the outcome onto "the linked ERP order") is real but currently hypothetical —
no shipped consumer needs it, v1 literal triples cover the known cases, and the added surface is a
data-driven cross-base write, the highest-risk class in this line. Fail-closed default costs nothing today
and keeps the decision reversible; building speculatively does not.

  `targetSheetId`/`targetBaseId` → skip, nothing written anywhere. Removing the resolved-record domain

## FU-2 — idempotent cross-base-backwrite ledger for resume retries

### (a) The exact open decision

V1 documented (did not fix) that **a resume retry may re-consume cross-base quota and re-write the target**
(v1 build-contract note 5: *"quota may be re-consumed on a resume retry unless a separate idempotent
cross-base-backwrite ledger is introduced"*). Decision: accept this posture, or ratify an idempotency
ledger for the backwrite.

### (b) Risk class: other (duplicate-write / quota-burn; not a new authority surface)

The retried write passes the full ratified gate again — no privilege change. Exposure is a duplicated
status/approver/completedAt patch (last-write-wins on identical values) and double quota consumption.

### (c) PROPOSED default

**DEFER — keep the documented posture.** Revisit only on real evidence of duplicate backwrites or quota
exhaustion from resume retries. If later ratified, reuse the shipped T2-6 claim-then-fire shape
(`meta_automation_event_fires`, `INSERT … ON CONFLICT DO NOTHING RETURNING`) keyed per approval-completion ×
target triple — no new mechanism class.

### (d)–(f) in brief

Blast radius: same `writeApprovalResultBackCrossBase` path + one table (only if built). Golden (only if
built): replaying the same completion event writes/consumes exactly once; removing the claim → double write
→ RED. Enablement: migration-bearing ⇒ owner-gated slice of its own; nothing ships from this draft.
