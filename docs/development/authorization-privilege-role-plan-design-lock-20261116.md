# Privilege role discovery and revalidation

## Scope

This slice supplies a read-only role plan and a consistency check, not authorization. It introduces no business caller, proof purpose, flag, schema, deployment or consumer conversion. The role-witness transaction primitive remains unchanged. Full writer closure and B2 acceptance remain separate gates.

## Frozen contract

1. `discoverPrivilegeRolePlan(queryable, subjectIds)` requires a nonempty array of canonical user IDs: nonempty strings, no surrounding whitespace or ASCII controls, at most 255 code units. Duplicate subjects collapse and sort by code unit. It never trims or stringifies IDs.
2. Exactly one parameterized SELECT reads complete `(user_id, role_id)` memberships directly from `user_roles`. No role join, privilege filter, namespace filter or cache is allowed. Empty role sets are explicit. Unknown subjects, malformed rows/role IDs and duplicate pairs fail closed. Role spelling is preserved.
3. The result contains only `subjectIds`, ordered `subjects` with their complete `roleIds`, the role union and `lockPlan`. Every container is copied and frozen. A module-private WeakSet recognizes only plans generated by this module; casts, spreads and serialized copies are not plans.
4. The deeply frozen `lockPlan` contains only `intent: 'CONSUME_CLASS_DECISION'`, `roleIds`, and `witness` with both subject `userIds` and `admissionUserIds`. Use exactly this object with the existing transaction entry. Additional R1, identity or business needs require a separately reviewed complete consumer; do not extend or reuse this plan as B2 authorization.
5. `revalidatePrivilegeRolePlan(tx, plan): Promise<void>` first asserts a real open runtime token bound to itself, genuine plan membership, exact `tx.plan === plan.lockPlan`, shared CONSUME intent, the exact role-row key set, every locked R5 user and both actual witness sets. It invokes `requireUserRows` and `requireRoleRows`. It takes no late locks and accepts no alternate executor.
6. Read `readPrivilegeInputs` sequentially for every subject through that same token, checking the runtime brand before and after asynchronous reads. Compare complete per-subject role sets, not merely the union or privilege class. Added, removed or transferred membership is stale even if the union is unchanged. Missing rows and malformed or unreadable inputs refuse.
7. Success returns only void. It exports no inputs, class, witness, authorization result or serializable verified object. Success does not prove that all privilege sources remain stable until commit. A future complete consumer must reassess within its fully reviewed transaction.
8. Plan errors use fixed `AUTHORIZATION_INPUT_PLAN_INVALID` messages and bounded reasons. Membership drift uses `AUTHORIZATION_INPUT_PLAN_STALE`, status 409, reason `role_membership_changed`, retryable false. Brand failures retain the existing token-rejection family. Unavailable errors never expose driver messages, detail, cause, identifiers or input values. Caller must abandon the transaction and rediscover; no implicit retry or catch-and-write continuation.

## Exact registration and guards

- Register only K-03, `revalidatePrivilegeRolePlan|readPrivilegeInputs`, count one, ADVISORY, with the explicit nonauthorization reason. The token parameter alone is not LOCKED_DECISION.
- K-02 stays PENDING_LOCKED/AIS-3b, the pending pin is unchanged, `hasPendingConsumers()` stays true, converted writer counts stay zero and the prerequisite stays false.
- Permit exactly three helper-to-contract import statements: brand value/assert/error, brand queryable type, and lock plan/token types. Permit exactly one helper-to-classifier static statement. Pin static import shapes and occurrence counts; do not allow a wildcard consumer, namespace replacement, re-export, dynamic load or brand mint.
- Preserve full production/plugin scans, missing/duplicate/unexpected-edge controls, consumer omission/rename/namespace controls, the mint restriction and existing runtime-template writer-removal regressions.

## Verification gates

| Gate | Evidence required |
| --- | --- |
| G1 | Whole new unit file: normalized and empty subjects, immutable copied results, actual entry tokens, per-subject drift including unchanged union, forged/closed/async-escaped token, missing R3/R5/role locks and fixed outward error shapes |
| G2 | Whole lock/classifier/writer-guard/consumer-guard and role-assignment neighbors, with no reduced assertions, test-name filtering or skipped acceptance |
| G3 | Independent source mutations removing runtime brand, post-await check, per-subject comparison, R3 witness, actual held-row checks, exact plan identity or K-03 registration must produce discriminating red; restore exact current dirty source |
| G4 | Existing CI-registered serialization whole-file gains real discovery/exact returned plan/void success including empty roles and repeated subjects; another connection commits add/remove/swap before entry, all stale with zero business writes/no late locks |
| G5 | Real deletion after discovery yields entry missing-role refusal before R3/R5/work; missing user refuses. Keep schema legal, preserve the DB sentinel and existing lock-conflict controls; no DDL weakening to manufacture an orphan |
| G6 | Independent code acceptance and main-owned PostgreSQL/mutation receipts. Author unit green is not PG, CI, deployment, writer closure or product acceptance |

Database execution and source mutations are separately coordinated. Do not run the DB suite without a real authorized database or count its no-database skips as evidence. The existing four role-witness lock-control cases remain distinct from the new helper scenarios.
