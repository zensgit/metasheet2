# 多时区实施 D0：技术合同补充
日期：2026-10-12（Asia/Taipei）
状态：基础设计及两项首版限制已获用户批准；以下为保持现有安全／冻结不变量的实施约束。管理员关联单据模式的新建议仍待用户范围答复，不在本合同中默认批准。不得合并、转 Ready、部署、启用或操作真实数据。

冻结源：main154df39332fd28dd02b71795a42e0e072dd19df0 / tree35910045e2d8b4c41b72ddeca5c04e9eca1c9f4d。新 Mac 专属代码目录独立；旧证据与旧工作区只读。Astra/high 已完成源级合同审阅；这是分析，不是新功能测试通过。

1. 系统默认只来自所属组织唯一有效默认考勤规则。新增严格读取，不复用现有 loadDefaultRule 的 DEFAULT_ORG_ID/常量/schema-error 回退。缺行、非法、重复默认、读失败分别有明确值无关错误。新策略缺行只说明多时区关闭，不说明默认时区可省略。
2. 保留班次身份／墙上时刻选择，将有效时区贯穿 resolveWorkContext、prefetch、published candidate、rehydrate、W4 frozen builder 与 W7 effective facts；后层不得再以 shiftTimezone 覆盖。W4/W7 独立功能开关保持当前默认与权限，不因本功能顺便启用。
3. checkout 先找当前组织员工唯一可续接的原冻结班，加载原快照，不只查询现在时区的今天／昨天。多目标 409；同日新开班在 canonical target lock 内比较工作日、班次／assignment、时区、窗口及版本身份，不同上下文零事件增量拒绝。
4. 同键回放必须在读取可变新策略前完成；出差结束、策略关闭或后续读取故障不改变原精确回执。新策略不能作为由客户端随时间变化的字段添加到原 operation 指纹。
5. 原 FrozenAttendanceContextV1/V2 均为闭合合同，不直接塞 policyVersion/tripId。使用独立版本化 timezone provenance companion，同事务绑定既有冻结身份／指纹。外部 prepare 与 canonical 内部权威读取仍按既有 fingerprint/equality 检测差异，不删除 divergence guard。
6. 员工覆盖及出差有效区间为明确 UTC 瞬间的半开区间。计算组归属仍绑定目标班次 workDate 的既有日期区间。候选解析出现两个合法解时拒绝，不按行序选择。date 和 instant 不互相假定。
7. 整班边界在出差批准和后续排班／策略／组配置变更两侧都检查。已开始班不变；未来变更不得切穿已批准安排。无打卡但已开始的发布班次仍计入边界检查；禁止追溯改变历史。
8. business_trip 专用提交、同组织类型详情和最终批准发布安排，取消审批需显式扩充既有适配器及能力校验（现有批准后取消仅 leave），不得仅加 enum。并发重叠批准 DB 排他，失败不产生半成品安排。
9. 请假输入与目标班次上下文绑定，不能用浏览器 new Date(datetime-local) 解释。保留明确 minutes／整天／半天与既有假期类型的计量和最终批准扣减协议；不把多时区当作改计薪／扣假规则的授权。多日或多上下文单据只能依既有可表达的目标工作日结构处理，不能把全部分钟写到第一天；无法表示时说明冲突并要求受治理的分开申请。
10. 严格转换采用既有冻结链的 unique 首尾约束。出差重复本地时刻可确认偏移转 UTC，但不由此放宽班次端点消歧合同；禁止宽松转换异常后退 UTC。任务模块的另一套既有 DST 语义保持独立。
11. 建立并验证策略／员工／成员时间线／排班事实／父记录及请求的锁序，不能在已持有 parent/request 锁后临时加一个逆序策略锁。已有 W7 membership timeline→schedule facts 顺序保留。实际锁方案在接线前用真实 PostgreSQL 并发负例验证。
12. 新测试须覆盖跨日期变更线旧班续接、批准后反向冲突、原回执在策略读故障时回放、请假跨上下文拒绝、后层不恢复旧班次时区。D1 纯选择器通过不代表 D2/D3 全链路已成立。

实施顺序：D1 纯选择器／组织隔离配置 → D2 权威读取及冻结运行时 → D3 出差申请批准取消 → D4 关联单据输入、UI、真实合成链路、CI与独立终审。新管理员关联模式在确认“显示输入 vs 计算”范围后再接线；通用任务／待办改造不默认加入。
