## Public surface

`startCurrentAppCeremony(queryable, body, session, deps?)` accepts exactly `{ connectionId }` as a lowercase UUID. Success is `{ success: true, data: { url }, browserToken }` after commit. The URL is `https://login.dingtalk.com/oauth2/auth` with `client_id`, `redirect_uri`, `response_type=code`, `scope=openid`, `state`, and `prompt=consent`. `browserToken` is a separate 32-byte base64url value. The state and the browser token are hashed with SHA-256 before storage. The response has no cookie, secret, fingerprint, subject, or witness.

`completeCurrentAppCeremony(queryable, body, session, deps?)` accepts exactly `{ browserToken, code, state }`. Success is `{ success: true }` only. No evidence id is returned.

`deps.transaction` is the existing `AuthorizationInputTransactionRunner`. `deps.fetchFn` is not a request-body field and is not a profile injection. There is no injected exchange result.

The alias runs before request-shape checks, again before preflight, and as the first statement of every root. A throw from the alias becomes `session_rejected`. NUL and unpaired surrogates in the body are `unrepresentable_string` before shape. `DINGTALK_REDIRECT_URI` is read after those checks and before discover or challenge pre-read. A missing, blank, or untrimmed redirect is `redirect_unavailable` and spends no claim. The ceremony does not read `DINGTALK_CLIENT_ID`, `DINGTALK_CLIENT_SECRET`, `DINGTALK_CORP_ID`, or `DINGTALK_BASE_URL`.

Closed refusal codes, and no others: `request_shape`, `unrepresentable_string`, `production_unavailable`, `redirect_unavailable`, `corp_not_allowed`, `transport_config_unusable`, `provider_exchange_refused`, `subject_mismatch`, `material_mismatch`, `evidence_already_live`, `ceremony_exchange_spent`, `integration_inactive`, `session_rejected`, `privilege_refused`, `account_ineligible`, `membership_missing`, `scope_mismatch`, `capability_moved`, `binding_mismatch`, `epoch_mismatch`, `identity_missing`, `read_failed`, `ceremony_expired`. No SQL text, provider body, corp id, secret, open id, witness, or evidence id is copied into the body.

The outer catch reconstructs a refusal only from this module's `CurrentAppCeremonyRefusalError`, and only when `code` is one of the closed codes. ## F1 session witness

The alias authenticates only the existing WeakSet. After the kernel prefix has the user row `FOR UPDATE`, the root locks the domain tables, writes pins, and only then runs inline session SQL. That SQL is not a new session framework and does not call proof, registry, or revocation helpers.

Under the held user lock the ceremony executes `INSERT INTO user_session_revocations (user_id, revoked_after, updated_at) VALUES ($1, timestamptz '1970-01-01 00:00:00+00', clock_timestamp()) ON CONFLICT (user_id) DO NOTHING`, then `SELECT floor(extract(epoch FROM revoked_after) * 1000000)::text FOR SHARE`, then `SELECT` the real `user_sessions` row `FOR SHARE`. An existing watermark is not overwritten. The session row must be the matching user and sid, unrevoked, and unexpired by `expires_at > clock_timestamp()`. The token is valid only when `BigInt(tokenIssuedAt) * 1000000n > BigInt(watermarkUs)`, with `tokenIssuedAt` a safe positive integer. Absent relations, missing columns, and non-canonical microsecond text are `session_rejected`.

START stores `token_issued_at` and `watermark_us` as exact decimal text. CLAIM and FINISH re-read the current watermark and session and require those stored texts to be unchanged. They do not regenerate or update them. `created_at` and `expires_at` are immutable, and `expires_at` is exactly `created_at + interval '5 minutes'`, so a same-sid refresh does not extend the original challenge bound.

## F2 witness and lineage

The challenge stores `access_generation` and the full privilege witness (`privilege_class`, `privilege_reasons`, `privilege_witness`). One `assessSecurityActionPrivilege` read inside the locked root is the re-evaluation. The call uses this same transaction: it awaits `tx.query` and returns `{ rows, rowCount: result.rowCount ?? null }`. It does not cast the transaction, open another transaction, or call the pool. CLAIM and FINISH compare that current witness with the stored witness and do not write a new assessment back. Standard class and an empty reason array are required. Any other class or a non-empty reason array is `privilege_refused`. `PrivilegeInputsUnavailableError` is `read_failed`.

The evidence lineage trigger compares only actual S1 evidence columns: consumed challenge id, claim and consume timestamps, connection, org, identity text, subject, app scope, application revision, binding revision text, material fingerprint, capability revision text, slot snapshot, `created_by` against `target_user_id`, and assurance `self_authenticated`. The count must be exactly one. The lineage function source does not mention `access_generation` or `privilege_witness`. Other `producer_id` values pass through. S1 is not edited. Evidence rows do not gain those two columns.

## F3 challenge history

A new challenge insert must be unclaimed and unconsumed, with every immutable snapshot present, server `clock_timestamp()` within five seconds and not in the future, and expiry exactly five minutes later. Provider is `dingtalk`. Privilege class is `standard` and reasons are `[]`. Hashes are 64 lowercase hex. Revisions and the watermark are canonical decimals. `token_issued_at` is a positive decimal. The slot object has exactly `corpId`, `externalKey`, `localUserId`, `provider`, `providerOpenId`, and `providerUnionId`, with union a string or JSON null.

Exactly two forward updates exist: null claim to a claim timestamp within five seconds, consume still null; then unchanged claim to both consume columns within five seconds. `DELETE` and statement-level `TRUNCATE` both raise `55000`. There is no `xmin` column and no defense against a database owner disabling guards. A counterfeit that walks the legal SQL states and then inserts matching evidence is inside the trusted SQL boundary. Raw evidence for `current_app_target_ceremony` without that consumed challenge raises `55000` with message `admin grant target ceremony lineage refused`.

`up()` and `down()` require one caller-owned read committed transaction. Autocommit, repeatable read, and serializable have distinct refusal codes. The install schema is the first `current_schemas(false)` entry and is rejected when it is empty, `pg_*`, or `information_schema`. Dollar-quote tags are generated from the body. `up` refuses an already installed challenge table. It requires the S1 receiving tables, `directory_integrations`, `admin_grant_application_successor(revision text)`, and the three S3 admit triggers whose function is `admin_grant_receiving_admit` in that same schema. It does not require those receiving tables to be empty. `down` takes `ACCESS EXCLUSIVE` on the challenge and then on evidence, refuses when any challenge row exists or any evidence row has producer `current_app_target_ceremony`, and drops only the ceremony triggers, functions, and challenge table. Missing objects are `DOWN_PREREQUISITE`, not success. The migration text contains no `CASCADE`. Lock-timeout and deadlock errors are not swallowed. Timeouts come from `migration-timeouts.ts` and are restored on the ceremony's own refusal codes. S1, S2, and S3 objects stay. The migration does not call `transaction()` on a Kysely transaction.

## F4 subject

Exchange uses `exchangeCodeForUserAccessToken(code, explicitConfig, options)` and profile uses `fetchDingTalkCurrentUser(accessToken, options)`. Both receive `{ fetchFn: deps?.fetchFn, logUpstreamMessage: false }`. The explicit config is the locked stored `appKey`, the in-memory decrypted `appSecret`, the redirect, and the locked corp. A provider throw after the claim is `provider_exchange_refused`. The claim is not cleared and the provider call is not retried. No HTTP runs inside a transaction.

## Root order and epochs

Each root is `withAuthorizationInputTransaction` on the `CONSUME_CLASS_DECISION` shared plan from `discoverPrivilegeRolePlan(queryable, [session.userId], { sourceIntegrationIds: [connectionId] })`. Inside the root: alias, `revalidatePrivilegeRolePlan`, `requireIdentityRead([connectionId])`, then domain locks. Modes are chosen up front: integration, application pin, identity, binding pin, live evidence, and the challenge are `FOR UPDATE`; capability is `FOR SHARE`. There is no share-to-update upgrade. User rows are already `FOR UPDATE` before an identity-touching insert. The source freeze serializes two finishes of one source. A `23505` is `read_failed` for the whole transaction. There is no catch-and-continue.

Account gate, all `account_ineligible`: not deleted, not purged, `activation_status === 'activated'`, `is_active === true`, `local_password_set === true`, `must_change_password === false`, and a canonical `access_generation` text. Wrong types or missing deletion columns are `read_failed`. Membership is an active `user_orgs` row or `membership_missing`. A null session org is allowed. A non-null session org that differs from the integration org is `session_rejected`. The body cannot supply an org.

Integration must be `active` and `dingtalk`, or `integration_inactive`. Capability must be login-enabled, bound provider `dingtalk`, and bound org equal to the integration org, or `capability_moved`. Tenant and app scope must equal `scopeFromValues(corp_id, appKey)` with `appKey === appKey.trim()`, or `scope_mismatch`. `assertDingTalkCorpAllowed` maps `DingTalkCorpNotAllowedError` to `corp_not_allowed` with no corp id in the body.

Pins are written only at START, after the fresh-evidence check and before the watermark lock. An absent application pin is born at revision `1`. An equal fingerprint keeps the revision. A different fingerprint advances once through the installed `admin_grant_application_successor(revision text)` in `current_schema()`, then stores that returned text and the current fingerprint. JavaScript does not increment the revision. An absent binding pin is born at revision `1` with the six current slots. An existing binding pin that differs from the identity slot is `binding_mismatch` and is not rewritten. S2 remains the parent-change updater. Finish never refreshes a fingerprint and never adopts a new epoch.

`CURRENT_APP_EVIDENCE_FRESHNESS_SECONDS` is 300. Evidence uses one `clock_timestamp()` for `witnessed_at` and `fresh_until = witnessed_at + interval '300 seconds'`. That bound applies only to a new admin-grant issue and consume. It does not expire an admitted grant, login, refresh, session, or current token. The live evidence row stays at its existing R6 position. The read carries whether that row is fresh. It does not refuse inside the shared read. START refuses a fresh row with `evidence_already_live` before either pin write. CLAIM finishes session binding, challenge comparison, and the spent-state check before that fresh refusal. A claimed or consumed challenge is `ceremony_exchange_spent` even when the first finish left a fresh row. An unspent challenge with a fresh row is `evidence_already_live` and is not claimed. FINISH keeps the claimed-and-unconsumed check, then the profile checks, and refuses a conflicting fresh row before retirement, consume, or insert. A fresh row is not retired. A live row that is already expired stays in place at START. FINISH, in the same transaction, sets `revocation_generation = revocation_generation + 1` and `live_identity_id = NULL` on that one expired row. S1 writes `revoked_at`. The ceremony then stores the new evidence id on the challenge and inserts a new evidence row. The new id and witness are independent 32-byte base64url values. Assurance is `self_authenticated`. Producer `current_app_target_ceremony` is an identifier, not proof. `created_by` is the session user. Bigint binding and capability revisions are assigned from canonical decimal text. The new row does not replace a grant or a session. The old grant stays until an explicit later T4 revoke. T2 does not retarget it.

A changed application revision, binding revision, access generation, or integration org versus the captured challenge is `epoch_mismatch`. A changed capability revision, disabled login, or bound provider or org drift is `capability_moved`. A changed fingerprint at finish is `material_mismatch`. S2 steps an application pin when material, org, provider, or corp changes, and leaves the old fingerprint in place. S2 steps a binding pin when a slot column changes. An A-to-B-to-A round trip of material or of a slot therefore leaves a newer epoch, and finish refuses without adopting it. A profile-only round trip, an access-generation change that is restored, and a standard-to-standard privilege change that is restored can still match the captured witness. An add-only standard-to-high or witness drift is `privilege_refused` and is not written back. Name, `schedule_cron`, and profile-only parent updates do not step epochs. S3 first-birth triggers stay enabled. An application-pin birth and a later evidence insert each bump the parents with `schedule_cron = schedule_cron` and `profile = profile`. Those no-op assignments do not themselves step pin epochs.

Complete may pre-read `connection_id` by state hash so the plan names that source. Zero rows are `ceremony_expired`. The locked re-read is the authority for target user, session, browser hash, and expiry. A preview connection that differs from the locked row is `read_failed`. Browser, session, watermark, or issue-time mismatch is `session_rejected`. A second complete after claim or consume, while the locked challenge is still unexpired, is `ceremony_exchange_spent` and does not call the provider again. The same consumed challenge and the same evidence row remain. An expired locked challenge is `ceremony_expired` before the spent check. An immediate successful complete followed by the same complete, with current inputs unchanged, is the spent result above.

Finish rollback restores predecessor retirement and the new insert. The earlier claim stays spent. Start failure rolls the pin write and the challenge back together. Two completes of one challenge produce at most one claim and one provider call.

The ceremony writes only: the non-revoking epoch watermark insert, an application pin insert or successor update, a binding pin insert, the challenge insert and its two updates, the expired-evidence retirement, and the new evidence insert. It does not insert or update `user_sessions`, grants, `user_orgs`, or `user_external_identities`.
