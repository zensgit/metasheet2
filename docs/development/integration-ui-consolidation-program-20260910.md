### 7.2 本窗口最重要的一条：守卫接对了，出口却被下游改写

G05 的实现本身是干净的——门放在 `executeSendWebhook` 内、URL 必填检查之后、header/HMAC 组装与两阶段派发与任何 `fetchFn` 之前，一次调用覆盖两条分发路径；拒绝时不算 HMAC、不落地 `Authorization`、不占用出站意图凭据。37 条新用例每条拒绝都断言 `fetch` 被调用 0 次，5 项变异给出精确的判别计数。

**但三条互相独立的复核视角各自撞上了同一件事**：门后的 `fetchFn` init 只有 `{method, headers, body, signal}`，全文件 `redirect` 零命中，于是 undici 按默认值 `follow` 跟随重定向。门只判首跳——**任何能编辑自动化规则的人，只要让第一跳指向自己控制的公网主机并回一个 307，方法、正文、以及本 PR 自己新加的 `X-Webhook-Signature` 就会被原样重放进内网，https-only 也一并失效（会跟到 `http://`）**；legacy 路径每次重试重跑一遍，等于一次触发三发。两份设计/验证文档 `grep redirect` 零命中——既没修也没声明。

同仓里本就有两个不会被重定向绕过的现成先例：`guards/egress-dispatcher.ts:201` 的 `redirect:'manual'` + 逐跳重校验 + 重新 pin，以及 `multitable/webhook-pinned-fetch.ts:51-63` 的 `https.request`（node 原生不跟随）——按钮路由用的就是后者。也就是说，PR 注释里"规则路径与按钮路径是同一道控制"在唯一未被披露的那一维上恰好不成立。

这条值得单独记下来，因为它不是"守卫写错了"，而是**守卫写对了、接对了、测充分了，但它保护的那次出站在它之后被运行时改写成了另一次出站**。第一窗口总结的五类漏法（假件背书 / 守卫没接线 / 边界无强制 / 逐套绿整链红 / 触发与边界不同量）里没有这一类，现补第六类：**出口在守卫之后被下游重写**。

终审同时给了三条裁决：**https-only 保留**（明文内网、明文承载存储型 `Authorization` 是实打实的攻击面；放行 http-to-public 要靠 DNS 判定，而本 PR 自陈不做 resolve-then-pin，等于把最易被 rebinding 打穿的分支重新打开），条件是合并前做一次只读的存量 `http://` 规则盘点并写进发布说明；**日志记 `sheetId` 不越 values-free 线**（标识符不是值），真正的问题是注释承诺"能定位到出问题的规则"却没记 `ruleId`/`executionId`；**`ruleSnapshot` 的既有泄漏留单，但文案必须本波改**——两份文档写"由 `redactValue` 在落库时擦掉"属于假件背书，因为 `url` 不在 STRUCTURED_FIELDS 里，走 `redactString` 而其规则集既无通用 userinfo 也无通用 `token=`。

终审点名的"所有视角都没看的一条路径"是 `automation-executor.ts:4251` 与 `:4348` 的 `redactString(url)`：它们在**放行之后**每次投递失败都会打，就在本 PR 加固的同一个函数里，直接顶撞提交标题「日志不带 URL/凭据」。代码是基线既有，**但那句断言是本 PR 新作的**。

### 7.6 我自己的错误与订正（本窗口两条，均为基线算错）
