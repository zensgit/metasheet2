# 钉钉单账号登录身份受控修复

状态：Draft／HOLD。本轮修订以 PR #6693 当前 head 为准；原 head `6aa9a739998527c94665d5baf22da352d5c9a94f` 的 201 项记录不能替代修订验证，也不能证明旧实现可上线。

## 范围与身份依据

仅提供运维私有文件 CLI，修复现有账号的钉钉登录身份，不建立公开绑定接口。保留本地账号、角色、准入、组织成员权限、目录关联及审批记录；不切换企业、不代审批、不启用同步。另提供双人控制的受控重锚，只用于 release 无法结束的 applied 修复，见下文「受控重锚」。

verify 同时要求有效管理员及其密码、目标账号的非临时本地密码、新鲜的当前应用钉钉资料，以及当前应用下已经关联到目标账号的活动目录证据。企业、UnionID、OpenID 证据必须相容；另一用户占用、隐藏的第二个人、企业不符、仅 OpenID 相同而 UnionID 冲突均拒绝。不按昵称、邮箱相同或管理员知道密码推定同一人。证据不足的旧 E4 关联仍阻断，不能用本工具绕过完整 E4→Canary 交接。目录证据必须已存储 UnionID：目标账号任一活动的钉钉目录关联（任何应用，目录账号与集成均为活动）缺少 UnionID 时，verify 在调用钉钉之前即以 `REPAIR_DIRECTORY_UNION_ID_REQUIRED` 拒绝；apply 不会再得到这个码：已关联来源行的 UnionID 等判定列在 verify 之后改变（如 UnionID 被清空）会使快照摘要不同，apply 先以 `REPAIR_SNAPSHOT_CHANGED` 拒绝；仅 OpenID 相同（同应用亦然）不构成同人证据；UnionID 存在而目录 OpenID 为空的来源仍可作为证据。当前应用、同企业、同 UnionID 且仍关联到目标账号的活动钉钉来源必须恰好一个，多于一个以 `REPAIR_CANONICAL_SOURCE_REQUIRED` 拒绝。身份来源检查、journal 来源、release 允许列表与目录守卫只覆盖 `provider='dingtalk'` 的目录账号；本地目录账号保留在审批快照与摘要中，不受围栏约束。管理员不得是目标账号本人：verify 在校验任何密码、调用钉钉之前即以 `REPAIR_DUAL_CONTROL_REQUIRED` 拒绝，preview／apply 再次核对；rollback、release 及两种预览在校验管理员密码之前同样拒绝目标本人。数据库 CHECK 另外拒绝 actor_id 等于 user_id 的 journal 行，以及 rollback_actor_id 等于 user_id 的行。

证明使用平台 AES-GCM 材料加密，绑定管理员凭据摘要、目标权限／准入快照、登录应用范围与一次性 nonce，五分钟过期。只输出证明文件，不签发本地会话。预览仅输出打码线索和摘要，不构成本人确认的替代。

## 执行与互斥

preview、rollback-preview、release-preview、reanchor-request、reanchor-preview 为只读 REPEATABLE READ 事务，不加核心表写锁、不递增 generation、不创建会话，也不写审计记录（零写入测试固定）；审计行只由 apply、reanchor、rollback、release 写入（reanchor-request 只写请求文件）。权限快照包含 users、角色、角色权限、直接权限、组织、namespace admissions、外部授权、目录关联、身份键和来源。仅忽略 created_at、updated_at、last_login_at 这三类元数据。

写事务首句固定 READ COMMITTED，再取得身份维护互斥、核心表 SHARE ROW EXCLUSIVE 锁及 canonical 用户锁。这三步不使用 NOWAIT，每次加锁都在 lock_timeout（五秒）内有界等待；lock_timeout 按单次加锁计时，核心表一步要取 13 把锁，有多个持有者时等待会累加（实测两个持有者时约 9 秒才拒绝），整条语句最多到 statement_timeout（三十秒）为止。等待超过 deadlock_timeout 时，冲突的 autovacuum／autoanalyze 会自行取消。其他持有者（含防回卷 vacuum）使锁阶段的某次加锁超过五秒、出现锁环，或身份维护互斥等待超过五秒，都拒绝为 `REPAIR_LOCK_BUSY`，不写任何行，可在确认无长事务后重试；lock_timeout 按单次加锁计时，statement_timeout 按单条语句计时，事务没有总时限：锁阶段的互斥、核心表锁和用户行锁（每个用户一条）语句各自受这两个限制，之后每条语句各自不超过三十秒。锁阶段内单条语句（如 13 张表的 LOCK TABLE）累计等待达到三十秒时，服务端以 57014 取消，同样映射为 `REPAIR_LOCK_BUSY`，不写任何行；锁阶段之后的语句被服务端以 57014 取消时，CLI 打印 `REPAIR_STATEMENT_TIMEOUT`，事务已回滚。`REPAIR_LOCK_BUSY`（退出码 75）只覆盖锁阶段，即身份维护互斥、13 张核心表的 LOCK TABLE 和用户行锁。锁阶段之后的语句同样受五秒 lock_timeout 限制：它们在 13 张表以外的表（如 user_session_revocations、user_sessions、multitable_api_tokens、audit_logs）的行上等锁超过五秒（55P03），或成为死锁牺牲者（40P01）时，CLI 打印 `DINGTALK_LOGIN_REPAIR_REFUSED`，退出码 1，事务已回滚，不写任何行。维护 CLI 进程自行要求客户端读超时不低于 max(45000, DB_STATEMENT_TIMEOUT+15000) 毫秒：未设置时自动采用该值；显式低于该值或无法解析（DB_STATEMENT_TIMEOUT 无法解析时同样）以 `REPAIR_CLIENT_TIMEOUT_TOO_LOW` 拒绝，且在建立连接池之前拒绝，不连接数据库；连接池建立后再核对其实际持有的值，不足同样拒绝。客户端读超时同时不得超过 2147483647 毫秒（2^31−1，Node 定时器可设的最大延迟；更大的值会被 Node 当作 1 毫秒，查询几乎立即以读超时结束，每次运行都成为「结果未知」）：显式值超过该上限，或 DB_STATEMENT_TIMEOUT 大到下限超过该上限（例如 PostgreSQL 自身的最大值 2147483647），以 `REPAIR_CLIENT_TIMEOUT_TOO_HIGH` 拒绝，同样在建立连接池之前拒绝、不连接数据库；连接池建立后的核对也检查该上限。应用进程参数不变。因此服务端超时先于客户端超时到达；客户端读超时（`REPAIR_CLIENT_TIMEOUT`，退出码 69）表示结果未知，须先读 journal。按另一顺序取这些表的并发写入（目录同步、角色或权限管理写入，以及登录写入，含钉钉 OAuth 登录：它锁用户行并写身份行，缺少 corpId 时还锁整张身份表）可能反过来被选为死锁牺牲者而中止，因此维护窗口内须暂停目录同步和角色、权限管理；期间个别登录也可能因此失败，需要重试。apply 排队期间，需要写这些表的请求会跟着等待，例如其他用户的登录：只有一个持有者时约五秒，多个持有者时更久，最长到 apply 被拒绝为止。令牌校验本身只读，不排队；只有在需要为该用户首次补齐考勤自助角色、写入 user_roles 时，才会像登录一样等待。与 applied handover 双向排斥；安全解绑也不能抹掉日志中原来源的互斥依据。不修改 handover 的产品摘要规则。reanchor 的写事务与 apply、rollback、release 使用同一锁阶段、超时与错误映射，另锁定两名管理员的用户行。

apply 需精确证明摘要及 `confirm=apply`。身份旧值加密保存；写产品审计，记录的管理员为 verify 时校验密码的管理员（apply 本身不另行认证执行者）。reanchor 的两名管理员各自在本步骤用本地密码认证：第一人在 reanchor-request，第二人在 reanchor-preview 与 reanchor；journal 与审计记录两人。撤销目标已存在的 JWT 会话、session registry 记录与多维表 API token，递增 generation，不倒退。OAuth／免登认证结果携带在用户锁内取得的 generation，登记 session 时重新锁定并核对；API token 创建／轮换也复核请求认证时的 generation。旧 refresh 不得重新激活已撤销 sid，无 sid 的 refresh 同样复核 generation。切换组织（POST /api/auth/session-org）重新签发会话时同样携带请求认证时的 generation，版本已变则返回 409 `authentication_changed`，不登记会话。强制改密（POST /api/auth/password/change）重新签发会话时也携带请求认证时的 generation；版本已变则返回 409 `authentication_changed`，提示用新密码重新登录，不登记会话，已写入的新密码和会话撤销保留。

携带 generation 的签发（refresh、切换组织、强制改密、OAuth／免登登记会话，以及 API token 创建／轮换）在登记时对该用户的 users 行取共享锁，所以会排在任何持有该行锁的事务之后，例如目录同步的本地应用事务（整个事务期间锁住该集成的全部候选用户）和管理员访问图写入（绑定、解绑、角色与权限管理、回收站与撤权）。持锁时间短时只是变慢；等待超过 statement_timeout（默认三十秒）时签发失败：refresh 返回 401，切换组织返回 503，强制改密返回 500（新密码与会话撤销已经提交），API token 创建返回 500，OAuth 登录同样失败。不带 generation 的签发（密码登录、激活、开发令牌）登记会话时不锁 users 行，与本 PR 之前相同；密码登录仍在更新最后登录时间时等待该行锁，这是 main 上已有的行为，超时被吞掉，登录照常成功。

这不禁止修复完成后的有效新登录，也不承诺取消所有已经执行的业务请求。现有无 sid JWT 在应用节点时钟超前于数据库时，仍受既有时间水位机制限制；本轮没有修改全局 JWT 合约。生产必须完成迁移并验证时钟与会话机制，不能把本地结果称为全部凭据系统的安全证明。开发模式 RBAC_TOKEN_TRUST 不提供数据库 generation 时，API token 签发会拒绝；非 production 的信任声明模式下，用户的 generation 一旦变动，切换组织也会返回 409。未提供 generation、非 production 且用户确实不存在时保留原虚拟用户会话兼容；携带 generation 的 OAuth／refresh 不可走此分支，遇 schema 错误也拒绝。原无版本调用的缺表 synthetic 兼容未改，因此仍要求完整迁移。目标库在部署前必须已有 `users.access_generation` 列（迁移 zzzz20260724170000 添加）：`SELECT 1 FROM information_schema.columns WHERE table_schema=current_schema() AND table_name='users' AND column_name='access_generation'` 必须返回一行；缺列时携带 generation 的签发路径会出错，不会退回无版本行为。撤销不会断开已经建立的 WebSocket／Yjs 连接，这是平台既有行为，本轮未改。

## 防覆盖、回退与 release

活动记录严格固定企业、UnionID、OpenID、external key 及身份归属。只有新鲜 OAuth 在同一用户锁和事务内验证同企业／同 UnionID／同应用后，才可推进 OpenID pin；目录旧 OpenID 不能自行覆盖。目录 OpenID 为空的正常成员继续使用同人登录身份补全。第二目录来源关联由数据库守卫拒绝。

rollback-preview 显示当前摘要及变动分段。后续登录、角色补齐、资料或合法权限变更不再让恢复永久无出口，但必须重新审阅和批准当前恢复摘要。rollback 只恢复本次身份旧值，保留之后的角色、准入、密码、启用标记等合法变更。以下情况拒绝且不写任何行：未解决撤权（`REPAIR_REVOCATION_UNRESOLVED`）；其他用户持有旧身份（`REPAIR_OLD_IDENTITY_CONFLICT`）；旧身份对应的钉钉目录行（同企业，同 UnionID 或同 OpenID，任何应用）关联或提示给其他本地用户（`REPAIR_DIRECTORY_OWNER_CONFLICT`，pending 提示也算占用，与 verify、release、重锚的占用定义相同）；applied handover。rollback-preview 不解密旧身份，后两项只在执行时检查，预览成功不代表执行不会以这两个码拒绝。执行后再次撤销目标当前会话和 API token。恢复不能复活已撤销授权。

release 不恢复旧身份，也不恢复权限。release 分两种模式，两者都从 journal 记录的来源 ID 重新读取并核实真实目录账号与集成（历史 ID 本身不是证据）：被核实的是 apply 时记录为 `canonical_account_id` 的那一行（apply 预览中显示为 canonicalAccountId），其余 journal 来源 ID 只重新读取，用于发现被其他用户占用的情形。可登录用户（授权开启、钉钉身份存在、账号可登录）走 canonical 模式：必须恰好有一个当前应用、同企业、同 UnionID、活动且仍关联到该用户的钉钉来源，否则 `REPAIR_CANONICAL_SOURCE_REQUIRED`（可 rollback、重绑原账号或撤权后终结）。已撤权用户（授权关闭、身份已删、账号停用／回收站／未激活）走终结模式：只接受恰好一个同企业、同应用、同 UnionID 的原来源（来源 inactive 允许，不恢复其活跃状态），否则 `REPAIR_HISTORICAL_SOURCE_UNVERIFIED`；终结不重新启用授权、不恢复身份、不恢复关联、用户状态、权限、组织成员或旧会话，撤权状态与证据保留。两种模式都拒绝：登录应用或企业已变（`REPAIR_LOGIN_SCOPE_CHANGED`）、同企业同 UnionID 的目录行被其他用户占用（`REPAIR_DIRECTORY_OWNER_CONFLICT`）、其他用户持有该人的钉钉身份（`REPAIR_IDENTITY_CONFLICT`）、用户名下仍有名单外的钉钉关联（`REPAIR_SOURCE_OUTSIDE_ALLOWLIST`，含 inactive 旧关联，须先安全解绑；只有被解绑的目录行按 UnionID、OpenID 或 external key 与该用户的钉钉身份相符时，解绑才删除该身份并使 release 走终结模式，否则身份保留，release 仍按上述条件选择模式；解绑时一并关闭钉钉授权同样使 release 走终结模式）。拒绝时不写任何行。**release 仅解除身份 pin，目录来源约束继续生效。** released_account_ids 恒为恰好一个账户 ID，数据库 CHECK 拒绝空数组、NULL 与含 NULL 元素的数组；历史来源 IDs 保持不变。release-preview 输出 mode、releasedAccountIds、linkedDingTalkAccountIds、localLinkCount，并把当前登录 scope、最终名单与重新读取的来源行绑定进摘要，执行时在锁内重新计算：变化使某项 release 检查不成立时，以该检查自己的码拒绝（如 `REPAIR_LOGIN_SCOPE_CHANGED`、`REPAIR_DIRECTORY_OWNER_CONFLICT`、`REPAIR_HISTORICAL_SOURCE_UNVERIFIED`、`REPAIR_SOURCE_OUTSIDE_ALLOWLIST`）；各项检查仍成立、但绑定进摘要的计划或快照变了时，拒绝为 `REPAIR_RECOVERY_SNAPSHOT_CHANGED`。登录应用已变（同一企业）、apply 记录的 canonical 来源不再是当前应用的同人来源、或 journal 中另一个人的目录行已归属其他本地用户时，按下文「受控重锚」处理；企业变更、找不到当前应用下此人的目录行、此人的目录行或钉钉身份归属其他本地用户时，重锚同样拒绝（见「受控重锚」末段）。新来源接入、跨企业或解除此持久约束不在本轮范围，须另行设计和批准。正常受控交接移动原稳定账户 ID，不创建第二个账户。

此约束不依赖没有实际消费者的 connectionDisabled 字段，也不把 status=inactive 或 sync_enabled=false 当作手动同步／在途同步已停止的证明。具有完整有效配置、能够成功同步的旧来源，在 release 后尝试第二关联仍由真实数据库守卫拒绝；其同步批次可能失败，禁止自动解除守卫。

## 受控重锚

受控重锚（reanchor）只处理 release 无法结束的 applied 修复，且只在同一企业、同一个人之内进行。适用三种情况：登录应用已变（同一企业；release 为 `REPAIR_LOGIN_SCOPE_CHANGED`，网页 OAuth 登录返回 409 `repair_identity_mismatch`；免登（容器）登录不带 OpenID，不经过 pin 的登录应用核对，按固定的 UnionID 仍登录目标账号，也不推进 pin，该路由默认关闭（DINGTALK_CONTAINER_LOGIN_ENABLED））；apply 记录的 canonical 来源已不存在，或不再是当前应用、同企业、同 UnionID 的钉钉来源（release 为 `REPAIR_HISTORICAL_SOURCE_UNVERIFIED` 或 `REPAIR_CANONICAL_SOURCE_REQUIRED`）；journal 来源中另一个人的目录行已关联或提示给其他本地用户（release 为 `REPAIR_DIRECTORY_OWNER_CONFLICT`）。其余情况拒绝为 `REPAIR_REANCHOR_NOT_NEEDED`，应改用 release、rollback、重新绑定或解绑。

不换企业，不换人：登录企业与修复确认的企业不同即 `REPAIR_REANCHOR_CORP_CHANGED`。新记录逐字沿用原记录确认的身份（企业、UnionID、OpenID、external key）和回退用的旧身份密文，由数据库从原记录复制并在提交时核对。重锚不写钉钉身份；新应用的 OpenID 仍由之后真实的钉钉登录在用户锁内推进（见「防覆盖、回退与 release」）。仅 OpenID 相同（包括其他应用）只会导致拒绝，不作为同人依据。

目录证据：新的 canonical 来源必须是当前登录应用、同企业、已存储同一 UnionID、未关联或提示给其他本地用户的钉钉目录行，且恰好一个；原 canonical 来源仍符合时继续沿用。可登录用户（授权开启、身份存在、账号可登录）要求该行活动、集成活动且已关联到该用户，与 verify 的目录证据相同；已撤权用户不要求关联或活动，有活动行时只取活动行。找不到为 `REPAIR_PERSON_NOT_PROVEN`，多于一个为 `REPAIR_CANONICAL_SOURCE_REQUIRED`。同企业同 UnionID（或同 OpenID）的目录行只要关联或提示给其他本地用户即 `REPAIR_DIRECTORY_OWNER_CONFLICT`，其他用户持有此人的钉钉身份即 `REPAIR_IDENTITY_CONFLICT`；这两项先于 `REPAIR_REANCHOR_NOT_NEEDED` 检查。目标账号所有活动的钉钉关联（任何应用）同样须已存储 UnionID 且为同一人。

扫码：可登录用户在登录应用变化后重锚，须由本人用当前应用扫码，授权码由第一名管理员写入 reanchor-request；扫码得到的 UnionID 必须与修复确认的一致，否则 `REPAIR_REANCHOR_PERSON_MISMATCH`；未提供为 `REPAIR_REANCHOR_SCAN_REQUIRED`；扫码 OpenID 已在其他用户的目录行或钉钉身份上时拒绝。扫码只作核对，不写入。已撤权用户和登录应用未变的重锚不需要扫码，提供了也照样核对。不要求目标账号的本地密码：重锚不改变登录身份，也不能换人。已撤权用户在换应用后不扫码重锚，不能证明新应用下 UnionID 不变：若新应用属于另一开发者，之后重新开启授权时钉钉登录仍会失败，此时可在账号恢复可登录后 rollback。

双人控制：需要两名不同的有效管理员，均使用本人本地密码，均不得是目标账号。第一人运行 reanchor-request，给出原记录 ID、本人密码和第二人的用户 ID（approverId），需要扫码时另给授权码；程序校验第一人密码，确认第二人是有效管理员，计算重锚计划，输出十分钟内有效的加密请求文件，绑定第一人凭据摘要、第二人 ID、当前登录 scope、一次性 nonce 与计划摘要，并在标准输出显示计划和摘要。只有请求中指定的第二人可以运行 reanchor-preview 核对同一计划和摘要，再运行 reanchor 给出该摘要和 confirm=reanchor。执行时在锁内重新计算计划和摘要，重新核对第一人的凭据摘要（密码或 generation 变化即 `REPAIR_OPERATOR_CHANGED`；第一人被停用、未激活、须改密或失去管理员身份即 `REPAIR_OPERATOR_REQUIRED`），并再次校验第二人的密码。同一人担任两步、由指定人以外的管理员执行、或任一人是目标账号，均为 `REPAIR_DUAL_CONTROL_REQUIRED`，数据库 CHECK 同样拒绝；给出的摘要与请求不符为 `REPAIR_APPROVAL_REQUIRED`，状态已变为 `REPAIR_RECOVERY_SNAPSHOT_CHANGED`；请求过期、scope 变化或用途不符为 `REPAIR_PROOF_INVALID`。第二人临时不能到场时，由第一人重新发起请求并指定另一人；需要扫码时须重新扫码。能直接执行 SQL 或持有加密材料的人不受这一控制约束，与 verify 证明相同；一人持有两个管理员账号属于组织管理问题。

写入：同一事务内，原记录改为 superseded（记录执行人和时间），新增一条 applied 记录：supersedes_id 指向原记录，actor_id 为第一人，approver_id 为第二人，login_client_id 为当前应用，canonical 为新来源；来源为该用户当前关联的钉钉行、新 canonical 行，以及原来源中仍属此人且未被他人关联的行。不再属于此人或已归属他人的原来源不再进入目录守卫，其所在集成也不再因本修复被交接互斥（该用户仍有关联的集成照旧互斥）。随后递增 access_generation，撤销目标会话、session registry 与多维表 API token，写两条审计（原记录 superseded、新记录 reanchor，均记录两名管理员、原因、模式与是否扫码）。不写身份、授权、关联、目录账号、组织成员、角色、权限、准入、撤权证据或用户标记。任何拒绝都不写行。数据库另外保证：只有 applied 记录可以改为 superseded，提交时必须恰好有一条同用户、同身份、同旧身份密文、来源最多只多出其 canonical 行的 applied 后继；后继只能接续已 superseded 的记录，一条记录最多被一个后继接续。

重锚之后：身份 pin、目录守卫、登录 pin 检查与受控交接互斥都以新记录为准；release、rollback 用新记录 ID，原记录 ID 返回 `REPAIR_NOT_ACTIVE`。rollback 恢复整条修复链最初 apply 之前的身份（新记录复制了原记录的旧身份密文），之后不再有 pin，也不再有本条修复链的目录约束，与原 rollback 相同；它不回到重锚之前。例外：该用户此前另有已 release 的记录时，目录守卫在没有 applied 记录时取最新一条 released 记录，该记录的 released_account_ids 在之后的 apply、rollback 之后继续约束目录关联，rollback 不解除它。release 按原规则核实新 canonical：可登录用户走 canonical 模式，已撤权用户走终结模式，之后重新绑定与授权按终结后的流程。已 release、rollback 或 superseded 的记录不提供重锚。

换登录应用的顺序：（一）切换之前，先 release 能 release 的修复（release 后不再有 pin，用户用新应用登录时按 UnionID 照常更新身份），不再需要的修复先 rollback；仍停在 applied 的才需要重锚。（二）原地修改持有 canonical 来源的现有钉钉集成的 appKey／appSecret，不要新建或删除集成：同一企业的同一人只能有一条钉钉目录行（目录账号唯一键为企业加 UnionID），旧集成仍在时，新集成同步此人会冲突失败；修复 applied 或 released 期间，新集成按身份关联此人也会被目录守卫拒绝，整批同步失败。（三）切换后完成一次同步，使该行的 UnionID 来自新应用。（四）切换部署的 DINGTALK_CLIENT_ID。（五）按上文执行双人重锚。（六）用户用新应用登录成功后，按需 release。若原目录行已被删除且用户仍持有钉钉身份，新集成的同步会被目录守卫阻断，重锚无行可锚：须先移除该身份（用户本人在产品中解除钉钉绑定，或清除账号），使下一次同步建出未关联的目录行，再按终结模式重锚并 release，最后用产品绑定和授权恢复登录。

本版不支持、journal 停在 applied 的情形：企业变更；找不到当前应用下此人的目录行（人员已离开企业、目录行已删除且未重建、该行已改为另一个人或缺少 UnionID、新应用属于另一开发者）；此人已改用另一个本地账号。可登录用户仍可 rollback。已撤权用户的此类 journal 继续固定其身份、阻止该账号的新修复，并在相关集成仍存在时阻止其来源集成的受控交接。此人确已改用另一账号时，可用现有产品操作退出：先从另一账号解绑该目录行（会删除其钉钉身份），再对旧账号 release（登录应用已变时先重锚），最后把该行连同授权绑定回另一账号；其间另一账号暂时不能钉钉登录。

## 运维入口与备份

以下仅说明接口，不授权真实执行：

```sh
cd packages/core-backend
pnpm --silent ops:dingtalk-login-repair verify /restricted/verify.json /restricted/proof.json
pnpm --silent ops:dingtalk-login-repair preview /restricted/proof.json
pnpm --silent ops:dingtalk-login-repair apply /restricted/apply.json
pnpm --silent ops:dingtalk-login-repair rollback-preview /restricted/recovery.json
pnpm --silent ops:dingtalk-login-repair rollback /restricted/rollback.json
pnpm --silent ops:dingtalk-login-repair release-preview /restricted/recovery.json
pnpm --silent ops:dingtalk-login-repair release /restricted/release.json
pnpm --silent ops:dingtalk-login-repair reanchor-request /restricted/reanchor-request.json /restricted/reanchor.request.json
pnpm --silent ops:dingtalk-login-repair reanchor-preview /restricted/reanchor-preview.json
pnpm --silent ops:dingtalk-login-repair reanchor /restricted/reanchor.json
```

这些命令须从仓库根目录先进入 `packages/core-backend` 再运行：脚本 `ops:dingtalk-login-repair` 只在该包的 package.json 中定义。留在仓库根目录也可以写成 `pnpm --silent --filter @metasheet/core-backend ops:dingtalk-login-repair …`。在仓库根目录直接运行上面的命令时，pnpm 找不到脚本，以退出码 254 结束，stdout 与 stderr 都为空；254 不在下文的退出码之列，表示 CLI 根本没有运行。

verify 输入：userId/password/code/actorId/actorPassword。preview：proof。apply：proof/digest/confirm。两种 recovery preview：id/actorId/actorPassword；执行 rollback／release 再增加 digest/confirm。reanchor-request：id/actorId/actorPassword/approverId（第一名管理员；approverId 为第二名管理员的用户 ID），可登录用户在登录应用变化后另加 code；输出请求文件 0600 且不覆盖，内容只有 request。reanchor-preview：request/actorId/actorPassword（第二名管理员）。reanchor：request/actorId/actorPassword/digest/confirm（第二名管理员，confirm 为 reanchor）。输入必须为私有常规文件，无组／其他用户权限，最多 64 KiB，严格字段集；证明输出 0600 且不覆盖。凭据、授权码和证明不得进入命令参数、聊天或 PR。失败只打印固定拒绝码集合中的一个（模块码与 CLI 码清单见 `dingtalk-identity-repair-codes.ts`），不打印错误文本、堆栈、SQL 或标识。下述输出流保证适用于上面在 `packages/core-backend` 下的 `pnpm --silent ops:dingtalk-login-repair …` 调用、仓库根目录的 `--filter` 写法（`--silent` 必须写在脚本名之前；写在之后会作为 CLI 参数传入，被拒绝为 `REPAIR_INPUT_INVALID`）以及直接调用 `tsx scripts/dingtalk-login-repair.ts …`；不带 `--silent` 的 `pnpm` 会在 stdout 另外打印自己的脚本横幅，失败时再打印 ELIFECYCLE 行，stdout 便不再是可解析的 JSON（退出码与 stderr 不变）。CLI 进程在加载任何会写日志的模块之前接管标准输出与标准错误：应用日志（含慢查询、ROLLBACK 失败与连接池配置警告）、console 与库输出一律丢弃，stdout 只含成功时的一行 JSON，stderr 只含一个拒绝码；连接在等待中被终止等未捕获异常或未处理拒绝同样按上述分类只打印一个码（读超时为 `REPAIR_CLIENT_TIMEOUT`，其余为 `DINGTALK_LOGIN_REPAIR_REFUSED`），之后按下文「非零退出之后」确认是否已提交。CLI 不提供调试输出，需要诊断时由 DBA 查看数据库日志与 `pg_stat_activity`。`REPAIR_LOCK_BUSY` 退出码 75，`REPAIR_CLIENT_TIMEOUT` 退出码 69，其余 1；输入文件、字段或权限问题为 `REPAIR_INPUT_INVALID`；成功输出 JSON 含 clientQueryTimeoutMs。

执行 apply、rollback、release、reanchor 之前：（一）定时同步关闭不等于没有同步在跑：确认该企业所有钉钉集成在 `directory_sync_runs` 中没有 `status='running'` 的行，且 `pg_stat_activity` 中没有处于事务中的同步会话；（二）窗口内暂停手动同步、管理员绑定／解绑以及角色、权限和组织成员管理；（三）执行前立即重新运行对应的 preview；（四）CLI 进程不设置 DB_QUERY_TIMEOUT（由 CLI 预设下限），或显式设置为不低于该下限的值，显式更低的值以 `REPAIR_CLIENT_TIMEOUT_TOO_LOW` 拒绝且不连接数据库；显式值不得超过 2147483647，DB_STATEMENT_TIMEOUT 不得超过 2147468647（使下限不超过同一上限），否则以 `REPAIR_CLIENT_TIMEOUT_TOO_HIGH` 拒绝且不连接数据库；（五）锁阶段内登录会排队（每个持有者约五秒），并发写入可能被选为死锁牺牲者（见上文执行与互斥）；（六）确认当月 audit_logs 分区存在：`SELECT to_regclass('audit_logs_' || to_char(date_trunc('month', now()), 'YYYY_MM'))` 不为空。audit_logs 按月分区且没有默认分区，缺当月分区时审计写入失败，整笔事务回滚。

非零退出之后：（一）先确认是否已提交。rollback／release 重新运行同一 preview：返回 `REPAIR_NOT_ACTIVE` 表示已提交；仍能预览表示未提交（没有其他变化时摘要与之前相同）；以其他拒绝码结束时由 DBA 读取 journal。reanchor 由第二人用同一请求文件重新运行 reanchor-preview：返回 `REPAIR_NOT_ACTIVE` 表示已提交，得到同一摘要表示已回滚；请求过期（`REPAIR_PROOF_INVALID`）后由 DBA 读取 journal 及两个 id 最新的 audit_logs 行。apply 用同一证明重新运行 preview：仍然成功表示 apply 未提交；返回 `REPAIR_SNAPSHOT_CHANGED` 不能单独说明已提交：apply 改变了身份会得到这个码（此检查先于 `REPAIR_ALREADY_ACTIVE`），快照覆盖的表在期间的任何其他变化也会得到这个码（如令牌校验时首次补齐考勤自助角色写入 user_roles），因此得到该码、其他拒绝码或证明已过期（`REPAIR_PROOF_INVALID`）时，都由 DBA 读取 journal（`SELECT id,state,supersedes_id,actor_id,approver_id,released_account_ids FROM dingtalk_login_repairs WHERE user_id=$1 ORDER BY created_at DESC`）及该 id 最新的 audit_logs 行。（二）退出码 75 时由 DBA 在 `pg_stat_activity`、`pg_locks` 中查找 `hashtext('directory:identity-maintenance')` 互斥或 13 张核心表的持有者；等待约五秒后以退出码 1、`DINGTALK_LOGIN_REPAIR_REFUSED` 结束时，同样查找持有者，范围扩大到 13 张表以外的表（如 user_session_revocations、user_sessions、multitable_api_tokens、audit_logs）上该用户相关行的锁。（三）重新运行对应 preview 并批准新摘要。（四）只手动重试一次，不循环重试；CLI 不自动重试。（五）退出码 69 时，在确认 journal 状态之前不做任何操作。暂停真实同步、修改在线参数和执行修复仍是三项独立审批。

真实窗口前必须另批：完整迁移台账、专用加密材料及可恢复配置／数据库备份、当前身份与目录证据、审批在途依赖、session/API token 影响、来源约束后续处理和维护窗口。新加密字段 `dingtalk_login_repairs.before_identity` 已登记普查和启动探测，单字段最多抽取二十行，不代表全库普查。journal 的 `expected_identity`（修复确认的企业、UnionID、OpenID、external key）以明文 jsonb 保存，修复 applied 期间每次网页 OAuth 登录推进 pin 时改写，账号清除（purge）后仍保留；`before_identity`（修复前身份）以密文保存，同样保留。换材料而不迁移密文会使恢复拒绝；必须保留原材料与密文备份。非空修复历史不允许 migration down，不能通过删除历史或直接拆守卫回滚。迁移在合并前再次原地改写（CHECK、目录守卫函数、superseded 状态、supersedes_id 与 approver_id 列及修复链守卫）：跑过 `f51b92d2d6` 或更早版本（含 `2ea948c0f7`、`cbd01a7101`）的开发库须重建：本轮新增两条 CHECK（actor_id、rollback_actor_id 均不得等于 user_id）。

## 本版限制

- 不支持目录缺少 UnionID 的修复：verify 在调用钉钉之前拒绝，须先补齐目录 UnionID。
- 受控重锚只在同一企业、同一 UnionID 内进行，且只能锚定已存在、未被他人关联的当前应用目录行；企业变更、UnionID 变化、此人已改用另一个本地账号或找不到此人的目录行时，journal 停在 applied（可登录用户仍可 rollback）。已 release 的记录不提供重锚，其目录来源约束保持不变。
- 同一用户在当前应用下有两个活动的同人来源时，verify 拒绝（`REPAIR_CANONICAL_SOURCE_REQUIRED`），须先解绑其中一个。
- release 前必须解绑名单外的钉钉关联（任何应用，活动或 inactive）。只有被解绑的目录行按 UnionID、OpenID 或 external key 与该用户的钉钉身份相符时，解绑才删除该身份，即撤销其钉钉登录，release 随之走终结模式；不相符的行（如 UnionID 与 OpenID 均为空、external key 也不同）解绑后身份保留，授权仍开启、账号可登录时 release 仍走 canonical 模式。
