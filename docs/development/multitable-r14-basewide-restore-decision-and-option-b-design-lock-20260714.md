## §3 The >5k / base-wide async leg (Option-B operation-level restore) — the hybrid's second half
**Model (v1 semantics, stated without contradiction):** a persistent restore operation with a deterministic plan, executed in chunks under a write fence. **v1 is defined as: observable, recoverable, explicit-partial-progress.** Reads during `applying` see the mid-apply state (write-fenced, progress-visible via the operation row) — there is **no** "never observable half-restored" claim and **no** one-shot visibility flip; those two promises plus explicit-partial cannot coexist, and v1 keeps the honest pair. **State machine:** `planning → fencing → applying ⇄ paused_retryable → done | abandoned_partial`. Failure/crash ⇒ `paused_retryable` with **write protection retained**; permanent abandonment (`abandoned_partial`) is exclusively an **owner-explicit accept-partial action** — an ordinary failure never auto-releases protection.

1. **`meta_restore_operations`** (new table): `id` (operation-id, idempotency key), `base_id`, `as_of` (T), `state` — the **exact same enum as the model's state machine**: `planning | fencing | applying | paused_retryable | done | abandoned_partial` (NO `fenced`/`finalizing`/`failed` — those drifted enums would reintroduce the 'ordinary failure releases protection' ambiguity; a crash/failure sets `paused_retryable` with protection retained, and only an owner-explicit accept-partial reaches `abandoned_partial`), `plan` (jsonb: per-sheet deterministic revert/delete/resurrect sets + per-sheet precheck verdicts + scope hashes), `journal` (jsonb: per-chunk completion cursor), `actor_id`, timestamps. One active operation per base (partial unique on `base_id` where state active) — concurrent restores refuse.
2. **Plan phase:** per sheet — run the W0-1 precheck (**hard dependency:** the #4262 v3.1 correction lock must be landed + trusted; a base-wide restore over an untrusted chain multiplies the healed-gap blast radius by N sheets), compute the deterministic sets via `reconstructRecordsAtT`, record scope hashes. Preview = the aggregated plan (per-sheet counts + samples), signed like existing previews (CAS/typed-confirm house pattern).
3. **Fence phase:** acquire the **shared per-sheet writer fence** for every sheet in the base — the *same* primitive as #4262 v3.2 §3 (`acquireAutoNumberSheetWriteLock`, under the same-txn/same-connection contract), acquired in **deterministic sheet-id order** (no deadlock). Advisory locks are the fast-path serializer only — a session advisory lock **vanishes if the coordinator's connection drops**, so it can never be the sole protection. The authoritative write-block is the **durable active-operation row**: every sheet writer checks, **inside its own transaction**, for an active `meta_restore_operations` row covering its sheet and refuses with `RESTORE_IN_PROGRESS` (409 + operation id). Per chunk, a **transaction-scoped advisory barrier** (acquired+released within the chunk txn) serializes ordering; there is **no** long-lived coordinator session lock (§6.1). Between a worker crash and its resume the durable-row check alone keeps writes refused (no reopened window). Protection releases only on `done` or owner-accepted `abandoned_partial` — never on ordinary failure or a dropped connection.
   **TOCTOU close (plan→apply):** after **all** sheet protections are in place (durable row committed + advisory locks held) and **before the first mutation**, re-run the W0 precheck per sheet and recompute/compare every plan scope hash; any mismatch ⇒ `paused_retryable` (re-plan required), zero mutations. Finalize's re-verify is retained but is no longer the first check.
4. **Apply phase:** chunked (e.g. 500 records/chunk), each chunk one txn, journal cursor updated per chunk — crash/failure ⇒ **resume-forward from the journal** (re-run is idempotent: plan is deterministic, applied chunks are recorded; no compensation/rollback machinery — the fence guarantees no interleaved writes to compensate around) — **fork §6.2**. Each chunk's writes emit normal revisions (`source:'restore'`, `restored_from_version`/operation-id threading) — the restore itself is time-machine-visible and reversible by a later restore.
5. **Finalize:** per-sheet scope-hash re-verify (in-fence, so must match), mark the operation `done`, release protections. Mid-apply read visibility is as stated in the model (reads see progress; **fork §6.3** records the rejected alternative: MVCC-style "old visibility until a flip" needs shadow tables — A-grade machinery unjustified here, and incompatible with explicit-partial semantics anyway).
6. **Scope (the honest product boundary):** record data (all sheets) + the **already-revisioned** config tiers (field/view/sheet_config families with existing config revisions). Automation/workflow/dashboard configs are **excluded and documented** — under B they do not enter the config-revision system. The base-restore preview declares exactly what is and isn't covered (no silent "whole base" over-promise — 不用文档掩盖未覆盖面).
7. **Ceiling/limits:** per-sheet 5,000 sync ceiling stays for the sync routes; the operation runs as the async job (SC.1), no ceiling but progress-reported. Retention interplay: plan refuses if `as_of` predates the retention floor (#4224 / #4262 v3.1 §6 baseline+floor) — fail-closed, same doctrine.

## §6 Open forks (owner; recommendations **bold**)
1. **Fence hold across chunks (recommendation REVERSED per owner P1):** the **durable `meta_restore_operations` active-operation row is the authoritative write-block**, checked inside every writer's own transaction — **recommended**. Each chunk takes a **per-transaction advisory barrier** for ordering only (acquired and released within the chunk txn); do **NOT** hold a long-lived session advisory lock on a pinned coordinator DB connection (it vanishes on disconnect and monopolizes a connection for the whole operation). The durable row + per-chunk barrier gives true protection without a long-held session lock.
2. **Failure semantics:** **resume-forward from journal via `paused_retryable` (recommended)** vs compensation/rollback (no interleaved writes exist to compensate around, given the protections — rollback machinery is dead weight). Either way, abandonment is owner-explicit (`abandoned_partial`), never automatic.
3. **Mid-apply read visibility:** **reads-see-progress + fenced writes (recommended)** vs shadow-table flip (A-grade cost, unjustified).
4. **Config-tier scope:** already-revisioned tiers only (**recommended**, honest boundary) vs pulling automation/workflow/dashboard into config revisions (that IS choosing A's hardest part).
