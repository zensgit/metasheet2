> **Product shape (owner direction, rev 5): HYBRID — with the sync leg stated honestly per path.** **Reset ≤5,000:** synchronous, single-sheet, **atomic** (one transaction — this is the only landed sync path that may be called atomic). **Revert ≤5,000:** stays **default-OFF** (#4261 master gate) until its per-record transaction loop is refactored into a real outer transaction — it is **not atomic today and must not be described as atomic**. **>5,000 / base-wide: Option-B async chunked operation** — observable, recoverable, with frozen preview/hash, idempotency, progress, retry-resume, conflict detection, and **explicit partial-completion semantics**. **No cross-sheet long-transaction atomicity is promised at any scale.** §2 records what full Option A would additionally require, so that door is closed on evidence.

- **Read path (measured):** reconstruct + precheck + previews — 50k **p50 ≈122–220ms, p95 ≈251–346ms**. The 10k/50k "preview" rows measured the **fast 413 ceiling refusal**, not full preview computation.
- **Write path (measured @1k, once per run; larger figures are LINEAR EXTRAPOLATIONS):** reset-execute (single txn, thin writes) ≈0.4s @1k → ~20s extrapolated @50k; revert-execute (per-record txns) ≈4s @1k → ~3.6min extrapolated @50k. The gap is partly per-record write weight, not purely txn boundary (control experiment pending).
- **What the evidence DOES support:** keep the 5,000 sync ceiling; any larger restore must be an async path (SC.1). **It does not alone prove B over A** — the case for the hybrid rests on §1 (scale) *plus* §2 (A's config-surface cost) *plus* the owner's product judgment.
- A base is N sheets: cross-sheet single-transaction whole-base restore at production scale means lock-hold measured in minutes — per the extrapolations above, not an option we will promise; hence "no cross-sheet long-txn atomicity" as a hard product line.

## §3 The >5k / base-wide async leg (Option-B operation-level restore) — the hybrid's second half
**Model (v1 semantics, stated without contradiction):** a persistent restore operation with a deterministic plan, executed in chunks under a write fence. **v1 is defined as: observable, recoverable, explicit-partial-progress.** Reads during `applying` see the mid-apply state (write-fenced, progress-visible via the operation row) — there is **no** "never observable half-restored" claim and **no** one-shot visibility flip; those two promises plus explicit-partial cannot coexist, and v1 keeps the honest pair. **State machine:** `planning → fencing → applying ⇄ paused_retryable → done | abandoned_partial`. Failure/crash ⇒ `paused_retryable` with **write protection retained**; permanent abandonment (`abandoned_partial`) is exclusively an **owner-explicit accept-partial action** — an ordinary failure never auto-releases protection.

**`abandoned_partial` governance (owner rev-5 requirement — required before ratify).** Because reaching `abandoned_partial` *permanently releases the write fence over a base left in a knowingly-partial state*, the transition is the single most dangerous action in the whole operation and is gated exactly like the destructive execute paths:
- **Permission:** requires **base-admin** capability (the base-wide analogue of `canManageSheetAccess` used by revert/reset execute) — strictly above plain record-write; a chunk-level operator/worker cannot self-abandon.
- **Typed confirm:** an explicit `confirm:'abandon-partial'` body token (house typed-confirm pattern, like reset's `confirm:'reset'`), plus the operation id and the **current progress digest** (chunks-done/total + the frozen scope hash) echoed back — so the actor is confirming *this* partial state, not a stale view.
- **Audit:** a durable audit record — `meta_restore_operations` retains the terminal `abandoned_partial` row (never deleted) with `abandoned_by`, `abandoned_at`, the progress digest at abandonment, and a reason; and an audit-log/notification entry is emitted. The partial state and who accepted it are permanently attributable.
- Any path that is NOT this gated action (crash, error, timeout, dropped connection) goes to `paused_retryable` with protection **retained** — it can never reach `abandoned_partial` implicitly.

1. **`meta_restore_operations`** (new table): `id` (operation-id, idempotency key), `base_id`, `as_of` (T), `state` — the **exact same enum as the model's state machine**: `planning | fencing | applying | paused_retryable | done | abandoned_partial` (NO `fenced`/`finalizing`/`failed` — those drifted enums would reintroduce the 'ordinary failure releases protection' ambiguity; a crash/failure sets `paused_retryable` with protection retained, and only an owner-explicit accept-partial reaches `abandoned_partial`), `plan` (jsonb: per-sheet deterministic revert/delete/resurrect sets + per-sheet precheck verdicts + scope hashes), `journal` (jsonb: per-chunk completion cursor), `actor_id`, timestamps. One active operation per base (partial unique on `base_id` where state active) — concurrent restores refuse.
2. **Plan phase:** per sheet — run the W0-1 precheck (**hard dependency:** the #4262 v3.3 correction lock must be landed + trusted; a base-wide restore over an untrusted chain multiplies the healed-gap blast radius by N sheets), compute the deterministic sets via `reconstructRecordsAtT`, record scope hashes. Preview = the aggregated plan (per-sheet counts + samples), signed like existing previews (CAS/typed-confirm house pattern).
3. **Fence phase — the WRITER-GATE ORDERING CONTRACT (owner rev-6 P1: close the check-before-fence TOCTOU).** The durable active-operation row is the authoritative write-block, but *checking it is not enough* — the check must be **ordered after the fence acquisition**, or a writer that checks (sees no active op), then has the restore activate underneath it, then writes, drifts the frozen plan. The exact protocol, on ONE connection each, using the shared per-sheet fence (`acquireAutoNumberSheetWriteLock`, #4262 v3.4 §3, same-txn/same-connection):
   - **Every sheet writer (create/update/delete/plugin/automation/lock/…):** `BEGIN` → **acquire the sheet fence** → **THEN** check for an active `meta_restore_operations` row covering this sheet → if active, `ROLLBACK` and refuse `RESTORE_IN_PROGRESS` (409 + operation id); else mutate → `COMMIT`. The fence-**before**-check is load-bearing: a restore that is concurrently activating holds the fence (below), so the writer *blocks on the fence*, and only re-reaches the check *after* the restore has committed its blocking state — so it can never miss it.
   - **Restore activation (the durable blocking state):** acquire the fence of **every** sheet in the base **in deterministic sheet-id order** (no deadlock) → **commit** the `meta_restore_operations` row into a writer-blocking state (§ below) → **release** the fences. After release, writers are blocked by the **durable row** (not the advisory lock, which is gone), and any writer that had been queued on a fence re-checks on acquiring it and 409s.
   - **Writer-blocking states** (a writer that finds the row in one of these must refuse) = `{fencing, applying, paused_retryable}`. **Non-blocking / released** = `{planning}` (pre-fence, plan not yet frozen), `done`, `abandoned_partial`. The **partial-unique "one active operation per base"** covers the **same** writer-blocking set `{fencing, applying, paused_retryable}` — so exactly one in-flight restore per base, and the set that blocks writers is the set that is unique. Per chunk, a **transaction-scoped advisory barrier** (acquired+released within the chunk txn) serializes ordering; there is **no** long-lived coordinator session lock (§6.1). Between a worker crash and its resume the durable-row check alone keeps writes refused. Protection releases only on `done` or owner-accepted `abandoned_partial` — never on ordinary failure or a dropped connection.
   **TOCTOU close (plan→apply):** after **all** sheet protections are in place (durable row committed + advisory locks held) and **before the first mutation**, re-run the W0 precheck per sheet and recompute/compare every plan scope hash; any mismatch ⇒ `paused_retryable` (re-plan required), zero mutations. Finalize's re-verify is retained but is no longer the first check.
4. **Apply phase:** chunked (e.g. 500 records/chunk), each chunk one txn, journal cursor updated per chunk — crash/failure ⇒ **resume-forward from the journal** (re-run is idempotent: plan is deterministic, applied chunks are recorded; no compensation/rollback machinery — the fence guarantees no interleaved writes to compensate around) — **fork §6.2**. Each chunk's writes emit normal revisions (`source:'restore'`, `restored_from_version`/operation-id threading) — the restore itself is time-machine-visible and reversible by a later restore.
5. **Finalize:** per-sheet scope-hash re-verify (in-fence, so must match), mark the operation `done`, release protections. Mid-apply read visibility is as stated in the model (reads see progress; **fork §6.3** records the rejected alternative: MVCC-style "old visibility until a flip" needs shadow tables — A-grade machinery unjustified here, and incompatible with explicit-partial semantics anyway).
6. **Scope (the honest product boundary):** record data (all sheets) + the **already-revisioned** config tiers (field/view/sheet_config families with existing config revisions). Automation/workflow/dashboard configs are **excluded and documented** — under B they do not enter the config-revision system. The base-restore preview declares exactly what is and isn't covered (no silent "whole base" over-promise — 不用文档掩盖未覆盖面).
7. **Ceiling/limits:** per-sheet 5,000 sync ceiling stays for the sync routes; the operation runs as the async job (SC.1), no ceiling but progress-reported. Retention interplay: plan refuses if `as_of` predates the retention floor (#4224 / #4262 v3.3 §6 baseline+floor) — fail-closed, same doctrine.

## §5 Verification plan (goldens, mutation-proven, when built)
Operation idempotency (re-run after crash at chunk k resumes, no double-apply); fence-refusal (concurrent write during `applying` → 409 `RESTORE_IN_PROGRESS`, constructed race); **writer-gate ORDERING race (rev-6 P1, constructed)** — a writer that has taken its sheet fence but not yet checked, while restore activates: because the writer holds the fence, restore *blocks* acquiring it, so the writer completes-or-the-restore-waits; and a writer that starts *after* restore holds all fences blocks on the fence, then on acquiring it re-checks and 409s. The frozen plan never drifts. **Mutation: move the active-operation check to BEFORE the fence acquisition ⇒ the writer misses the concurrently-activating restore and writes after the plan froze ⇒ this golden reds** (a post-restore mutation is observed on a "restored" sheet). Assert the writer-blocking state set `{fencing,applying,paused_retryable}` blocks and `{planning,done,abandoned_partial}` do not. **post-fence pre-mutation re-check** (a write committed between planning and fencing ⇒ hash mismatch ⇒ `paused_retryable`, zero mutations — constructed); **crash-window protection** (kill the coordinator: advisory lock gone, writers STILL refused via the durable operation row until resume — constructed; mutation: drop the in-txn durable-row check ⇒ this reds); scope-hash drift refuse (in-fence mutation between plan and apply is impossible — mutation-test by disabling the fence ⇒ drift golden reds); one-active-operation (concurrent second restore refuses); preview↔execute identity (signed plan); cross-sheet link consistency at T (restored links point at restored rows); excluded-surface honesty (preview declares automation/workflow/dashboard configs unrestored); retention-floor refuse; per-chunk revision emission (`source:'restore'`, operation-id threaded).

## §6 Open forks (owner; recommendations **bold**)
1. **Fence hold across chunks (recommendation REVERSED per owner P1):** the **durable `meta_restore_operations` active-operation row is the authoritative write-block**, checked inside every writer's own transaction — **recommended**. Each chunk takes a **per-transaction advisory barrier** for ordering only (acquired and released within the chunk txn); do **NOT** hold a long-lived session advisory lock on a pinned coordinator DB connection (it vanishes on disconnect and monopolizes a connection for the whole operation). The durable row + per-chunk barrier gives true protection without a long-held session lock.
2. **Failure semantics:** **resume-forward from journal via `paused_retryable` (recommended)** vs compensation/rollback (no interleaved writes exist to compensate around, given the protections — rollback machinery is dead weight). Either way, abandonment is owner-explicit (`abandoned_partial`), never automatic.
3. **Mid-apply read visibility:** **reads-see-progress + fenced writes (recommended)** vs shadow-table flip (A-grade cost, unjustified).
4. **Config-tier scope:** already-revisioned tiers only (**recommended**, honest boundary) vs pulling automation/workflow/dashboard into config revisions (that IS choosing A's hardest part).
