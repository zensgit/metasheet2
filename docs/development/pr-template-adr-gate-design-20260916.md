# PR 模板：新增操作/新增插件消费者/边界变更 ADR 硬门（设计）

日期：2026-09-16
任务：W6-A（缺口审计矩阵 GOV-08）
范围：零代码，仅 `.github/PULL_REQUEST_TEMPLATE.md`、`.github/PULL_REQUEST_TEMPLATE.zh-CN.md`

## 为什么加这条门

直接动因是 owner 两轮复核里反复出现、且现有模板拦不住的两类问题：

1. **“选项②被缩写成改文档/UI，实则扩大 allowlist”**：PR 描述写的是"更新文档说明"或"调整前端展示"，
   实际改动里悄悄把某个路径塞进了全局门豁免表，或者把 `mst_` 前缀的 allowlist 加宽了一条。这类变更
   本该走独立评审（因为它扩大了系统的信任边界），但因为夹在功能 PR 里，审阅者按"文档/UI 变更"的心态
   过了一遍就放行。
2. **“代理顺手新增 CI 泳道”**：在完成一个功能任务时，代理顺手加了一个新的 workflow job 或新的 CI 检查
   项，这本质上是部署/发布边界的变更（决定了什么代码能不能合并、谁的检查是必需的），但因为它看起来是
   "顺便让 CI 更完善"，没有被当作独立变更对待。

这两类问题的共同结构是：**变更的"标签"（文档/UI/顺手加测试）掩盖了变更的"实质"（授权边界或部署边界
被移动了）**。现有 PR 模板的硬门（provenance 测试、对抗核验、及时合并）都是事后/过程性的检查，没有一条
是"这个变更是否需要独立评审、是否需要 ADR"的入口筛查。这条新硬门补的就是这个入口。

## 它要拦住的具体形态

新硬门覆盖三类变更，要求代码 PR 与对应 ADR 分别提交：

- **新增操作**：新端点、新动作（route/action/RPC）。这类变更扩大了系统对外暴露的能力面，即使实现本身
  很小，也应该有独立记录说明"为什么需要这个新入口、谁能调用、边界在哪"。
- **新增插件消费者**：某插件第一次拿到宿主 facade，或者已有插件的 facade 能力范围被扩大（例如从只读
  facade 换成可写 facade，或新增了一个敏感方法）。插件消费宿主能力是信任链的一环，扩大它等于扩大了
  攻击面/误用面。
- **部署边界或授权边界变更**：这是最容易被“顺手”带过的一类，给出三个具体例子帮助作者自查：
  - 把某个路径加入全局门（例如 fail-closed 门、租户隔离门）的豁免表；
  - 扩大 `mst_` 前缀的 allowlist（决定哪些表/字段可以被跨租户或跨插件访问）；
  - 给一个原本 fail-closed 的门加一个旁路开关（哪怕默认关闭，"存在开关"本身就是边界变更）。

不拦的：单纯的文档改动、UI 文案调整、不改变已有端点行为的 bug fix、纯测试补充——这些不需要 ADR，
硬门里的自查项写的是"命中以上任一类型"，避免把门槛滥用到所有 PR 上。

## CODEOWNERS 悬空引用的处置

`git ls-files .github/CODEOWNERS` 核实为空，仓库里确实没有 `.github/CODEOWNERS` 文件（`.github/` 下
只有 `ISSUE_TEMPLATE/`、两个 PR 模板、`PULL_REQUEST_TEMPLATE_V2.md`、`workflows/`、
`branch-protection-backup.json`，没有 CODEOWNERS）。原模板第 38 行"监控/告警配置变更需双人审批"的
条目引用了这个不存在的文件，属于悬空引用。

处置选择：**不创建 CODEOWNERS**（是否建立该文件、由谁 own 哪些路径，是仓库治理决策，超出本任务"零代码
文档补丁"的范围，也不是我能替 owner 做的判断），改为在同一位置明确标注"CODEOWNERS 尚未建立，此项审批
要求暂由 owner 人工把关"。这样：

- 不产生新的悬空引用（原来指向不存在的文件，现在明确说明现状）；
- 不假装治理机制已经存在（如果直接删掉这行，双人审批的意图会连同悬空引用一起消失，比留一个准确的
  "尚未建立"说明更容易被忽略）；
- 为后续 owner 决定是否建立 CODEOWNERS 留下一个显式的、可搜索的锚点（`grep CODEOWNERS` 能找到这条
  待办）。

## 已知限制 / 未做事项

- 仓库里目前没有 ADR 目录或 ADR 模板（`find . -iname "*adr*"` 为空）。这条硬门假设"ADR"是一个团队
  已理解的概念（独立于代码 PR 的架构/边界决策记录），但没有规定 ADR 应该放在哪、用什么格式。这是否
  需要补一个 `docs/adr/` 骨架和模板，留给 owner 判断，不在本任务范围内。
- `PULL_REQUEST_TEMPLATE_V2.md`（"精简模板"）没有任何硬门区块，本任务未触碰它——它的定位和主模板不同，
  是否也需要这条门，留给 owner 判断。
- 这条门是自查性质的 checkbox，不是 CI 强制门；它能否被绕过（例如作者勾选但实际没写 ADR）取决于
  review 环节，不在本次改动的强制力范围内。

## 如何验证（人工核对清单）

因为本任务零代码、不涉及可运行的验证脚本，用以下人工核对清单确认改动符合预期：

1. `git diff main -- .github/PULL_REQUEST_TEMPLATE.md`：确认只新增了一条硬门 checkbox（含 4 条子要点）
   和一处 CODEOWNERS 措辞调整，没有改动其它章节。
2. `git diff main -- .github/PULL_REQUEST_TEMPLATE.zh-CN.md`：确认新增的"## 硬门"小节与英文模板里新增
   的那一条在语义上一致（三类变更 + 三个边界变更例子 + 自查句）。
3. `git ls-files .github/CODEOWNERS`：确认仍然为空（本任务承诺不创建 CODEOWNERS）。
4. 打开两份模板文件，确认 Markdown 语法正确（checkbox 语法 `- [ ]`、加粗 `**...**`、列表缩进）能在
   GitHub 上正常渲染——可通过本地 Markdown 预览或 `git show` 后目视检查缩进层级。
5. 确认改动未涉及 `packages/`、`plugins/`、`scripts/`、任何 `.yml` workflow 文件（`git diff --stat main`
   核对改动文件列表）。
