## Assumptions and implementation direction

- #6300 is to merge first. This work starts from its resulting `main` state; it must re-check the exact main SHA, route contracts, and CI wiring before implementation.
- `GET /api/attendance/rules/me` is the existing authenticated, membership-checked source for self-service runtime rules. With no `asOf`, it defaults `resolvedForDate` to the UTC calendar date and resolves `runtimeRule` for that date. `data.resolvedAt` is only the server-time sample; it does not assert that the rules are for the user’s calendar-today in the attendance timezone. Reuse this response rather than add a clock endpoint. No user/org/group override is allowed on this self-service read.
- The employee hero clock and its `todayWorkDateKey` currently derive from device `new Date()`. The live display and its day boundary should instead derive from one calibrated server-time anchor.
- Calibration parameters for this implementation direction are: maximum RTT 5 seconds, sample freshness 5 minutes, and resample every 60 seconds and when page visibility returns. The displayed estimate uses the response-receive monotonic instant as its anchor because `resolvedAt` is generated before the response; do not subtract half-RTT and mistake server processing time for one-way network delay. The uncertainty bound is the accepted RTT limit, not millisecond-level synchronization. These parameters are implemented and locally verified; see the verification snapshot.
- Idempotency and outdoor common-receipt topology below are the approved implementation direction from Sol and Astra review. Implementation and local gates are complete; fresh remote CI remains pending at this pre-push snapshot.

## Problem and desired behavior

Device wall clocks can be wrong or changed while an employee is viewing the attendance page. That can make the visible time/day misleading, and a normal online punch can currently supply `occurredAt` or its `occurred_at` alias. The server must own the instant recorded for every ordinary online punch.

The employee page will display a server-calibrated clock, and its `today` key will use the same estimated server instant plus the currently resolved attendance IANA timezone. For this slice, that timezone comes only from `runtimeRule` and the existing resolved attendance context: `resolveWorkContext` selects `rotationInfo.shift ?? assignmentInfo.shift ?? defaultRule` (plugin `index.cjs`, approx. L15639). Do not substitute device timezone or `attendanceGroups[].timezone`; the latter is assignment data, while `configuredGroupRule` is marked `not_user_calc_chain` and the response warns `GROUP_RULE_SET_PREVIEW_DIVERGENCE` (plugin `index.cjs`, approx. L17689). A normal online punch will be stamped on the server regardless of client clock fields. Missing, malformed, stale, or excessively delayed calibration must produce a visible unavailable/error state; it must never silently switch to device time.

## Server clock calibration

1. On authenticated attendance-page initialization, request the existing `rules/me` response. Capture `performance.now()` immediately before sending and immediately after receiving it. Treat `data.resolvedAt` as the server instant associated with the response.
2. Accept a calibration sample only when the response is successful, `resolvedAt` parses as a finite ISO instant, the measured round-trip time is within the configured bound, and the sample is fresh. Anchor the estimate at the response-receive `performance.now()` value; advance the estimated server instant using elapsed `performance.now()`, never by repeatedly consulting `Date.now()`.
3. Reject a response whose session generation is no longer current, whose request sequence is older than the last accepted sample, or whose monotonic timestamps are invalid. A later-issued request must not be overwritten by an earlier response that happened to arrive last.
4. When the document becomes hidden, immediately invalidate the clock sample and the active rules-refresh round version, and stop background sampling and publication. Do not let hidden/in-flight responses publish afterward. On visibility restoration, call the same invalidate-and-resample entry point used by `pageshow` when `event.persisted` is true. The recovery round always starts with a fresh `rules/me` request without `asOf`, obtains a new server instant and candidate timezone, and may issue at most one date-correction request. This is an explicit recovery exception to the later-refresh path that derives `asOf` from a trusted anchor. A retained previously aligned timezone may be held as data, but without a fresh server anchor it is not trusted for clock display or as an explicit punch timezone. Until recovery sampling succeeds, show clock/date unavailable; keep punch submission enabled and let the backend stamp server time. Never compensate with `Date.now()`.
5. While continuously visible, retain the 60-second sample cadence. A normal 60-second background refresh may keep using the existing aligned rules snapshot while it remains fresh. Preserve the existing manual Refresh behavior that clears stale rules and availability before reloading; do not apply background retention to every caller. Hidden-state recovery always invalidates first. On unmount, clear timers and remove visibility/page-show listeners. A fresh valid sample replaces the anchor atomically. Do not fall back to device time. This display state does not disable ordinary punch submission: the backend continues to stamp a trustworthy server time for each online punch.
6. Keep server-clock calibration independent from rule-date alignment: a valid server-time anchor may update even while today’s rules are unavailable. For the initial rules read, omit `asOf`; treat its `runtimeRule` IANA timezone only as a candidate. Compute the target calendar date from the calibrated server instant in that candidate timezone and compare it with `resolvedForDate`. If they differ, issue at most one corrective `rules/me?asOf=<target-date>` read. Publish the today rule snapshot and its timezone only when the returned `resolvedForDate` aligns with the target date.
7. On later continuously-visible 60-second and calendar-day refreshes, derive `asOf` first from the latest trusted IANA timezone and calibrated server instant, then validate the returned `resolvedForDate`. (Visibility and persisted-pageshow recovery use the fresh no-`asOf` exception in step 4.) If a mismatch remains, allow at most one corrective read in that refresh cycle. Validate the correction; if it still does not align, mark today’s rules/date unavailable and wait for the next scheduled refresh. Never recurse or start an unbounded correction loop. A newly returned timezone is not trusted until its snapshot passes this alignment.
8. Apply the current session/generation and request-version checks to both the initial and corrective request. A late response from either leg cannot publish after a newer cycle, a session/org change, or a superseding correction. Preserve the existing `omitHeaders` request behavior. Keep the backend `asOf` ±31-day validation unchanged.
9. Do not use an unaligned timezone as a trusted explicit punch timezone. If no aligned rule snapshot is available, omit the explicit timezone and let the backend resolve the instant/timezone using its existing rules and shift logic. Preserve existing IANA timezone resolution and overnight-shift attribution. Calendar `todayWorkDateKey` is not necessarily the punch’s attributed `workDate`; never claim that they are equivalent.

Some operating system/browser sleep and process-freeze cases do not advance `performance.now()`, despite the monotonic-clock design; see [MDN: `Performance.now()` ticking during sleep](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now#ticking_during_sleep). Visibility/BFCache invalidation and a fresh recovery sample handle that limitation without deriving elapsed sleep time from the device wall clock.

The calibrated browser clock is display/supporting context only. It does not authorize a client-supplied punch instant. With the 5-second RTT acceptance bound, the display estimate’s uncertainty is bounded by the accepted sample RTT; this design does not claim millisecond-level agreement. A valid server-time sample does not make a rules snapshot date-aligned, and a calendar date in an attendance timezone does not define the punch work date: backend punch attribution continues to use its independent timezone and overnight-shift rules.

## Ordinary online punch authority

- At the authenticated `POST /api/attendance/punch` write boundary, derive `occurredAt` exactly once from server time. Do not accept caller `occurredAt` or `occurred_at`; reject either alias when present, including null/empty/malformed values, with a fixed values-free client error. Do not silently ignore supplied values.
- Re-derive work date, effective IANA timezone, and shift-window attribution from the server instant using the existing rule/shift resolver and existing ambiguity refusal. Preserve event/history timezone fields and historical records as stored; this is not a backfill or reinterpretation project.
- Keep existing authenticated identity, organization-membership checks, reserved-source rejection, schedule/policy gates, canonical writer, event/projection behavior, and transaction boundary. Client-selected `source` must not create a bypass; ordinary online requests remain unable to claim reserved/internal provenance.
- Apply the same prohibition to any alias or online presence/event path that can create an ordinary live punch. The implementation must enumerate concrete write entry points and demonstrate there is no alternate route that accepts a caller-selected instant or bypasses the ordinary-punch boundary. Ordinary punches continue to use backend-generated time even when the browser clock display is unavailable.
- Retain controlled historical-import and approved makeup/correction entry points under their existing authorization and provenance rules. They are distinct governed operations and must not be silently converted into “now” punches.
- Explicitly stop or quarantine legacy raw-event scripts that write ordinary live punch timestamps. Do not silently rewrite their timestamps to now or leave them appearing to work. The PR must identify the scripts and provide a clear fixed refusal/retirement path; no unrelated script cleanup.

All owned traps were closed. No real environment was accessed. This diagnostic is not an implementation, test, or acceptance gate PASS.

## Approved idempotency implementation direction

Sol and Astra approved this implementation direction. Implementation and local gates are complete; see the verification snapshot and final independent receipt. Remote CI is recorded per successor head.

- Reuse the existing `live_punch` operation row as a common receipt. Do not change authoritative payload fingerprint v1 or its freeze geometry. A new online request fingerprint domain uses the closed raw client-input frame plus authenticated subject/org and a validated internal status/body frame. Existing receipt rows from the old domain must never be reinterpreted as the new domain; cross-domain reuse returns 409. Preserve the existing `chk_aro_business_snapshot_scope` constraint: a direct-live common receipt keeps `normalized_business_input_snapshot` NULL. The independent online request projection supplies only its stable fingerprint domain; the sealed `response_snapshot` preserves the first full HTTP status/body.
- For an ID-bearing outdoor request, the existing request-create receipt/auth/provenance remains authoritative; add the common live-punch receipt in the same transaction. The two existing operation identities must be acquired in one global order: ascending final signed-bigint numeric value. Do not use lexical ordering. Sol and Astra approved this as the implementation direction. This is a design decision only; no implementation or test result is implied.
- The stable request fingerprint must bind only the closed raw client-input frame and authenticated subject/org. It must not include server time, resolved work date, derived shift timezone, or other values that change when the same request is retried. Keep authoritative payload fingerprint v1 unchanged, and preserve the existing outer mirror / inner freeze contract.
- Under the existing operation locks, a same-ID race resolves to one business result for each supported pairing: normal/normal, outdoor/outdoor, and normal/outdoor. The loser must receive the winner’s exact status, body, and server timestamp on a valid replay; no second append/projection/event occurs. Old completed receipts are not replayed through the new domain and return 409. For a new online request, a primary-key 23505 may trigger only an exact-constraint, bounded fresh-transaction retry; do not broaden or alter global SQL retry behavior.
- If mutable preparation fails or races before the inner freeze, use the same preflight fence for **replay-or-refusal**: re-read the receipt under lock and either return a valid sealed replay or refuse. A temporary claim made during preparation must roll back on refusal/failure; winner rollback must leave no hanging receipt row. Every online HTTP request, including replay, continues through the existing HTTP `withPermission` route gate, including its permission check before mint; its transaction rechecks actor identity liveness (`users.is_active` / `activation_status`) and active `user_orgs` membership. The transaction does not recompute user/role permission grants, and this slice does not claim linearization against a permission-grant revocation racing an already-authorized HTTP request. A currently permission-revoked request must be denied by the HTTP gate before receipt read and before DML. Membership or activation changes after mint must be refused by the transaction liveness check. A completed operation may replay only when the current route gate and transaction liveness checks pass. Do not fall through to a fresh append after mutable preparation failure. Preserve the current outer-prepare / inner-freeze geometry and all existing freeze invariants.
- Check a sealed same-key replay before the existing minimum-interval gate so an exact retry is not incorrectly rejected by the interval created by its original write. Same-key concurrent requests must yield one write and one exact replay/refusal. This slice does not expand minimum-interval concurrency guarantees for different operation IDs. A request whose first successful claim straddles local midnight must keep the original receipt/outcome on replay and must not create a second next-day punch.
- Normal-punch operation IDs and generic request-create UUIDs occupy independent identity spaces. A new outdoor request and generic request-create operation reusing the same UUID can still contend on an inner primary key; that case must resolve to a stable 409 or the narrowly scoped exact-constraint retry, without leaking SQL errors. This design does not claim safety when old and new binaries run concurrently. Before implementation completion, verify the supported same-version receipt races, rollback/no-hanging-row behavior, completed replay through current HTTP permission gate plus transaction identity/member liveness, permission-revoked HTTP request denied before receipt read and with zero DML, post-mint membership/activation revocation rejected by the real PostgreSQL transaction liveness guard, old-receipt 409; do not claim transaction-time permission-grant recomputation or concurrent grant-revocation linearization, cross-midnight replay, retry inside the interval, failed mutable preparation fence, and the normal/outdoor/generic UUID cases. Do not add different-key minimum-interval concurrency control to this slice.

## Compatibility and migration impact

- Existing clients that omit punch time continue to submit ordinary punches; the server supplies the instant. The current web client already omits `occurredAt` from its normal punch payload.
- Clients and scripts that intentionally send `occurredAt` / `occurred_at` to the ordinary live route will receive an explicit refusal and need to use a governed historical-import or makeup/correction workflow where eligible.
- Historical event instants and IANA timezone values remain as stored. Existing rule, shift, overnight-window, and work-date attribution semantics remain authoritative. `rules/me` keeps its UTC-default and ±31-day `asOf` behavior; punch timezone/work-date resolution remains independent, so calendar today is not equated with punch work date.
- Product expectation recorded for future work: when multitimezone attendance is ON, an approved Singapore business trip should use Asia/Singapore during its effective period, then return to the employee’s underlying timezone afterward. When OFF, an approved trip does not override the system default attendance timezone. This requires an effective-dated temporary attendance assignment/shift linkage that resolves through `runtimeRule`. It is not implemented by this clock slice: current attendance `REQUEST_TYPES` (plugin `index.cjs`, approx. L139) has no `business_trip`, and an approval alone does not change the runtime rule. This note does not create approval authority or a new flag.
- Future multitimezone rule (design pending): OFF uses the organization/system default attendance timezone even during approved travel, tentatively `defaultRule.timezone` rather than server OS timezone; ON uses the administrator-approved effective attendance arrangement, including an approved travel destination for its effective period and the underlying arrangement after it ends.
- Switch ownership is tentatively organization-admin controlled as the recommended value; the optional preference reply is still outstanding. This is not ratified implementation approval. This clock slice does not implement the switch or travel linkage, change current `rotation > assignment > defaultRule` resolution, or change existing explicit-timezone compatibility; all future design remains pending.
- The owner stated that old attendance data can be discarded. For follow-up enablement, preserving or migrating old attendance history is therefore not a required business outcome. Actual deletion target/environment is still unspecified; this slice deletes no existing environment data and retains the current fingerprint, audit, and governed-operation contracts.
- No schema migration is expected for the server-clock or ordinary-time-authority change. The proposed fingerprint may fit in existing registry fields; verify that against the post-#6300 implementation before asserting this. If a migration proves necessary, stop and revise the lock with forward/rollback notes.
- No new feature flag is proposed. This is a fail-closed correctness rule for ordinary online writes, not a default-off capability.
- This design direction authorizes no deployment, real-tenant read, production write, external system write, customer-data access, or traffic expansion. Deployment requires the hard gate above and separate authorization. The local acceptance statuses below are supported by the verification snapshot; release and business acceptance remain separate.

## Out of scope

## Transaction liveness scope clarification

The existing SERIALIZABLE transaction reads activation and membership from its transaction snapshot; `set_config` SELECT may establish that snapshot before the liveness read. The post-mint revocation test therefore commits revocation before the fresh transaction snapshot and verifies refusal. A revocation committed after the snapshot may serialize after the punch and is not guaranteed to invalidate it. This slice preserves the current guard and does not introduce global row locking or claim concurrent membership/activation revocation linearization. HTTP permission is re-evaluated for every request before receipt access.
