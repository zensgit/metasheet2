# Claude 两份 MetaSheet 平台设计意见复核

日期：2026-08-20  
审阅对象：

- 《MetaSheet 业务应用平台化总体设计 v3》
- 《多维表如何引入外部数据、用户端如何配置出业务系统》

复核范围：两份 PDF 全文、此前上传的备料系统代码、MetaSheet 当前 GitHub `main` 的关键实现路径。本文不是对 Claude 文档的摘要，而是对其事实、架构选择和实施顺序的复核。

## 一、结论

两份意见总体质量较高，尤其第二份比第一份更接近可执行设计。它们正确识别了 MetaSheet 从“多维表产品”走向“多应用平台”最关键的缺口：系统身份、外部数据绑定、字段写入归属、批量变更计划、应用蓝图、安装升级和历史数据迁移。

我的总体判断是：**约 80% 的方向可以采纳，但不能原样立项。** 主要原因不是它判断错了，而是它把太多平台能力串成了一条前置链，容易演变成“先建设半年平台，再交付第一个应用”。此外，少数数据模型选择会在后续造成运维和演进困难，个别代码事实也已经被当前 `main` 更新。

最重要的调整是：

1. 保留“备料是第一个业务灯塔应用”的目标，不必等待所有通用底座完成。
2. CRM 可以作为验证蓝图通用性的工程样板，但不应因此把备料推迟到平台建设末期。
3. 外部数据绑定、字段归属和外部业务键应使用服务端归一化模型，不应主要塞进 sheet/field 的可编辑 JSON。
4. `masterRef`、统一收件箱、外部实时查询都应按真实复用需求后置，不能成为首个应用前置条件。
5. 应用形态应是“蓝图 + 可选领域插件”，不是“一律无插件”。

## 二、Claude 判断得最准确的部分

### 1. 系统主体是能力 0，而不是实现细节

这是两份意见中最重要、也最值得补进原总体设计的发现。当前平台的若干访问接口只接受真实用户主体；数据源访问又按精确 `ownerId` 判断，已保存的 `workspaceId` 没有真正参与授权。于是同步任务、定时任务、外部推送和应用安装器如果没有正式的 integration/system principal，只能冒充用户、使用空身份或开旁路。

建议把主体明确建模为：

- `human`
- `integration`
- `automation`
- `system_migration`

每个非人工主体都必须有租户、工作区、来源实例、权限范围、有效期和审计归属。调用方不能从请求体直接指定系统身份；只能由服务端根据获批绑定签发。

### 2. 字段“只读”不等于字段归属

Claude 正确指出，把外部源归属放在客户端可写的 `meta_fields.property.source` 中不可信。当前通用属性清洗会保留部分对象属性，而记录写路径只知道字段是否只读，不知道“谁可以写”。

需要的不是单一 `readonly`，而是服务端拥有的写入策略：

```text
ownership_kind: human | formula | system_binding | app_managed | detached
owner_binding_id: nullable
policy_version
```

人、普通自动化和无关插件必须被拒绝；只有对应 binding 的受信同步写者可以写自己的字段。所有写路径——UI、OAPI、表单、自动化、插件、导入、同步——都必须经过同一策略。

这里两份文档存在一个需要消解的内部矛盾：第一份提出 writer-aware 的 `assertFieldWritableBy(field, writer)`；第二份说已有 `readonly/readOnly` 判断足够。后者只足以拦截普通写入，不能授权“对应同步主体写入只读系统字段”。最终仍需要 writer-aware 检查，或者一个严格受控且验证归属的同步专用写入缝隙。

### 3. `plan → 人工确认 → apply` 是正确的通用抽象

备料计算、BOM 展开、清洗去重、排产建议、派工建议、外部同步差异，本质上都不是一个公式，而是一次可审阅的批量变更。Claude 提出的 plan 应保留，至少包含：

- run/plan id、输入快照或水位
- 目标 sheet、候选变更和摘要
- diff、告警、不可分类项
- 过期时间、一次性确认令牌
- apply 状态、操作者、审计信息

但 plan 不应强行覆盖所有自动化；只用于批量、可回滚或高影响的变更流程。

### 4. 任务、审批、确认和通知不能混成一种对象

这点完全赞同。统一收件箱只能做投影层，而不能消灭底层语义：审批有决策与代理规则，任务有候选人和领取，确认是某次 plan 的一次性授权，通知通常没有待办状态。

### 5. 应用蓝图必须有安装、实例和升级语义

Claude 对 `instanceKey`、`id_map`、资格校验、升级前检查、环境 ID 占位符、原生字段权限迁移的建议都很有价值。当前售后插件安装器按 tenant + app 形成单一安装，并用 appId 生成 projectId，多实例容易冲突；现有 `ensureFields` 冲突更新会覆盖名称、类型、属性和顺序，也不适合作为可保留租户修改的升级器。

蓝图不应替代 manifest，而应分层：

- `app.manifest`：包身份、能力、依赖、导航和安全声明；
- `blueprint`：可安装的数据模型、视图、自动化、审批和策略；
- `binding`：某租户环境中的连接、角色和参数实例。

### 6. 不做实时虚拟表、不在 v1 做外部回写

先做物化同步表、标量字段、单向入站、手工确认 apply，是合理的风险控制。实时外部 lookup、双向同步、复杂链接同步和外部回写应等稳定性、权限、缓存和故障语义成熟后再做。

### 7. 历史迁移与双轨运行必须单列

旧备料系统不只是功能参考，还包含历史数据、用户习惯和业务证据。迁移、校验、回退、并行运行和切换验收应独立成阶段，不能藏在模板安装里。

## 三、需要修改的设计

### 1. 不建议把完整 `source_binding` JSON 直接挂在 `meta_sheets`

文档同时要求绑定有版本、五态审批、资格证明、主体、密钥引用、历史和升级，却又倾向把绑定主体放入 sheet JSON。这两个方向冲突。

建议使用归一化表：

```text
multitable_source_bindings
multitable_source_binding_versions
multitable_source_binding_qualifications
meta_field_source_policies
```

sheet 只保存 `active_binding_id` 和状态投影。这样才能支持版本审计、撤销、重审、未来多绑定和无损历史。

### 2. 不建议为每个 sheet 动态创建 JSON 表达式唯一索引

按业务键 upsert 必须有唯一性保障，但每个动态 sheet 创建局部 JSON 表达式索引会引入 DDL 抖动、组合键归一化、字段改名、软删除和在线重建问题。

更稳妥的是通用外部键注册表：

```text
meta_record_external_keys(
  binding_id,
  normalized_key_hash,
  normalized_key_json,
  record_id,
  active
)
UNIQUE(binding_id, normalized_key_hash) WHERE active
```

它还可以承载幂等、冲突诊断和重绑，不需要为每张表做动态 DDL。

### 3. “解绑后 system 自动变 human”风险过高

这会悄悄改变字段治理和数据来源。建议解绑后进入 `detached`：冻结原始来源和最后同步水位，只允许管理员经过明确评审后转换为 human-owned；历史 provenance 永久保留。

### 4. 外部数据配置不能只有封闭 preset

生产制造的 PLM/K3 适合“认证 preset + 服务器封闭参数”；但普通 CRM、售后和项目系统需要租户管理员自助选择获准的数据源对象和字段。

建议两个信任等级：

- 认证模式：厂商预置对象、字段映射、限额和读计划，适合核心生产系统；
- 管理员自助模式：只能在已授权 schema/对象/字段内选择，服务端重新校验，仍禁止原始 SQL、URL 和凭据进入浏览器。

否则平台会成为“厂商预置目录”，而不是可配置应用平台。

### 5. “预览永远不返回值”不宜成为全局产品规则

元数据预检应默认无值；但普通租户自有数据在做字段映射时，完全看不到样例会显著降低可用性。建议增加受权限控制的脱敏样例预览：单独 scope、少量行、字段掩码、全量审计、禁止共享缓存。核心制造 preset 可以继续禁值。

### 6. `masterRef` 不宜立即成为新字段类型

它本质上打开了主数据管理、编码治理、跨应用变更传播和权限边界。首阶段先用现有跨 base 链接，加主数据 registry 与校验策略；当 2–3 个应用证明相同问题反复出现，再提升为一等字段语义。

### 7. 统一收件箱不是备料首发阻塞项

首期可以在现有审批/任务页面上提供应用入口和深链。等售后、项目和 HR 同时产生跨应用待办后，再做统一投影。它是有价值的平台能力，但不该进入备料 MVP 的关键路径。

### 8. “以后不写领域插件”需要改成混合模型

配置型应用应主要由蓝图表达；BOM 展开、物料根选择、排产、匹配去重、复杂 SLA 等算法仍应是版本化、可测试的领域 action/plugin。应停止复制应用壳和安装器，而不是停止写领域代码。

## 四、代码事实复核

以下关键点在当前 GitHub `main` 得到支持：

| Claude 主张 | 复核结果 | 判断 |
|---|---|---|
| 系统/默认主体无法直接通过插件数据源 principal 检查 | 代码明确拒绝默认/system/tenant/admin fallback | 成立，且是 P0 设计锁 |
| 数据源访问只比对 ownerId，workspaceId 未参与授权 | `DataSourceManager.assertAccess` 如此实现 | 成立 |
| 字段已有 `readonly/readOnly` 通用只读判断 | `permission-derivation.ts` 已支持 | 成立，但不足以表达 writer ownership |
| 字段属性中的 source 元数据可能由客户端携带 | 通用 property 清洗路径无法保证服务端不可伪造 | 成立 |
| 普通记录写路径会拒绝所有 always-readonly 字段 | `records.ts` 如此实现 | 成立；同步写者需受控专用权限 |
| 插件 `assertSheetScope` 调用忽略了 `false` | 一处宿主 API 只 await，未检查返回值；备料事务路径另有正确检查 | 成立，应尽快修复 |
| 工作流任务可通过 `assignee/candidateUser/...` 参数越权列举 | 只在无过滤参数时才默认限制当前用户 | 成立，属于明确安全缺陷 |
| 自动化 `create_record` 没有 revision | 当前 main 已在同一事务写 `recordRecordRevision(action:'create')` | 已过时/已修复 |
| 自动化 create 使用裸 INSERT、未走完整字段 codec/只读/字段权限 | 当前代码仅补了跨 base gate、富文本清洗、revision 等，仍未统一进入 canonical writer | 基本成立，但应精确表述 |
| App 安装不支持同租户多实例 | 售后安装 ledger 与 projectId 派生均未纳入 instanceKey | 成立 |
| `ensureFields` 会覆盖租户修改 | 冲突更新覆盖 name/type/property/order | 成立，升级器必须重做 |

因此，Claude 的代码阅读总体可信，但实施前必须重新基于目标 commit 跑静态检查和测试，不能把文档中的每一项当作当前事实。

## 五、关于备料是否应作为第一个应用

**可以，而且我仍建议它作为第一个业务灯塔应用。**

备料同时验证外部数据、BOM 领域算法、计划确认、审批、任务、权限、通知和历史迁移，能真正检验平台。但它不适合作为“最简单的模板示例”。正确做法是双轨：

- 备料：第一个真实业务应用和纵向切片，目标是尽早产生业务价值；
- CRM-lite：蓝图引擎的工程一致性样板，证明不是只为备料硬编码。

因此我不赞成“先把五大平台能力全部完成，再到 P3 做备料”。这会把最重要的业务验证推迟太久。也不赞成只做 CRM 后再决定备料，因为 CRM 无法暴露系统主体、字段归属和批量 plan 的真实复杂度。

首期备料范围必须收紧：

- PLM/K3 首期只读；
- 计算输出候选 plan，人工确认后写 MetaSheet；
- 不做 K3 自动写回；
- 保留旧系统双轨校验；
- 先形成薄的 app manifest、权限、实例和导航，不等待完整模板市场；
- 领域算法保留为可测试插件，不塞进公式。

## 六、建议的实施顺序

### P0-A：安全闭环，1–2 周

- 关闭旧备料 `/erp/*` 暴露面，轮换泄露凭据，重置历史弱密码并做事件排查；
- 修复 workflow task 查询越权；
- 修复 `assertSheetScope` 未检查 false；
- 锁定 system/integration principal、字段归属和审计模型。

### P0-B：备料薄应用化，2–4 周

- manifest、所需权限、目录可见性、app instance、导航；
- 复用已完成的备料计划/持久化能力；
- 导入或只读连接旧数据，建立双轨比对；
- 不依赖统一 inbox、masterRef 或通用外部 lookup。

### P1：外部同步 A1，6–8 周

- 归一化 binding/version/qualification；
- integration principal；
- 标量字段映射、服务器字段归属；
- 通用 external key registry；
- 分块 upsert、同 binding 串行、限额、熔断、审计；
- `sync → plan → manual apply`，定时任务只产 plan。

### P2：AppBlueprint 与安全升级，6–8 周

- 蓝图 schema、preflight、id_map、instanceKey；
- 增量安装、三方 diff、保留租户修改、失败回滚；
- CRM-lite 作为通用性测试夹具；
- 将当前备料安装描述逐步迁入蓝图，而不是重写业务算法。

### P3：第二个真实应用，6–8 周

建议售后服务或项目管理。只有在第二、第三个应用中反复出现相同需求时，再将 `masterRef`、统一 inbox、外部 lookup 和复杂链接同步升级为平台 P1 能力。

Claude 给出的 28–40 或 60+ 人周，对“完整平台范围”并不夸张；但对第一个可用备料应用明显过重。应区分“业务 MVP”和“平台完整态”的估算。

## 七、两份文档遗漏或论述不足的事项

1. 物料、数量、单位、日期、金额、物料版本等领域语义契约；仅有字段映射不足以保证跨系统一致性。
2. 卸载归档、备份恢复、灾难恢复、数据保留、租户导出、升级回滚和 SLO。
3. 页面编排、角色模拟、移动端、可访问性、应用预览等用户端配置体验。
4. 连接器 secret 轮换、出站网络白名单、签名 webhook、防重放、审计保留和数据最小化。
5. 50k/100k 行规模下的明确性能预算、队列背压、索引成本和容量模型。
6. 可执行测试矩阵。两份意见自己也承认没有运行测试；这必须在 design lock 批准前补齐。
7. 应用目录与插件权限、`requiredPermissions`、多应用共用插件时的隔离规则，需要和现有 App Center 实现正面衔接。

## 八、最终决策建议

### 直接采纳

- system/integration principal
- 服务端字段归属与 writer-aware 写入检查
- plan/confirm/apply
- 任务/审批/确认/通知分离
- 蓝图的 instanceKey、id_map、preflight、升级和回滚
- 物化同步、v1 单向只读、外部回写后置
- 历史迁移和双轨运行独立阶段

### 修改后采纳

- source binding 改为归一化版本表
- JSON 唯一索引改为通用 external key registry
- preset 改为认证模式 + 管理员自助模式双层
- 无值预览改为默认无值 + 权限化脱敏样例
- 应用改为 blueprint + optional domain plugin
- 解绑改为 detached，不自动转 human

### 暂缓

- `masterRef` 新字段类型
- 统一收件箱完整实现
- 外部实时 lookup
- 双向同步和 K3 写回
- 复杂 link 字段同步

### 不采纳

- 先完成完整平台计划、再开始备料应用
- 所有业务应用都不得有领域插件
- 解绑后自动把系统字段变成人工字段
- 把客户端可编辑 JSON 当作安全边界

总体上，Claude 的设计应作为高质量“问题清单和架构候选”，不是可直接执行的总包方案。最佳路线是以备料做纵向业务切片，同时抽出最小通用底座；每完成一个真实应用，再把被重复验证的部分固化为平台能力。
