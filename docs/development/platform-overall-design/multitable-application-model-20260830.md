# 多维表应用(Multitable Application)模型(2026-08-30,DRAFT)

> **地位**:接管后产品化候选二号,与《源接入自助化:确认不配置》(候选一号)配对;不进入当前任何门;values-free。
> **命名与定位由 owner 给出(2026-08-30)**:备料不是"一个插件的功能",而是第一个**多维表应用**。

## 0. 一句话定义

**多维表应用 = 建在多维表底座上的可安装业务单元**:一组受管表 + 操作页面 + 权限码 + 配置面 + 验收判据,由一份应用清单(manifest)声明,点击"安装"即自动就位。**装的是表和配置,不是代码**——代码永远随产品版本发布(CI/pin/溯源),动态代码分发是章程红线,永不做。

## 1. 应用清单(manifest)——安装器的唯一输入

```
app: stock-preparation
  managedObjects:                 # 幂等 ensure,安装器逐一补齐
    - plm_stock_preparation_confirmation_decision   (确认裁决账本, 16列)
    - plm_stock_preparation_sandbox_*               (沙箱目标, 25列; objectId 由清单给定, 不许自拟)
  permissions: stock-prep:read / :operate / :admin  # 种子化, 零自动授予(R-11)
  views: /stock-prep 确认队列工作台
  configSurfaces:                 # 安装后引导, 不阻塞安装
    - customer pack(装列)  - ext 字段映射  - 只读数据源(走"确认不配置"流程)
  envContract:                    # configure 脚本写入; 值随清单
    - STOCK_PREP_SANDBOX_MODE / STOCK_PREP_SANDBOX_TARGET_OBJECT_IDS
  acceptance:                     # 安装完成的定义
    - dry-run→apply 后 ext_ 列非空 且 human_preserved 列保持空
    - 二次刷新全 skip(幂等)
  posture(只报不改):production Apply 关闭 / K3 永久禁写 / B2a 休眠 / 出站写门未设
```

## 2. 安装 = preflight(查)+ bootstrap(补)+ acceptance(验)

三个组件全部已有或在途:preflight 聚合检查(#5344 线)、幂等 ensure 端点(已有)、合成验收自举(脚本化中)。"安装"按钮只是把三者按清单串起来加进度条。**首次真机部署的两次事故(命名空间自拟、双方表名对不上)就是清单必须存在的理由**:objectId 在清单里,人不再取名。

## 3. 客户旅程(与候选一号拼合)

**装应用(一键)→ 接源(确认不配置,五步)→ 用(确认队列三动作)** ——全程点击与确认,零手工配置、零术语。

## 4. 治理不变量(安装器永不越过)

- 动态代码分发不存在;应用启停不改变任何围栏姿态;
- posture 四项只展示,永无"修复"按钮——安装器不得诱导武装 B2a/出站写/production Apply;
- 真实客户源接入永远走 草案→审核→服务端文件,不因"应用化"而短路;
- 受管表创建幂等且限于应用自己的命名空间(沙箱前缀守卫已实证)。

## 5. 节奏

- **H0(现在)**:首家客户手工走完;preflight + 自举脚本落地——它们就是安装器的前后两半。
- **H1(接管完成后)**:manifest 格式 + 安装页(点击→进度→绿),备料作首个应用做验收样本;判据:安装页产出与首家手工过程等效(同一组 ensure/配置/验收,零人工命名)。
- **H2**:第二个应用(考勤或审批按此模型改造)证明 manifest 的通用性;届时才谈应用列表/按租户开通。

## 11. 应用命名(owner 定名 2026-08-30)与三层标识

清单必须把**标识**与**称呼**分开——前者进代码不可变,后者随部署与客户可改:

| 层 | 值 | 可变性 |
|---|---|---|
| 应用 ID | `stock-preparation` | 不可变(已在代码/路由/文档) |
| **显示名** | **「BOM备料」** | 清单字段;随部署/客户可改(下一家叫「齐套准备」只改一行) |
| 一句话说明 | 「从 PLM 拉取项目 BOM,逐层展开为备料明细;冲突交人工确认,人工列永不被系统覆盖」 | 同上 |

同理,**每张受管表的显示名与每个字段的显示名也属清单字段**,不是事后补丁。首次真机部署的实证:插件建表默认全部落进 `base_legacy`(界面名 "Migrated Base")且字段名为英文模板名——"表存在"与"人找得到、看得懂"是两回事,当日需人工建 base、搬表、改 66 处表头。清单应声明:应用自有 base 名、各表显示名、字段显示名(含语言变体),安装器建表时即就位。

## 12. 客户可以改什么(交付说明必备条目)

系统**没有任何一处按显示名寻址**:字段绑定一律走稳定派生 id(`fld_ = hash(项目, 表对象, 逻辑名)`),apply 用 action 配置里钉死的 `fieldIdMap`,readiness/预检/修复用同一函数计算 id,人工列的墙按 id 拦截,离线派生脚本亦然。实证:66 处表头改为中文后,readiness 与 dry-run 计数逐项不变。

| 客户动作 | 后果 |
|---|---|
| 改字段显示名 / 表显示名 | 零影响 |
| 改 select 选项(材料类型等) | 本就属客户自有(config_info) |
| 改字段类型 | 类型冲突 → **hold 而非写坏**(实证 `SOURCE_VALUE_NOT_A_NUMBER`) |
| 删字段 | readiness 立即 missing(fail-closed);ensure 可补回空列,**历史数据不可恢复** |

因此权限分层是必需的,而不是可选的:**"能填值"与"能改结构"必须是两件事**——首次部署时发现二者在多维表通用路由上是同一档(`canManageFields = canWrite`),即操作员可删列;修复见 `multitable:manage-schema` 分档。证据与报告一律使用逻辑 id(projectNo/totalQuantity),不使用显示名,故客户改名不影响远程支持时的共同词汇。

## 13. 公式属于配置,不属于代码(2026-08-30 owner 提出,查证后确认)

owner 的判断:"既然都是多维表了,公式是不是都可以用多维表来配置?" —— **成立**。多维表自带公式引擎
(`packages/core-backend/src/multitable/formula-engine.ts` 包裹 `src/formula/engine.ts`),函数表含
`DATEADD` / `WORKDAY` / `NETWORKDAYS` / `EDATE` / `LOOKUP` / `ROLLUP` / 跨表引用。于是:

```
需求日期 = DATEADD({总图日期}, -{提前周期}, 'days')      // 自然日
需求日期 = WORKDAY({总图日期}, -{提前周期})              // 工作日
提前周期 = LOOKUP(...)                                    // 按物料类别取自规则表,而非每行手填
```

**这条同时解开了一个设计死结**:`demandDate` / `leadTimeDays` 都在 human_preserved 段,机器写它们即破墙
(T-HUMAN-WALL)。而**公式列是派生列,不属于人工段**,所以"系统算需求日期"不再需要在"破墙"与"把列挪出人工段"
之间二选一。

### 由此划出的分工线(比此前更清楚)

| 能力 | 归属 |
|---|---|
| 行内派生计算(需求日期、各种换算) | **配置**——公式列 |
| 按类别取值(提前期规则) | **配置**——LOOKUP + 规则表 |
| 汇总统计 | **配置**——ROLLUP |
| **BOM 递归展开** | **代码**——多维表无递归 |
| **冲突检测 / 人工确认账本 / 指纹 supersede** | **代码**——治理语义 |
| **PLM 只读同步 + 围栏** | **代码**——源适配与授权 |

原则:**代码只做多维表做不到的事**(递归、外部同步、治理);凡行内计算、跨表取值、汇总,都应是客户可配的公式。

### 两条查证结论(不是推断)

1. **pack 目前不能声明公式列**:`STOCK_PREPARATION_FIELD_TYPES` 冻结为 `string/number/boolean/date/select`,
   无 `formula`。故公式今天只能由客户在装完后自行添加。
2. **客户自加的公式列不会被 apply 冲掉**:写入只覆盖 action 配置 `fieldIdMap` 里的字段,公式列不在其中——
   天然安全,无需额外守卫。

### 工作项(需 owner 排期)

- **F-1 pack 支持 `formula` 类型**:让公式成为应用清单的一部分,而不是装完让客户手动补。会扩大 pack 契约面
  (公式引用的字段必须存在、循环依赖检测、与 apply 的交互),故属独立设计,不是加一个枚举值。
- **F-2「总图日期」来源定义**:需求日期唯一的硬缺口——公式再强也算不出一个不存在的输入。候选:PLM 某列 /
  订单交期 / 人工填。**只有客户能定。**

## 14. 安装页展示默认配置,由客户确认(owner 定,2026-08-30)

安装不是"填表",是"**看默认值并确认**"——与源接入的「确认不配置」同一范式。清单给默认值,安装页摆出来,
客户做选择题:

| 内容 | 安装页 | 理由 |
|---|---|---|
| 表显示名、字段显示名 | **展示,可改** | 模板已给中文默认;客户词汇优先 |
| **选项集**(材料类型 / 毛胚类型 / 备料状态) | **必须确认** | 这是客户自有词汇,我方默认值一定不对 |
| **公式列口径** | **展示建议 + 确认** | 自然日还是工作日?提前期按物料还是类别? |
| 受管表 objectId、权限码 | **只展示,不可改** | 自拟即事故(首次部署两次实证) |
| 围栏姿态 | **只展示,无开关** | 安装器永不诱导武装 |

判据不变:客户全程零填空、每题带默认答案、可一路"下一步"走完,错了在预览里显形而非被表单拦住。

## 15. 客户管理员能做什么(交付说明整节;查证于代码,非推断)

多维表底座的价值正在于此:**客户管理员可以自己加列、加公式,不需要我们改代码**。权限分档见
`multitable:manage-schema`(#5357):**填值与改结构是两件事**——操作员填人工列,管理员改结构。

| 客户动作 | 允许? | 后果 |
|---|---|---|
| 改字段/表显示名 | 管理员 | **零影响**——系统全程按稳定派生 id 寻址,无一处按名字找列(实证:66 处改名后 readiness 与 dry-run 计数逐项不变) |
| **新增公式列** | 管理员 | ✅ **推荐**。自动计算,apply 永不覆盖(写入只覆盖 action 的 `fieldIdMap`)。需求日期、毛胚重量换算等都该走这条 |
| **新增普通列(人工填)** | 管理员 | ✅ 值保留,同步不覆盖 |
| **新增普通列(期待系统填)** | 管理员 | ⚠️ **永远是空的,且无任何报错**——要系统填值须改 ext 映射(服务端受审文件),不是加个列就行 |
| 改字段类型 | 管理员 | 类型冲突 → **hold 而非写坏**(实证 `SOURCE_VALUE_NOT_A_NUMBER`) |
| 删字段 | 管理员 | readiness 立即 missing(fail-closed);ensure 可补回空列,**历史数据不可恢复** |
| 以上任何一项 | **操作员一律不能** | `canManageFields` 已与 `multitable:write` 分离 |

**第四行是唯一的真陷阱**,且与本线踩过的"映射源列缺失 → `ext_` 全空且零报错"同属一类静默失败。风险主要靠
**告知**消解:客户知道规则就不会踩。

### 为什么不在预检里逐列告警(否掉一个自己提过的方案)

预检看不出**意图**:一个空列究竟是"客户想让系统填"还是"他还没填",判据无法写准;而几乎所有客户自加的列
都不在同步映射内,包括完全正常的人工列。逐列告警会**用噪音淹没信号**——一个被习惯性忽略的告警比没有告警更有害。

**正确解法是换时机**:在客户**新建字段的那一刻**提示一次("此列不会被 PLM 同步填充,需系统填值请联系实施")
——一次性、在正确上下文、零噪音。但那要改多维表通用建字段流程,属**跨车道**改动,须走公约,不在本线顺手做。
记为工作项 **S-1**。

## 16. F-2 部分解答:总图日期来自 PLM(owner,2026-08-30)

owner 答复:**总图日期是从 PLM 中获取的一个日期**。据此,F-2 的性质定了——它是**源侧字段**,不是人工填,
也不是订单交期倒推。仍待客户明确的只剩**具体是哪一列**。

### 这个答案带来的三点后果

1. **需求日期成为可配公式**:总图日期一旦作为源列进入备料表,`需求日期 = DATEADD({总图日期}, -{提前周期})`
   就是一条公式列,零代码(见 §13)。提前周期已是人工列,客户可填或用 LOOKUP 取规则表。
2. **需要为总图日期加一个源侧列**:它属 `plm_system` 段(机器写、人不改),须进 pack 的 `ext_` 声明与
   ext 映射;**不是** human_preserved。
3. **仍不宜先加空列**:在客户指明 PLM 源列之前加列,只会得到一个永远空着的字段——正是 §15 第四行那个陷阱。
   **先问,再加**。

> 若该日期维护在图纸/路径属性上而非物料上,请一并说明。)

前置不变:接客户真实 PLM 仍需 T-1 读窗授权与 O3 首条登记;本项定义可先就位,不构成读取。

## 19. BOM备料 引导式配置向导:问题问在流程里,答案由预置与客户字典打底(owner 纠正,2026-08-31)

### owner 的纠正:从"实施问卷"到"系统内配置向导"

我方最初的设计是一份**实施问卷**——部署前请客户方逐题填写口径与映射,再据此手工配置系统。owner 否决:

> "实施问卷意义不大,我们系统部署上去后,就是要配置了。"

纠正的要点不是"问卷这个形式不好",而是**问题该问在哪**:系统一旦部署,配置面本身就是给客户的界面——**问题必须由系统在配置流程内、在需要答案的那一刻提出**,并且**带一个机器算出的草稿答案**,客户做的是确认/修正,不是对着空白表格从头回答。实施交付物因此从"写好的配置"变成"确认过的草案"。

这是 §14"安装页展示默认配置,由客户确认"的延伸,只是把"确认默认值"的范围从**安装期默认值**(表名、字段名、选项集)扩到**源侧语义**本身——映射、词汇、日期口径这些此前被当作"实施先问清楚、再落配置"的东西,现在同样要由系统先出草案、客户在流程里确认,而不是靠一份纸面问卷倒推出配置。同一范式《源接入自助化设计:确认不配置》(`source-onboarding-self-service-design-20260830.md`,候选一号)§2 已定名:"配置(理解对方数据模型→填表)对客户是高成本高错误率动作;认出自己熟悉的数据是近零成本动作。"本节把该范式从"源接入五步流"延伸到备料应用**全部**的实施问题——包括此前需要人工先问清楚的日期口径(§16-§18 的 F-2/F-3)。

### 向导流程(七步,已与 owner 议定)

| 步 | 内容 | 依据 / 备注 |
|---|---|---|
| ① 接源 | 已有配置页,走受管连接 | 复用《确认不配置》五步流的①⑤ |
| ② 探针 | 按厂商预设读结构 + 客户字典表 | 命中预置直接出草案;预置形态见下节"两个在建项" |
| ③ 映射草案逐项确认 | 逐项确认,**每项带 basis 依据**;**未解决项醒目列出,绝不静默省略** | 红线见下 |
| ④ 选项词汇提取确认 | select 类字段(材料类型/毛胚类型等)候选词表,客户点选修正 | 客户自有词汇,我方默认值一定不准(§14) |
| ⑤ 需求日期口径三选一 | A 出图日顺推 / B 交付日期倒推 / C 手排 | owner 已裁 B 为**本客户**口径(§17);向导仍逐户出题——口径因客户而异 |
| ⑥ 自动建公式列 | 按所选口径生成公式,如 `DATEADD({交付日期}, -{提前周期}, "days")` | **F-3**:表达式字符串必须双引号,单引号静默 `#VALUE!`(§18) |
| ⑦ 预检 + 验收 | 已有能力接入向导收尾 | §2 preflight/acceptance |

判据延续 §1/§14 的既有基准:每题带默认答案、可一路"下一步"、错了在预览里显形而非被表单拦住。

### 两个在建项与它们的边界

向导建立在两块独立工作之上,**边界必须分清**:

| 项目 | 做什么 | 不做什么 |
|---|---|---|
| **P2 厂商预置目录** | 编码**怎么发现**——探测该厂商产品的结构特征、字典表位置、join 拓扑、已知坑 | **绝不编码发现到了什么**——schema 结构性禁止承载任何客户取值;预置的身份靠**表结构签名**识别厂商,不靠客户公司名 |
| **P3 向导本身** | 把 P2 吐出的草案接入上面七步交互,呈现 basis、收集确认 | 不定义"怎么探测"——探测逻辑全部在 P2;P3 依赖 P2 的输出形状 |

**P3 尚未启动,等 P2 落地**:向导要渲染的每一屏(映射草案、basis、未解决项列表)都由 P2 的输出形状决定,形状不定,向导没法先做。

两项均**在途**:P2 见分支 `feat/stock-prep-vendor-presets`;P3 见分支 `feat/source-probe-draft-emitter`——本节记录的流程与边界即两者的实现依据。

### 红线:不猜语义

机器出的草案只能来自两个来源:**编码好的厂商知识(P2 预置)** + **客户自己的字典表**——**绝不从列名猜语义**。列名不可靠已有实证:客户 PLM 的列名本身零语义,真实含义分散在若干张字典表里,DDL 对这类系统无效;《确认不配置》§9 首家客户实证同样显示——扩展列 36 列中 30 列无语义占位,字典启用极稀。**猜出来的映射是一场静默的错位灾难**:错误不报错,只产出错误数据(《确认不配置》§7)。因此:

- basis 缺失 = 该项**不生成**草案,进入未解决列表,**不得静默省略**;
- 未解决项必须在 ③ 醒目列出,客户看得见"系统不知道"这件事本身,而不是被悄悄跳过;
- 探测/提议阶段零业务行,真值样本只在受管预览里出现(《确认不配置》§7 治理不变量,直接沿用)。

### 经济性:做一家赚一家

- **同厂商第二家客户**:探针命中已有预置,向导跑完①-⑦,目标成本 **≈1 个确认日**(相较首家客户的专家式发现,3-5 人日)。省下的是"重新摸索结构"那部分,不是"客户确认"那部分——确认仍然要做,只是从专家工作变成客户点选。
- **新厂商第一家客户**:仍要付探索成本(手工 + 内置分析产出预置雏形,《确认不配置》§5-§6);但产出不是一次性成果,而是**下一条预置**——摊销到下一家同厂商客户身上。飞轮成立的前提是上面的红线不破:预置里不能带有这一家客户的东西,否则"做一家赚一家"会退化成"做一家只赚这一家"。
