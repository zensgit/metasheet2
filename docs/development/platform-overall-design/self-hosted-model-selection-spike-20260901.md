## 0. 一句话结论

**首选:Qwen2.5-32B-Instruct(AWQ INT4 量化),单卡 48GB 显存——中国大陆合规可采购型号是 L20(48GB,L40S 面向中国市场的合规替代型号),vLLM 起 OpenAI 兼容端点。** 备选(硬件更省、首次落地更稳):Qwen2.5-14B-Instruct(AWQ INT4),单卡 24GB(RTX 4090D,RTX 4090 的中国市场合规版本)即可。**原版 L40S 与原版 RTX 4090 均在美国对华出口管制范围内,不是中国大陆的合规可采购型号**(详见 §4.3)。国产化可选路线:华为昇腾 910B(生态不是 CUDA/vLLM 的直接替换,需改用 MindIE/CANN 推理栈,见 §4.3)。跨家族备选:DeepSeek-R1-Distill-Qwen-32B(需要更强显式推理链时)或 GLM-4-9B-Chat(客户已有智谱生态时——注意 GLM-4-9B 本身发布已有一段时间,属于偏旧的稳妥后备选择,采购时应核实智谱是否已有更新一代同量级模型)。

四类任务(schema 映射建议、BOM 变更影响摘要、自然语言转多维表筛选/视图、报错与下一步解释)全部是**咨询性、RAG grounded、人工确认后才落库**的任务,不需要前沿模型的长尾世界知识或复杂多步自主推理——中等规模开源模型 + 客户自己的字典/历史决策做检索增强,大概率够用。这正是本 spike 的判断依据,也是它作为"待验证假设"而非"已验证结论"的原因。

单机单卡在默认档位下**足以支撑单客户部署**(见 §7.3 的并发推演);多工厂/高并发客户才需要升到双卡档位(见 §8)。

## 1. 背景与约束复述

- 客户:内网部署的中国制造业客户,BOM/图纸/采购数据**不能出网**——这排除了任何调用云端 API(包括调用 Anthropic/OpenAI 云端接口)的方案,唯一路径是在客户内网 GPU 机器上**自托管**一个开放权重模型。
- **开放权重、拿来即用、不训练不微调**——选型必须落在 Qwen / DeepSeek / GLM 这类可离线下载、许可证允许商用自托管的模型家族;不考虑任何需要客户数据参与训练/微调的路径(既不必要,也会把"数据不出网"的边界从"推理"进一步收紧到"训练基础设施",复杂度不成比例)。
- 四类 AI 任务全部**咨询性**(建议,不直接落库)、全部**由 RAG 接客户自己的 schema/字典/决策历史做 grounding**、全部在 metasheet 既有的人工确认后写入流程之下(§6 展开)。这三条共同决定了"中等规模模型 + 好 RAG"是一个合理的起点假设,而不是需要去够千亿参数闭源模型的任务形状。

## 2. 四类任务复述与具体样例

| 任务 | 输入 | 输出 | 对模型能力的要求 |
|---|---|---|---|
| ① schema 映射建议 | 客户源系统里语义为零的列名(如 PLM 侧的 `Bom_ExAttr1`)+ 检索到的字段字典/同类列历史映射 | 建议这一列的业务含义 + 推理依据(为什么这么猜) | 中文理解 + 结构化检索结果的归纳 + 可解释的简短推理,不需要长链条数学/代码推理 |
| ② BOM 变更影响摘要 | 一次 BOM 改动(增/删/替代料)+ 检索到的上下游用料关系 | 用自然语言概括"这次改动影响了什么" | 中文摘要能力 + 对检索到的结构化关系做归纳,不需要自主多步骤规划 |
| ③ 自然语言 → 多维表筛选/视图 | 用户的中文自然语言诉求 | 结构化的筛选/视图定义(JSON 一类) | 强指令跟随 + 可靠的结构化输出(JSON 格式稳定性比"聪明"更重要) |
| ④ 报错/下一步解释 | 系统报错文本 + 检索到的相关文档/历史处理记录 | 用自然语言解释报错含义 + 建议下一步 | 中文解释能力 + 检索结果的忠实转述,不需要跳出检索范围"创造"解决方案 |

一个真实存在于本仓库、可以直接拿来当 schema 映射任务示例的例子:备料线 BOM 展开代码里,数量取自 `Bom_ExAttr1`——一个源系统裸列名(`plugins/plugin-integration-core/lib/stock-preparation-bom-expansion.cjs:221`)。这类"列名零语义、含义散落在源系统自己的字典表里"的情况,正是任务①要解决的问题:模型不需要"知道"这个客户的 ERP 内部约定(不可能知道,也不该训练进权重),它需要的是把检索到的字典条目(列名 → 业务含义 → 示例值)组织成一句人话建议,并标注置信度供人工确认——这是一个总结/归纳任务,不是知识问答任务。四类任务共同的形状都是"检索到的结构化信息 → 自然语言/结构化归纳",这进一步支持"不需要前沿模型"的判断。

## 3. 模型选型

### 3.1 候选总览(量级估算,采购前核实官方最新版本与许可证原文)

| 家族 / 型号 | 参数量 | 许可证(据我了解,需在采购前核实原文) | 原生上下文 / 可扩展 | 定位 |
|---|---|---|---|---|
| **Qwen2.5-14B-Instruct** | 14B(稠密) | Apache 2.0 | 32K(YaRN 可扩展至 128K) | 备选 / 小档位首选,单卡 24GB 舒适跑 |
| **Qwen2.5-32B-Instruct** | 32B(稠密) | Apache 2.0 | 32K(YaRN 可扩展至 128K) | **首选**,单卡 48GB 稳妥跑 |
| Qwen2.5-72B-Instruct | 72B(稠密) | Qwen License(commercial 但有 >1亿 MAU 通知条款,单客户部署基本不触发) | 32K(YaRN 128K) | 大档位候选,需双卡或 80GB 单卡 |

### 3.2 为什么是 Qwen2.5/Qwen3 的 14B/32B 档位

1. **中文能力**:Qwen 系列由阿里云训练,中文语料占比与中文指令微调投入在开源模型里长期处于第一梯队,官方披露的中文基准(C-Eval/CMMLU 一类)分数在开源模型中名列前茅,这对四类任务全部用中文交互、且要理解制造业/PLM/BOM 领域术语这件事很关键。
2. **指令跟随 + 结构化输出**:任务③(NL→筛选)本质是"稳定产出合法 JSON/DSL"的任务,Qwen2.5/3-Instruct 系列在指令跟随基准上的表现支持这一点;真正要验证的是量化后(AWQ INT4)结构化输出的稳定性有没有明显退化——这是 §9 负载测试要专门盯的一项。
3. **上下文长度**:RAG 场景下 prompt = 系统提示 + 检索到的字典/历史条目(可能几千 token)+ 用户输入,32K 原生上下文对四类任务都绰绰有余,YaRN 扩展到 128K 是留出的余量而非刚需。
4. **许可证**:14B/32B 两档是 Apache 2.0,商用自托管无额外条款(不像 72B 档位背着通知义务条款,虽然单客户部署大概率不会触达那个体量阈值,但 Apache 2.0 更省心,不需要法务额外过一遍)。
5. **量化生态成熟度**:Qwen 官方直接发布 AWQ/GPTQ-Int4/Int8 量化权重(不需要自己量化、自己踩量化配方的坑),vLLM 对 Qwen 系列的支持是主线维护对象,组合风险最低。

### 3.3 首选 + 备选定案

- **首选:Qwen2.5-32B-Instruct-AWQ**(或压测验证后升级到 Qwen3-32B-AWQ——建议两个都拉进 §9 的负载测试对照,谁在客户真实 prompt 分布下延迟/结构化输出稳定性更好用谁)。定位默认档位(§8),单卡 48GB。
- **备选(小档位/首次落地更保守的选择):Qwen2.5-14B-Instruct-AWQ**。单卡 24GB(消费级卡即可),延迟更低、显存余量更大、并发能力更好;代价是复杂案例(如需要综合多条检索结果做判断的 schema 映射)质量可能略逊于 32B。建议客户首次上线从 14B 起步、验证质量满足预期后再决定是否升级到 32B,而不是一步到位买大卡。
- **跨家族备选**:客户领域推理链需求突出(如 BOM 变更影响需要更长的显式因果推导)→ DeepSeek-R1-Distill-Qwen-32B;客户已有智谱生态或强调超长上下文→ GLM-4-9B-Chat / GLM-4.5-Air。这两条备选不作为默认路径,仅在首选家族出现意外阻塞(如某型号的 vLLM 支持临时退化、量化权重质量问题)时启用。

### 3.4 明确排除

- 任何闭源云端 API(Anthropic/OpenAI/字节/百度千帆等)——违反"数据不出网"的硬约束,不在候选范围。
- DeepSeek-V3/R1 旗舰(671B MoE)——不满足单机/小规模 GPU 盒子的硬件约束,排除。
- 任何需要微调/继续预训练的路径——任务需求本身是拿来即用+RAG,不需要;微调还会把"数据不出网"的边界从推理扩大到训练算力与训练数据管理,复杂度不成比例。

## 4. GPU / 硬件选型

### 4.1 显存预算方法(公式 + 量级示例,非精确值)

单卡显存需要覆盖三块:**模型权重 + KV cache + 推理框架的激活/调度开销**。

**模型权重**(按量化精度,近似值):

| 量化 | 每参数字节数(近似) | 32B 模型权重显存(近似) |
|---|---|---|
| FP16 | ~2 字节 | ~64GB |
| INT8 | ~1 字节 | ~32GB |
| AWQ/GPTQ INT4 | ~0.55–0.65 字节(含分组量化的 scale/zero 开销) | ~18–20GB |

**KV cache**(每 token 显存 ≈ 2(K+V)× 层数 × KV 头数 × head_dim × 精度字节数;用了 GQA 分组查询注意力的模型 KV 头数远小于总注意力头数,显存占用会小很多)。以一个 32B 量级、64 层、8 个 KV 头、head_dim 128 的架构为例(仅作方法示例,不代表任何具体型号的确切架构参数):每 token ≈ 2×64×8×128×2 字节 ≈ 256KB。若单请求上下文 8K token、并发 8 路,KV cache 总量 ≈ 8K × 8 × 256KB ≈ 16GB。

**结论**:32B 模型 AWQ INT4 权重(~19GB)+ 中等并发下的 KV cache(个位数到十几 GB,取决于并发路数与上下文长度)+ 框架开销,**单卡 48GB 是稳妥选择**,24GB 卡能跑但 KV cache/并发余量很紧(建议只在低并发的小档位场景用,且把最大上下文长度、并发数都主动限制住,不要留给 vLLM 自由竞争显存)。14B 模型 AWQ INT4 权重(~8–9GB)在 24GB 卡上则余量充足。

### 4.2 量化选项

- **AWQ(Activation-aware Weight Quantization)**:vLLM 一等公民支持,推理时无需额外反量化开销(权重本身以低精度存储、激活时按需处理),Qwen 官方直接发布 AWQ 权重,是本 spike 的**默认量化方案**。
- **GPTQ**:效果与 AWQ 接近,vLLM/大多数框架同样支持,可作为 AWQ 权重缺失时的备选量化格式。
- **INT8 / FP8**:精度损失更小,但显存/吞吐收益不如 INT4 明显;仅在压测发现 INT4 下结构化输出(任务③)稳定性不达标时,作为"退一步"的选项考虑。
- **不建议**:自己从 FP16 现场量化——用官方已发布并经社区验证过的量化权重,避免把"量化配方对不对"变成额外的风险变量。

### 4.3 推荐硬件(单卡为主,中国大陆合规可采购型号)

**先纠正一个错误**:本文早期版本曾把 **L40S** 与 **RTX 4090** 列为首选/备选硬件,这是错的——这两款卡本身都在美国对华出口管制范围内(2023 年 10 月管制收紧后,基于算力密度阈值,L40S、RTX 4090 与 A100/H100 一样都被列入需要许可证才能出口中国大陆的清单,不是只有 A100/H100 这类数据中心旗舰卡受限)。继续推荐这两款型号,客户采购部门的合规尽调一天之内就能发现,是会造成客户尴尬/信任受损的实质性错误,必须改为下表的中国市场合规可采购型号:

| 档位对应 | GPU(中国大陆合规型号) | 显存 | 说明 |
|---|---|---|---|
| 备选模型(14B) | **RTX 4090D**——英伟达专为满足中国出口管制阈值削减规格后针对中国大陆销售的型号,不是原版 RTX 4090 | 24GB | 消费级卡即可,性价比最高,适合首次落地/试点 |
| 首选模型(32B) | **L20**——L40S 面向中国市场的合规替代型号,同样是数据中心卡定位(ECC、企业级驱动支持) | 48GB | 本文实际推荐的可采购型号;§4.1 的显存预算方法(32B AWQ INT4 权重 ~19GB + 中等并发 KV cache ~16GB)照常适用,48GB 显存的结论不变,只是承载它的具体型号从 L40S 换成 L20 |
| 大档位(72B / GLM-4.5-Air 一类) | 2× L20(张量并行)或单卡 **H20**——A100/H100 面向中国市场的合规替代型号(高显存、算力按管制阈值削减,具体显存版本以采购时市场在售规格为准) | 96GB+ | 见 §8 大档位,超出"单机单卡"的默认框架,需要客户真实并发数据支撑才值得投入 |
| **国产化路线(可选)** | 华为**昇腾 910B** | 视具体型号 | 完全国产、不受美国出口管制约束的路线,但**生态不是 CUDA/vLLM 的直接替换**——本文 §5 描述的 vLLM 起 OpenAI 兼容端点、AWQ 量化生态、社区量化权重可用性,全部建立在 CUDA/vLLM 假设之上;昇腾栈要换成华为 **MindIE 推理框架 + CANN 计算架构工具链**,模型是否有昇腾适配版本、量化方案是否等价、OpenAI 兼容端点是否需要额外适配层,都需要单独验证,验证成本明显高于英伟达合规卡路线。仅在客户对国产化有明确合规/政策要求时,才建议优先评估这条路线而不是默认选择 |

**中国大陆出口管制现实约束(必须现场核实,本文不承诺具体可采购型号,政策本身也可能变化)**:出口管制适用的具体 SKU 是 **L40S、RTX 4090、A100、H100** 这一组型号,不是笼统的"数据中心卡"或"A100/H100 一类"——消费级的 RTX 4090 同样在管制清单里,不能假设"管制只影响数据中心卡"。上表列出的 **L20 / RTX 4090D / H20** 是英伟达针对中国市场推出的合规替代型号,是本文实际建议采购的目标;这几款型号的具体可采购状态、货期、是否会随出口管制政策进一步收紧而调整,仍然需要在采购前与本地渠道核实,不能假设本文列出的型号届时一定有货。若英伟达合规卡路线整体受阻,国产昇腾 910B 是另一条路径(见上表),但要为其生态适配单独规划验证时间,不能当作即插即用的平替。

### 4.4 单机粗略 BOM(默认档位,量级估算,非报价)

## 5. 服务栈

### 5.1 选型:vLLM 为主,Ollama 为小档位/POC 补充

| 方案 | 定位 | 理由 |
|---|---|---|
| **vLLM** | 默认/大档位的生产服务引擎 | PagedAttention + continuous batching,多并发下吞吐/显存利用率最好;原生支持 AWQ/GPTQ/FP8 量化;`python -m vllm.entrypoints.openai.api_server` 直接起一个 **OpenAI 兼容端点**(`/v1/chat/completions`、`/v1/completions`),不需要额外写适配层 |
| **Ollama** | 小档位/POC/演示 | 单命令部署,GGUF 量化生态成熟,对不熟悉 GPU 推理运维的现场 IT 最友好;近期版本也提供 OpenAI 兼容的 `/v1/chat/completions` 兼容层;高并发下吞吐不如 vLLM,不建议作为默认档位/大档位的生产选择 |
| TGI(Hugging Face Text Generation Inference) | 备选 | 能力与 vLLM 接近(continuous batching、量化支持),但生态成熟度/社区量化配方丰富度略逊于 vLLM+Qwen 的组合,许可证也经历过变化,建议只在 vLLM 遇到具体阻塞时评估 |

**结论**:默认档位/大档位用 vLLM 起 OpenAI 兼容端点;小档位/首次给客户做演示时可以先用 Ollama 快速起一个可用的版本,验证价值后再切到 vLLM 做生产部署——两者输出端点形状足够接近,切换成本低。

### 5.2 与 metasheet 既有 AI provider 边界的对接(关键发现)

这是本 spike 里最值得单独强调的一点:**metasheet 已经有一层 provider-agnostic 的 AI 服务边界,自托管模型不需要新造一层协议适配,只需要把现有边界的"第三个 provider"接上去。**

现状(已实现,非设计稿):

- `packages/core-backend/src/services/ai-provider-readiness.ts:56` 声明 `AI_PROVIDER_ALLOWLIST = ['anthropic', 'openai']`,`:63-78` 声明每个 provider 各自的模型允许表(`AI_MODEL_ALLOWLISTS`)。
- `packages/core-backend/src/services/ai-provider-client.ts:236-238`:实际发请求时,`baseUrl` 取 `MULTITABLE_AI_BASE_URL`(未设时才回落到云端默认地址),请求路径对 `openai` provider 固定拼成 `${baseUrl}/v1/chat/completions`,鉴权用 `Authorization: Bearer <key>` header。

这意味着:**把 `MULTITABLE_AI_PROVIDER=openai` + `MULTITABLE_AI_BASE_URL` 指向内网 vLLM 服务地址,协议层零改动**——vLLM 的 OpenAI 兼容端点实现的正是这套 `/v1/chat/completions` + Bearer 鉴权的形状。

但要真正把自托管模型接入,还有两处需要一个后续实现 PR(本 spike 范围之外,列出来是为了让下一步的工作量可见):

1. **模型允许表**:`AI_MODEL_ALLOWLISTS.openai`(`ai-provider-client.ts` 同侧 `ai-provider-readiness.ts:72-77`)目前只列了云端 GPT 系列型号名,需要把选定的自托管模型 served 名字(如 `qwen2.5-32b-instruct-awq`)加进去——或者更干净的做法是新增一个独立的 provider key(如 `self-hosted`),避免语义上和 OpenAI 云端 API 的成本/限流假设混在一起;这是个小决策,留给实现 PR 定。
2. **价格表**:`AiModelPrice` 表(`ai-provider-client.ts:71-82`)里,`preflight()`(`:201-209`)对不在价格表里的型号**会硬阻断**("refusing to spend unaccounted tokens")——这是既有的"不静默 $0"安全属性,自托管模型同样需要一行价格表条目,合理的做法是显式记 `$0`(或反映 GPU 盒子折旧的一个名义数字)并加注释说明这不是按 token 计费、而是资产折旧口径,而不是让这条防护被绕过。

好消息是:**人工确认后写入的 review-before-write 网关、脱敏管道、reserve-then-settle 配额系统都是 provider-agnostic 的**——只要自托管服务说的是 OpenAI chat-completions 协议,这些既有机制不需要为第三个 provider 单独改造(见 §6 caveats 部分对 review-before-write 网关的引用)。

### 5.3 离网/内网安装运维要点

- **权重与依赖的离线搬运**:在有互联网的准备机上下载模型权重(含量化版本)、embedding/reranker 模型、vLLM 及其依赖,做校验和(checksum)记录,通过客户认可的离线介质(如加密硬盘)按客户数据出入流程搬入内网——内网 GPU 机器本身不应该有出网权限,这是"数据不出网"约束的镜像面(内网机器也不该被反向污染)。
- **版本锁定,无自动更新/无遥测**:把模型权重版本、量化版本、vLLM 版本、CUDA/驱动版本都写进一份部署清单里锁定;关闭任何可选的使用统计/遥测上报(vLLM 等框架通常有可关闭的匿名统计开关,内网离线环境下这类上报本来就发不出去,但显式关闭更干净、也避免启动时的无意义超时等待)。
- **服务化**:以 systemd 服务或容器(带重启策略)运行,暴露健康检查端点;GPU 驱动/CUDA 版本需要对照 vLLM 支持矩阵提前验证,离线环境打补丁慢,建议保留上一个已知良好的容器镜像作为回滚路径。
- **日志与审计**:请求/RAG 检索日志可能包含客户 BOM/schema 原文,属于敏感客户数据,需要按 metasheet 既有的日志脱敏惯例处理(参考 `packages/core-backend/src/multitable/automation-log-redact.ts` 的脱敏模式)、设定合理的本地留存期限,而不是无限期堆积在 GPU 机器本地磁盘上。
- **监控**:GPU 显存占用/利用率/温度、并发请求数与排队深度、p50/p95 延迟——这类监控可以复用仓库里已有的"声明式就绪门"套路(`ai-provider-readiness.ts` + `scripts/ops/multitable-ai-readiness-gate.ts` 的模式),给自托管服务做一个对应的健康门脚本,是自然的下一步实现 PR,本 spike 不展开设计。

## 6. RAG 方案

### 6.1 核心判断:护城河是喂进去的数据,不是模型本身

四类任务的质量上限主要由**检索到什么**决定,而不是模型参数量——这也是"中等规模模型 + 好 RAG"这个假设成立的前提。RAG 索引的内容应该包括:

1. **客户字段字典 / schema 语义映射**:客户源系统的裸列名 → 业务含义 → 示例值(§2 的 `Bom_ExAttr1` 例子)。这类字典客户侧本来就存在(散落在多张字典表里,如 stock-prep 线已知的现状),RAG 要做的是把它们结构化索引起来,而不是让模型"记住"。
2. **metasheet 侧已经人工确认过的历史映射决策**:这是**最高置信度**的 grounding 素材——review-before-write 网关确认过的结果比字典表原始条目更值得信任,应该优先检索、并在 prompt 里明确标注"这是人工已确认的先例"。
3. **BOM 变更历史/上下游用料关系**:供任务②检索。
4. **报错/排障知识**:供任务④检索;起步阶段如果没有专门的知识库,可以先从代码里的错误信息文案 + 现有排障文档起步,逐步沉淀。

### 6.2 Embedding 模型:同样自托管

- **首选:BGE-M3**(北京智源 BAAI 出品):多语言(含中文)、多粒度(句子/段落)、支持稠密+稀疏混合检索,原生支持长达 8192 token 的输入,MIT 一类许可证,模型体量小(约 5–6 亿参数),CPU 上就能跑出可接受的检索延迟,不需要额外占用 GPU 资源(GPU 优先留给生成模型)。
- **可选(检索质量优先场景):BGE-reranker-v2-m3** 做二阶段重排——对任务①(schema 映射建议)这种检索质量直接决定输出质量的任务值得加一段重排延迟;对任务③(NL→筛选,追求短平快)可以跳过重排,直接用一阶段检索结果。
- **备选**:如果客户对更大 embedding 模型的检索质量有更高要求,可评估 `gte-Qwen2` 系列(体量更大、质量更高,但也更占资源),按需升级而非默认选择。

### 6.3 向量存储:优先复用现有 Postgres,而不是新起一个向量数据库服务

`packages/core-backend/package.json:64` 显示后端已经依赖 `pg`(`"pg": "^8.11.3"`)——说明 Postgres 已经是平台既有的数据库。对单客户量级的字典/决策历史/BOM 关系(大概率是几万到几十万行级别,不是十亿级),**pgvector 扩展**是最简单的选择:不需要在内网离线环境里新增一个独立的、需要单独运维/备份/权限体系的有状态服务,备份/恢复/权限可以直接复用平台现有的 Postgres 治理方式。只有当索引规模真的增长到 pgvector 力不从心的量级(单客户场景大概率不会),才值得引入专门的向量引擎(如 Qdrant,同样可自托管)。

### 6.4 检索策略与租户隔离

- 默认走**混合检索**(向量相似度 + 关键词/BM25),对 schema 映射这类术语敏感的任务尤其重要(客户内部术语的字面匹配有时比语义相似度更可靠)。
- 每条检索结果在 prompt 里都应该带上**来源标注**(哪张字典表、哪条历史决策、置信度/是否人工确认过)——这既是为了模型输出的可解释性(任务①明确要求"带推理依据"),也是为了配合既有的人工确认后写入网关:人工确认时能看到"模型是基于什么检索结果做的建议",而不是一段不可追溯的生成文本。
- **RAG 索引必须按客户/租户隔离,不做跨客户共享检索**——这是"数据不出网"约束在检索层的自然延伸,也和平台已有的 AI 功能租户隔离先例(`multitable-ai-l05-tenant-scoped-live-gate-designlock-20260707.md`)方向一致。本 spike 不假设、也不建议任何跨客户的知识共享路径。
- 索引更新:字典/决策历史变化时增量重新 embedding,不需要全量重建;更新频率低(字典变化不频繁),对索引新鲜度的要求不高。

## 7. 成本与延迟包络

### 7.1 GPU 盒子成本(量级,见 §4.4 明细)

- 小档位(14B + RTX 4090D):约 ¥25,000–40,000
- 默认档位(32B + 48GB 卡):约 ¥70,000–130,000
- 大档位(72B 级 / 双卡):见 §8,量级上一个数量级(约 ¥250,000+)

### 7.2 延迟量级估算(按任务)

以默认档位(32B AWQ INT4,单卡 48GB,vLLM)为量级参考,**这些数字是估算,不是跑分结果**:

| 任务 | 典型输入长度 | 典型输出长度 | 延迟量级(单请求,未排队) |
|---|---|---|---|
| ① schema 映射建议 | 中(检索结果 + 待映射列) | 短-中(建议 + 推理依据,~200–400 token) | 约 3–8 秒 |
| ② BOM 变更影响摘要 | 中-长(变更详情 + 上下游关系检索) | 中(摘要,~300–500 token) | 约 5–10 秒 |
| ③ NL → 筛选/视图 | 短(用户自然语言) | 短(结构化 JSON,~50–150 token) | 约 1–3 秒 |
| ④ 报错/下一步解释 | 短-中(报错文本 + 检索结果) | 短(~150–300 token) | 约 2–5 秒 |

这些量级对"点一下按钮、等一个建议"的咨询型副驾交互是可接受的——不是要做逐字流式打字机式的实时对话体验(即便做流式输出,首字延迟也在这个量级内,用户能更快看到反馈)。**具体数字必须用客户真实 prompt 长度分布(尤其是检索结果注入后的实际 prompt 长度)在真实硬件上复核**,本表只用于判断"量级是否在可接受区间",不能当作 SLA 承诺。

### 7.3 单客户部署,一块 GPU 够不够?

**大概率够。** 推演依据:

- 单个制造业工厂的 AI 副驾用户规模大概率是几十人量级,且这四类任务是"偶尔点一下"的咨询性交互,不是持续对话式聊天——真实的**峰值并发生成请求数**大概率是个位数到十几(而不是互联网级的成百上千并发)。
- vLLM 的 continuous batching 在这个并发量级下,单卡 48GB 跑 32B AWQ 模型是有余量的(§4.1 的 KV cache 估算显示中等并发+中等上下文长度的 KV cache 占用是个位数到十几 GB,权重占用固定 ~19GB,48GB 卡有明显余量)。
- 因此:**默认档位单卡足以支撑单客户部署**;只有当客户规模明显超出"单工厂"(如多工厂集中部署同一套服务、或并发用户量远超预期)时,才需要考虑大档位的双卡方案(§8)。

这一条判断同样属于"待验证假设"——§9 的负载测试应该专门用客户预期的真实并发数去压一次,而不是只测单请求延迟。

## 9. 诚实的差距(caveats)

### 9.1 自托管中等规模模型相对前沿闭源模型,会在哪些地方明显弱

- **复杂多步自主推理/规划**:如果未来任务扩展到"自主执行多步操作"而不是"给建议",中等规模开源模型的可靠性会明显落后于前沿闭源模型。当前四类任务都是单轮咨询,这个差距不构成实际问题。
- **长尾世界知识**:开源中等规模模型的预训练知识密度不如更大模型,遇到检索之外、需要模型"自己知道"的冷门事实时容易出错或编造。这正是本方案**强依赖 RAG**、而不依赖模型自身记忆的原因——把"知识来源"从模型权重转移到检索到的客户自有数据,模型只负责组织语言和归纳,天然规避了这个弱点。
- **量化带来的轻微精度损失**:AWQ/GPTQ INT4 相比 FP16 通常有小幅(个位数百分比量级)的精度损失,指令跟随/结构化输出的稳定性比纯问答类任务更敏感——这是任务③(NL→筛选,依赖稳定 JSON 输出)需要在负载测试里专门验证的点。
- **中文以外的多语言场景、专业代码生成/复杂数学**:不在四类任务范围内,不展开评估。

### 9.2 为什么这些差距对这四类任务是可接受的

- **全部咨询性、不直接落库**:四类任务的输出都是"建议",不是自动执行的操作。
- **全部人工确认后才写入**:平台已有的 review-before-write 机制(`docs/development/multitable-ai-bulk-fill-review-before-write-designlock-20260621.md` 描述的"生成建议值 → 展示 diff → 人工确认 → 才落库"网关)不是为这个自托管方案新造的,是既有的、生产已验证的机制——中等规模模型即便偶尔给出不够精准的建议,人工确认这道门本来就假设了"模型建议不总是对的",不依赖模型输出 100% 正确。
- **全部 RAG grounded**:模型的角色被限定在"组织检索到的客户自有数据"而不是"自由发挥",压缩了幻觉的空间。
- 因此:一个会犯错但错误可被人工快速识别、且犯错代价被网关兜住的模型,配合数据不出网的硬约束,是这个场景下合理的权衡——**不是"够好",而是"在人工确认网关下,够好这件事本身的容错空间更大"。**

## 10. 待验证事项 / 下一步(采购前必须做)

1. **真实负载测试**:用客户真实(或高度仿真)的 schema 字典规模、BOM 复杂度、并发用户数,在候选硬件(至少默认档位)上实测 §7.2 的延迟表与 §7.3 的并发假设,而不是照抄本文的估算数字。
2. **量化后结构化输出稳定性专项验证**:针对任务③(NL→筛选),专门测 AWQ INT4 量化后 JSON 输出的合法率/稳定性,如果不达标,评估 INT8 或更保守的量化方案。
3. **Qwen2.5-32B vs Qwen3-32B 平行对照**:两个都拉进负载测试,用客户真实 prompt 分布决定最终选型,而不是仅凭本文的定性判断拍板。
4. **provider 边界的后续实现 PR**(§5.2):扩展 `AI_MODEL_ALLOWLISTS`(或新增 `self-hosted` provider key)+ 价格表条目,这是把自托管模型真正接入 metasheet AI 服务边界的最后一步代码工作,不在本 spike 范围内。
5. **中国大陆 GPU 采购现场核实**(§4.3):数据中心级卡的可购买型号/货期受出口管制影响,采购前需要与本地渠道确认。
6. **许可证原文复核**(§3.1 表格标注处):选定型号后,采购前打开官方仓库核对当前许可证原文,不要依赖本文的"据我了解"。
