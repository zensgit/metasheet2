# BOM备料:我们系统的做法(定稿,2026-08-31)

> 56 项 legacy 业务盘点完毕、owner 全部裁决后的定稿。一页说清:数据怎么来、怎么管、人怎么用、
> 什么不做。后续实现以本页为准;修改须 owner 裁决。

## 一图流

```
PLM(只读,按钮触发)
  → 同步 + BOM 展开(数量累乘)
  → 快照批次 + 差异(added/removed/数量变/版本变)
  → 有冲突?→ 确认账本 → 确认队列(人工裁决)
  → 落入 备料表(多维表)
       ├─ 系统列(plm_system):机器写,人不改
       ├─ 人工列(human_preserved):人写,机器永不覆盖 ← 人工列墙
       └─ 公式列:需求日期 = 交付日期 − 提前周期(B 口径,配置非代码)
  → 生产/采购/仓库各用各的角色视图,行内编辑、实时协同、导入导出
```

## 十条做法

1. **数据源**:PLM 直连只读,按钮触发刷新(legacy 亦无定时任务,等价);每次刷新落快照批次,批次间差异可追;
2. **变化治理**:差异与冲突**先裁决后落数**(确认队列),这是我们对 legacy"直接覆盖+人肉核对"的根本升级;
3. **人工产权**:人工列墙——机器永不碰人填的格子;刷新/重装/升级都不例外(66 处改名 + 真机验证背书);
4. **计算即配置**:行内计算一律公式列(需求日期已真机验证);代码只做多维表做不到的(递归展开/外部同步/治理);
5. **角色即视图**:生产/采购/仓库 = pack 角色视图 + 列权限,不再自研权限五层(legacy 的批量覆盖缺陷在我们形态下不存在);
6. **权限三档**:操作员填值;管理员改结构(表头/表名/库名/删表——软删可恢复,在途 PR);安装归平台管理员;
7. **交付两个 pack**:项目备料(已在)+ 通用件备料(按任务单号,待配)——第二个 pack 是"配置即接入"的首个验证;
8. **安装即自证**:BOM备料 应用 = 安装页(默认值确认)+ 预检(7 阻塞码)+ 验收(两判据);实施走向导(P2 预设 + P3 草案确认);
9. **协同**:部门互相通知(legacy 用钉钉待办)近期以多维表评论+通知承接;远期对接**自家审批流程**(B 机车道,另出移交件);
10. **边界(不做,均有裁决)**:K3 一切写入永久禁(G-4;盘点证实 legacy 亦未跑通);MRP 不做;**工艺暂不做(客户在宜搭上做)**;**宜搭推送暂不做**(需要时导出对接);死数据层不移植。

## 与 legacy 的一句话对比

legacy 是"一套自研全家桶 + 三方直连 + 按钮驱动";我们是"**多维表平台 + 一个薄同步插件 + 配置**"——
平台吃掉了它 60% 的自研代码,治理层(裁决/围栏/审计)是它没有的,剩下的都是配置。
