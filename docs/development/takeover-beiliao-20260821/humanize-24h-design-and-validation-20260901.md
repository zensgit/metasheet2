## 三、核心案例:K3 围栏——对抗验证不止抓 bug,它逼出了正确的设计

G-4"永久禁 K3 外部写"是对客户最硬的安全承诺。这道围栏被对抗验证打了**四轮、击穿四次**:

| 轮 | 做法 | 击穿方式(均实跑证实) |
|---|---|---|
| 1 | 拦 K3 的 kind | 包装成 sqlserver kind 绕过 |
| 2 | 按目的地拦(查结构化 insert(表)) | 原生 `query('INSERT INTO t_ICItem')` 绕过 |
| 3 | 解析 SQL 找写目标 | `UPDATE...FROM` / `TOP` / 4段名——普通 T-SQL 就破 |
| 4 | 换架构:K3 连接只读 | CTE 打头写骗过白名单;链接服务器跳 K3 检测不到 |

**四轮逼出的真相(方法论价值)**:一个允许"任意写 SQL 到任意目的地"的通用数据源,**应用代码无法可证明地保证永不写 K3**——目的地能被链接服务器/同义词/动态 SQL 洗掉,语句能混淆到任何解析器之外。这是这类边界的数学限制,不是代码不够好。铁证:我方纯读判定与路由现成 `isReadOnlySql` 字节相同,而后者自己的注释就写着"真正的只读必须来自只读数据库账号"。

**当前状态**:#5402 做到了应用层能做的最紧(CTE 一律拒、跨服务器写一律拒、检测降级为尽力而为、残留精确标注),但**不合并**,因为它取决于一个产品边界决定:

> **待 owner 裁决**:K3 可达的数据源,要不要在注册时强制只读账号/只读连接?
> - 要 → 围栏变可证明(账号不能写,洗地无用);
> - 不要(任意写 SQL 是产品需求) → 对"内部人蓄意把 K3 包装成通用可写源"这一路,围栏尽力而为、非可证明,与"有写权限的 DBA 能写 K3"同类。

## 四、验证纪律:本轮沉淀的四类漏法

对抗验证(N 路怀疑者押证伪 + 变异测试员做作者未做的变异)本轮抓到的、单靠 CI+作者自证发现不了的:

1. **假件替真理背书**(早前 #5376):mock 把安全语义写死,真代码改坏照绿;
2. **守卫没接 CI = 死代码**(早前 #5378):测试写得好但没人执行;
3. **边界靠自律**:#5401 跨租户删除锁、#5403 未钉租户谓词、#5402 G-4 四重击穿——核心属性守住,边角藏洞;
4. **虚构交付报告**(#5400 首版):报告了不存在的提交号/PR。**验收第零步永远是 `git ls-remote` 验分支、`gh pr view` 验 PR,再谈内容。**
