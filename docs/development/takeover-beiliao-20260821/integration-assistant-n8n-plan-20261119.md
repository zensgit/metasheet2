> **基线**：代码引用在 main `df83192d9`（2026-11-19）上核过；ADR #6914 的引用取自它自己的分支 `docs/ipaas-steps-s1-s4-adr-20261116`（v5，2026-11-19），行号以那份 ADR 的冻结基线为准。

## 0. 结论先说

1. **类 n8n 的「引擎」已经做了一大半，缺的是「产品壳」。** 之前三条工作——I 链（两套引擎接通、定时作业、作业完成事件）、S 线（只调已批准具名操作的连接步骤、步骤间传值、转换步骤、单一出网门）、宜搭对接（三张表单、草稿编译、测试副本、发送门）——正是 n8n 的触发器、节点、表达式、凭据、执行记录这几层，而且每一层都带着本项目要的审批、开关、审计与 values-free。今天客户用不起来，不是因为少一套引擎，而是因为：① S 线还在 ADR / 本地切片阶段；② 没有一个把这些拼成「流程」的编辑器；③ 没有面向搭流程的人的执行历史与连接目录；④ 没有 AI 帮人起草。
2. **建议的形态：编辑器 = 现有自动化规则的「流程视图」，不另起引擎。** 一条流程就是一条 `automation_rules` 规则：触发器是规则的触发，节点是规则的动作，`{{steps.<key>.output…}}` 是 S2 的引用语法。编辑器存的就是规则 JSON，过的就是同一个保存门。这样所有已有的守卫（具名操作、出网门、K3 永久围栏、开关、授权主体复核、日志脱敏）自动对编辑器生效，不需要再证一遍。
3. **首期用「线性步骤」视图，不做自由画布。** 冻结基线 v2.3 §10 写了「不做通用画布、任意节点调任意 API、任意代码节点」，owner 2026-11-19 在 ADR #6914 OQ1 上刚确认它仍然成立。线性步骤（n8n 外观、自上而下一列卡片）能覆盖首发场景，而且不碰这条裁定；分支画布、子流程、代码节点放到第 5 阶段，**要 owner 改裁基线 :738 才开**（§7 决定 1）。
4. **AI 助手只起草、不执行。** 它读的是「已批准操作目录 + 节点类型 + 保存门规则」，产出一份规则 JSON 草稿，由人保存、由同一个保存门校验、按同样的门启用。它不接触客户数据值；调用外部大模型本身属 O ④（对外发送），要 owner 批（§7 决定 2）。
5. **和 222 首发的关系：不抢路。** 首发关键路径（R85 安装、宜搭窗口一 / 二、AIS #6915 → Y5a #6786、D21 fence）一项都不依赖这份方案。第 1 阶段只做前端视图、不加后端能力，可以和 S1-a / S2-a 的本地开发并行；第 2 阶段就是 ADR #6914 的形态 B，排在宜搭剩余系列合并之后（R-94 ②）。

## 2. 对照 n8n：差距与处理

处理口径：**照搬** = 思路照搬，形态与 n8n 基本一致；**改形态** = 要有，但按本项目的受控 / 审批 / 租户约束改；**不做 / 后置** = 本期不做，写明拉入条件。所有项都只借思路、不用 n8n 代码（R-94 ④：许可限制，且它的 HTTP / Code 节点会绕过本系统的出站闸）。

| n8n 能力 | 我们现在 | 处理 | 怎么做 / 为什么 |
|---|---|---|---|
| 可视化工作流编辑器 | 表单式规则编辑器，无流程视图 | **改形态** | 首期线性步骤视图，存的仍是规则 JSON；自由画布第 5 阶段、要改裁基线 :738（§7 决定 1） |
| 触发器：定时 | `schedule.cron` / `interval` / `date_field` | **照搬（已有）** | 带外部读的规则首片只许两种定时、间隔 ≥15 分钟（ADR #6914 Q6） |
| 触发器：手动执行 | 合成预览路由；S4-d 点选一行预览 | **照搬** | 预览专用，带点选行的规则不能启用 |
| 触发器：Webhook / 记录事件 | 入站 webhook 与记录事件已有 | **改形态** | 普通规则照用；**驱动外部读**的 owner 已裁不放开（ADR #6914 OQ4）；放开要限只读、显式声明、速率上限 |
| 触发器：另一个流程完成 | `integration.run_finished` | **照搬（已有）** | 一次作业一条摘要事件 |
| 节点库 / 连接器库（数百个） | 9 个适配器种类 | **改形态** | 不追数量。每个连接器 = 适配器 + 种类准入 + 已批准具名操作；按客户出处逐个加（PLM、K3 只读、宜搭、HTTP） |
| HTTP Request 节点（任意 URL） | 没有给规则作者的任意 HTTP | **不做** | owner 11-19 确认「不做任意节点调任意 API」；以「具名操作」代替：集成管理员写并批准，规则作者只能选 |
| 凭据管理 | 登记处 + 加密凭据库 | **照搬（已有）** | 规则作者永远拿不到明文；换 origin 必须重给凭据（S0-b / S1-c） |
| 表达式与数据映射 | `{{a.b}}` 模板；`{{steps…}}` 已定语法；8 种转换；宜搭规划器 | **改形态** | 表达式是闭集语法，不是 JS；映射界面做成「左输入字段 → 右目标字段」拖放 |
| Code 节点（JS / Python） | 无沙箱 | **后置** | 冻结基线 §10.1 ⑥ 层；要 QuickJS 沙箱 + 单独权限 + 默认关开关；有真实需求才做 |
| IF / Switch / Merge | 条件分支、并行分支已有 | **改形态** | 普通规则照用；带连接步骤的规则首期不许（ADR #6914 §2 ⑪），第 3 阶段开 |
| 子流程（Execute Workflow） | 无 | **后置** | 第 5 阶段；先要规则调规则的授权主体传递设计 |
| 循环 / 分批（Split in Batches） | 读步骤一步 ≤99 行、不翻页 | **后置** | 翻页与大批量走集成作业（管道），不走规则步骤 |
| 等待（Wait） | `wait_for_callback`、`start_approval` | **改形态** | 首期带连接步骤的规则不得含挂起动作（步骤输出不持久化）；S2-b 快照后解除 |
| 错误分支 / Error Workflow | 第一步失败即停、其余 skipped；作业失败发摘要事件 | **改形态** | 用「集成作业完成（失败）→ 通知」这条规则当错误流程（场景 B），不在单条规则里加错误支 |
| 执行历史 | 执行日志 + 统计 + 重试 | **改形态** | 视图照搬；**日志只记行数与结果码**，不像 n8n 那样存每步完整数据（日志面会保留业务值，ADR #6914 Q7） |
| 重试 | 整次重试；B 类步骤已发送即 `alreadyApplied` | **照搬（已有）** | 读步骤不自动重试、重读；写步骤靠意图台账防重 |
| 固定数据（Pin data）/ 单步调试 | 合成夹具 | **改形态** | 试运行固定用合成数据；对真实系统的预览算 O ① |
| 模板库 | `automationRecipes.ts` | **照搬** | 模板只收有客户出处的场景（A、B、C） |
| 版本 / 环境 / 导入导出 | 规则指纹；读源配置版本化 | **后置** | 交付包导入导出（any-node 计划 S7）有需求再做 |
| 多人 / 权限 | `workflow:*`、`integration:read/write/admin` | **改形态** | 三角色（§3.1）；非管理员可用要补权限种子（基线 ④ 层） |
| AI 节点 / AI Agent | 受治理 AI 边界、列映射副驾、自然语言 → 公式 | **改形态** | 第一步做「AI 起草流程」（不执行）；流程里的 AI 步骤（如物料描述归一）后置，且业务数据只走本地模型（`ai-routing-policy` 的结构性保证） |
| 自托管 / 队列模式 | 单租户现场部署；调度领导锁 | **不需要** | 现场就是自托管；领导锁开关已有 |

## 3. 产品形态

### 3.1 谁用

| 角色 | 在现有权限里是谁 | 在集成助手里做什么 | 不能做什么 |
|---|---|---|---|
| 集成管理员 | 持 `integration:write`（登记外部系统、写并批准读源配置） | 登记连接、写「具名操作」（读源配置）并批准；看所有流程的执行历史 | 不能绕过出站写门；K3 写永久禁止 |
| 流程搭建者 | 规则创建者（备料管理员、实施顾问），持 `workflow:*` 与表权限 | 在编辑器里拖节点、配映射、试运行、申请启用 | 看不到也改不了路径 / 请求体 / 凭据；只能在已批准操作里选 |
| owner | O 层门的裁定人 | 批：真实客户读（O ①）、生产写（O ②）、打开开关与部署（O ④） | — |
| AI 助手 | 不是一个主体；以当前用户的身份起草 | 把一句话翻成规则草稿，解释缺什么批准 | 不保存、不启用、不执行、不读业务值 |

「一个人要同时是三种身份」（规则所有者 + 读源属主戳 + 宜搭锚点 owner）是 ADR #6914 白话终点里的现场约束，编辑器要在「上线门」页签里直接显示出来，而不是让人试到失败。

### 3.3 界面（见原型）

- **左：节点库。** 分四组：触发 / 连接 / 数据 / 落点。没开放的节点照样列出来但上锁，鼠标悬停说明「为什么锁、要谁批、哪个阶段开」——让搭流程的人知道边界在哪，而不是以为系统做不到。
- **中：线性画布。** 一列卡片自上而下，每张卡片显示 `steps.<key>`、一句话配置摘要、门的状态（开关关 / 需 owner 批 / 预览专用）。
- **右：三个页签。** 「配置」（具名操作只能从已批准版本里选，业务键用 `{{…}}` 引用）；「输入 / 输出」（试运行后看每一步的数据，只在本页内存）；「上线门」（这条流程启用前要过的每一道门、T 层还是 O 层）。
- **下：执行历史。** 只显示行数、结果码与停在哪一步——这是日志面 values-free 的直接体现（ADR #6914 §5.7）。
- **顶部：模板、AI 助手、试运行（模拟）、保存草稿、申请启用。**

### 3.4 AI 助手的边界

- **输入**：用户一句话 + 已批准操作目录的**元数据**（操作名、业务键名、输出声明列名）+ 节点类型表 + 保存门规则。**不发送任何记录值、读回值或凭据。**
- **输出**：一份规则 JSON 草稿，加一段「还缺哪些批准」的说明。草稿进编辑器，由人看、改、保存；保存走同一个保存门，所以 AI 出的东西不可能比人手搭的更宽。
- **拒答**：K3 写回、正式表单落点、任意 URL、代码节点——直接说明为什么不行并给替代（原型里有示例）。
- **复用已有的 AI 边界，不另建**：起草走 `GovernedAiService` → `authorizeAiRoute()` 这条唯一的路（`governed-ai-service.ts:9-18`）。路由策略在结构上不让业务类数据去云端、未配置时只许本地（`ai-routing-policy.ts:11-26`）；起草只送元数据，正好落在「非敏感」类。先例是「列映射副驾」（AI 提议、人确认，`schema-mapping-copilot.cjs`）与「自然语言 → 公式」（只送字段名与类型）。
- **对外**：要用云端模型，部署要显式把「非敏感」类列进策略文件，这一步与 `MULTITABLE_AI_ENABLED` 的打开都属 O ④，模型与供应商由 owner 定。

## 4. 架构：复用 I 链与 S 线，不另起炉灶

```
┌──────────────────────── 前端（apps/web） ────────────────────────┐
│  流程编辑器（新视图）   执行历史（新视图）   AI 起草抽屉（第 4 阶段）  │
│        │ 读写同一份规则 JSON                │ 只产出规则 JSON 草稿     │
└────────┼───────────────────────────────────┼────────────────────────┘
         ▼                                   ▼
  自动化规则 API（已有）—— 保存门：闭合键集 / 放置限制 / 触发耦合 / 授权主体盖章
         │
         ▼
  自动化执行器（已有）—— 顺序执行；步骤结果；运行内传值通道（S2，RunValueStore 一般化）
     │                 │                         │
     │ run_integration_job（I 链，已合入）        │ transform_records（S4，纯函数）
     │                 │ call_connection（S3）    │ 宜搭方言 → 只调规划器
     ▼                 ▼                         ▼
  IntegrationRunPort  ConnectionCallPort（S1-b，新端口，插件登记）
     │                 │
     ▼                 ▼
  插件受治理入口（runGovernedStockPrepPull / runGovernedPipeline / runGovernedConfiguredRead[S1-a]）
     │
     ▼
  适配器传输层（已有）—— 出站写门（默认拒）· K3 永久写围栏 · 凭据库（加密）· B2a 读围栏
```

**要点**

1. **一条流程 = 一条规则。** 编辑器不引入新的存储格式。线性视图与规则 `actions[]` 一一对应：卡片顺序 = 数组顺序，`steps.<key>` = ADR #6914 §5.1 的步骤键。第 3 阶段开放分支时，分支卡片映射到规则引擎**已有**的条件 / 并行分支结构，不发明新语义。
2. **编辑器不加新的后端能力。** 它能放出来的节点，只有规则引擎已经能存、能跑、能守的动作类型；没有对应动作的节点在节点库里上锁。这样编辑器的每一个阶段都不需要新的保证类核验——保证类的工作全部留在 S 线与 I 链各自的切片里，按它们自己的门走。
3. **执行历史复用现有日志面。** 执行日志已经有步骤、触发事件与规则快照（经脱敏），I 链还有一次作业一条的摘要事件；新视图只是按流程聚合展示，不加新的落值面。
4. **AI 层是一个纯起草器。** 输入元数据、输出草稿；与执行路径没有任何连接点；走已有的受治理 AI 边界（§3.4）。第 4 阶段单独立项（ADR + O ④）。
5. **与现有编辑器的关系。** 现有 `MetaAutomationRuleEditor.vue` 是 6500 多行的表单编辑器，界面上至多 3 个动作（`:1818`）。流程视图是一个新组件，和它共用同一份草稿模型与保存接口；两者并存、可互相切换，直到流程视图覆盖全部动作类型。动作个数的上限以服务端保存门为准（例如 ADR #6914 的 `call_connection` 至多 8 步），界面不另设更宽的上限。
6. **不新增表、不新增引擎、不嵌 n8n。** 首期（1–2 阶段）的迁移只有 S 线 ADR 已列的两支动作 CHECK（`call_connection`、`transform_records`）。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 「类 n8n」被理解成「任意 API、任意代码」，范围失控 | 节点库只放已有动作；锁着的节点写明为什么锁、要谁批；§7 决定 1 |
| 编辑器与旧规则编辑器存出不同的 JSON，产生第二种规则 | 第 1 阶段验收要求逐字节相同；编辑器复用同一个保存接口与同一套类型 |
| 流程搭建者以为试运行 = 真跑 | 试运行固定标「模拟」，只用合成数据；真读的预览要 O ① |
| 首发路径被挤占 | §6 排序；第 1 阶段只在空档做，任何时候首发事项可以打断 |
| AI 起草泄露客户值 | 只给元数据；不给记录值、读回值、凭据；外部调用 O ④ |
| n8n 许可 | 只借思路，不嵌代码、不引依赖（R-94 ④） |

## 附：原型说明

`integration-assistant-prototype-20261119.html` 是一份静态页面：

- 默认打开场景 C（PLM 物料 → 宜搭测试副本草稿），右侧显示 PLM 读取节点的配置；
