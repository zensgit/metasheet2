备料数据地图

备料工作台的九个页面、十几张多维表、四条写入管线与守卫之间的读写和键连关系。每条结论都由五路取证对着代码核过;凡是"设计里有、代码里没有"的,标了出来。

一句话模型

PLM 是结构的权威(谁是谁的儿子、图号、材料、数量);人是自己那几列的权威(备料情况、需求日期、采购/仓库完成标记);系统的活儿只有一件:每次重拉 BOM 时,让这两件事同时为真。

PLM 改了要跟着改;人填过的东西一个字都不能被覆盖。整套代码里最重的那堵墙(人列墙)就是为这一句话立的。
plm_system:机器写、人不该写human_preserved:人写、机器绝不写守卫 / 门

一根 BOM 线,在系统里有两个身体

一次展开产出一批"展开行"。同一行会分叉成两条完全不同的落地——一条是可变的工作行(人在上面填字),一条是不可变的版本记录(PLM 当时说了什么)。它们只由"同一批展开行喂出来"这个事实相连,没有任何键把两张表 join 起来。

展开行PLM 树递归、SysVer 钉版本path / componentSourceId / totalQuantity
主表行20 13 人在这里填idempotencyKey = {projectNo, componentSourceId, parentSourceId, path}(字面 JSON)
快照行不可变、create-onlysnapshotLineId = hash(batchId | pathKey)
账本行人对冲突的裁决rowIdentity = idempotencyKey;decisionId = hash(stableKey, fingerprint)
备料行生成物,ERP 单位stockPrepLineId = hash(batchId | snapshotLineId)
导出行12 列 Excel读主表,按 projectNo 过滤

主表的键里天然嵌着项目号——结转的防伪、账本的命名空间隔离都靠这一点。快照行的 sourceFingerprint 只存哈希,原值绝不入列。

同一个概念,两套字段名

不是随意的:租户 ext_ 扩展列与冻结模板 id 是互斥命名空间,出厂客户包已经占了 ext_parentDrawingNo / ext_parentName / ext_spec;主表若也叫 spec,每个装了包的部署都会在自检时炸(FIELD_ID_TEMPLATE_COLLISION)。所以主表只能另起一套词。

A · 拉取刷新(主表管线)——按下"同步这个项目"时真正发生的事

默认:沙箱专用。没有服务端生产策略时 apply 门无条件拒绝正式主表。动:读写主表(或沙箱);账本由第 2 步 reconcile 单独写;审计。

  1. B2a 读授权门(未设登记表则休眠)
  2. 载入源适配器、解密凭据
  3. ext 字段映射与动作一致性断言
  4. expandPlmProjectBom 从外部 PLM 展开,铸出 idempotencyKey
  5. 按 projectNo 回读现有主表行
  6. 重复诊断 + 冲突计划;规划器顺带把父图号/父名称/规格反规范化到载荷
  7. 可选合入账本 resolver 并重算
  8. 铸出 revision 与一次性 dryRunToken(以上全程零写)
  9. apply:先过沙箱/生产门,再过 B2a,再消耗 token(取出即删),然后写

B · 快照留痕(九张冻结 MVP 表管线)

默认:工作台那条腿默认关——mvp-persist 路由需要 env 字面量 'true'。动:批次/快照行/运行/项目,全部 create-only(只有项目表允许 patch)。

  1. 路由铸身份:projectId = hash(tenant\naction\nprojectNo)、syncRunId、legacyBatchId
  2. 按 readPlan.batchIdentity.mode 决定 snapshotBatchId(默认 source_revision;按小时分批 opt-in)
  3. 同一事务:先取正式表栅栏,再取项目锁与批次锁
  4. 锁内分配 snapshotVersion = max+1,严格单调守卫
  5. 顺序写 batch(1 行)→ line(N 行)→ run → project 三键 patch

注意:另有两个落库入口只由 admin 门控、没有 env 开关(老的 /mvp/sync/persist、PLM source-run 自动落库桥)。"快照管线关着"对工作台成立,对整个表族不成立。

C · 裁决账本——人对冲突的答案怎么被记住并复用

默认:人填的值是只读参考,机器永不消费;唯一把人填的值写回主表的路径是 carry 确认。动:账本、对账租约表、审计。

  1. reconcile 服务端重跑只读计划(故意不带 resolver,让 revision 稳定)
  2. 取对账租约,抢不到即 409 BUSY
  3. 从计划的 manual_confirm 派生三类候选:keyed 重复键、匿名保留、carry 保留
  4. 逐候选:命中活行不动;同 stableDecisionKey 但指纹变了 ⇒ 旧行 superseded + 新建;命中作废行 ⇒ 重开
  5. 人在确认队列 confirm,写 resolutionAction / resolvedValue / notes
  6. 下一次 dry-run 时 resolver 读回账本,把对应 hold 解成决定

D · 生成备料行

默认:依赖快照管线的产物——默认装机下无输入可跑。动:读五张(批次/快照行/ERP 物料/映射/规则),写备料行、异常、运行。

  1. 取一个完整批次的快照行(不完整即拒)
  2. 读 ERP 物料、映射、规则及现有备料行/异常行
  3. 逐行解算成 ERP 可发料数量
  4. 按 stockPrepLineId upsert 备料行,并显式清空模板缺席列(重跑不留混血行)
  5. 异常 create-only,人处置三件套被剥离
  6. 重新统计未解决的阻断异常得出 ready

E · 主数据(ERP 物料 / 图号映射 / 单位换算)

默认:三张表的所有读写路由全部 admin,操作员一个都碰不到。映射候选必须显式给版本策略;退役 = isActive:false,永不删。

F · 导出——交到车间手里的那张 Excel

门:stock-prep:operate + 租户由宿主背书成员关系。动:只读主表(经绑定的 action.target,与写手同一条缝);审计。

  1. 取 action.target(不再硬编码正式主表——第一版正因此每个项目都 404)
  2. 按物理 projectNo 过滤、active≠false,分页 500×100,上限 20000
  3. 12 列固定顺序投影;三列原生值为空时逐行退回 ext_ 兜底
  4. 未绑定的列以 unresolvedColumns 值无关地报出,把"空白"和"没接线"分开

零行 ⇒ 404;有行但全 inactive ⇒ 合法的只有表头的导出。无租户的平台管理员在这里 403——看得见最多 Tab 的人反而导不出数据,这是刻意的。

G · 客户包安装与列写权限

默认:出厂的两个包都只声明 roleViews(藏列),没有一个声明 fieldWritePolicies——列写权限是已交付的能力,不是已交付的配置。声明了才会:角色预检(未知角色 422,此时一列未建)→ 逻辑列 id 翻物理 id → 宿主端口写 field_permissions(宿主没注入端口就 503)→ 陈旧写域普查只报告。

H · 交接棒 #5442 在飞

默认:双重 fail-closed——无服务端配置在碰 DB 之前就 501,表永远为空;无行读作游标 0。projectNo 先做形状校验(它会被插进钉钉 markdown)→ 存在性探针 → 事务内行锁 + step_index / notified_step_index 双 CAS,零行更新即 409 → store 确认后才写审计 → 发群通知(dispatch 永不抛,只返枚举)。

直言缺口

沙箱孪生才是行真正落地的地方。默认装机下 apply 无条件拒绝正式主表,行落在 plm_stock_preparation_sandbox*,正式主表是空的。任何"我们主表里有数据"的说法,先确认这台机器装的是哪张。
生产 apply 门没有宿主配置通道。门是完整的 fail-closed 代码,但宿主唯一的 config 装配点只产出六个键,不含 stockPrepApplyProduction。演示与首个窗口落沙箱表(D1=B);加载器是演示后事项。
